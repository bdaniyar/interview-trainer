# Recursive CTE

## Учебные цели

После урока вы сможете объяснить механизм Recursive CTE, предсказать строки на пустых и граничных входах, написать запрос и проверить его контракт.

## Теория

### Что это

SELF JOIN показывает только один шаг связи. Когда число руководителей заранее неизвестно, нужен обход: текущая строка порождает следующую, и работа продолжается до корня. Рекурсивный CTE описывает такой обход в одном SELECT.

### Как работает

Запись состоит из anchor, UNION ALL и recursive term. Anchor создаёт стартовые строки. PostgreSQL помещает их в рабочую таблицу; рекурсивная часть читает текущую порцию, строит следующую, затем заменяет рабочую таблицу. При пустой следующей порции обход заканчивается. Это итеративное выполнение рекурсивного описания.

Depth — часть результата: старту назначают 0, следующему шагу depth+1. Порядок выдачи сам по себе не доказывает порядок обхода; внешний ORDER BY depth задаёт нужное представление. UNION удаляет полные повторные строки, однако depth меняется на каждом шаге: наличие UNION вместо UNION ALL не гарантирует остановку цикла.

### Важный нюанс / ограничение

Внешний ключ разрешает ссылку только на существующий id, но не гарантирует отсутствие циклов. Ниже безопасный пример хранит посещённые числовые id в тексте с разделителями: /2/ не совпадёт с /12/. Для общего production-графа PostgreSQL предлагает CYCLE/массивы; этот ограниченный Lab их не разрешает. У задачи банка есть ацикличная входная гарантия: скрытые fixtures ей соответствуют. Отдельная проверка запускает бесконечную рекурсию и подтверждает deadline/cleanup. Обрыв на произвольной глубине не является корректным решением основной задачи для более длинной допустимой цепочки.

## Модель понимания

Проверьте anchor, направление ребра, depth=0, прекращение и порядок. FK и отсутствие циклов — разные гарантии. Не используйте deadline как условие правильного завершения.

## Что нужно знать на Junior

### Обязательно

Anchor создаёт начальный набор, recursive term получает следующие строки из рабочей порции, UNION ALL объединяет результаты. Завершение наступает, когда новая порция пуста.

Удаляются полные одинаковые строки. Если в строке растёт depth, повтор посещённого id имеет другое значение depth и не считается дубликатом. Нужна проверка посещений либо доказанная ацикличность данных.

## Примеры кода

Все примеры ниже выполняются в PostgreSQL 17 на неизменном shop-v1 либо явно заданных синтетических VALUES. SQL NULL обозначает отсутствие значения; строка `NULL` была бы другим значением.

### Пример 1

Anchor возвращает 3. Следующие рабочие порции содержат 2 и 1, затем ни одной строки: у 1 parent_id NULL.

```sql
WITH RECURSIVE nodes AS (SELECT * FROM (VALUES (1,NULL::integer),(2,1),(3,2)) n(id,parent_id)), walk AS (SELECT id,parent_id,0 AS depth FROM nodes WHERE id=3 UNION ALL SELECT n.id,n.parent_id,w.depth+1 FROM nodes n JOIN walk w ON n.id=w.parent_id) SELECT id,depth FROM walk ORDER BY depth;
```

Ожидаемый результат; типы: `id: int4`, `depth: int4`.

| `id` | `depth` |
| --- | --- |
| 3 | 0 |
| 2 | 1 |
| 1 | 2 |

### Пример 2

Данные содержат цикл 1→2→1. Проверка посещённых узлов останавливает повтор 1; depth<20 — дополнительный бюджет этого примера, не универсальное доказательство полноты.

```sql
WITH RECURSIVE nodes AS (SELECT * FROM (VALUES (1,2),(2,1)) n(id,parent_id)), walk AS (SELECT id,parent_id,0 AS depth,'/'||id::text||'/' AS path FROM nodes WHERE id=1 UNION ALL SELECT n.id,n.parent_id,w.depth+1,w.path||n.id::text||'/' FROM nodes n JOIN walk w ON n.id=w.parent_id WHERE w.depth<20 AND w.path NOT LIKE '%/'||n.id::text||'/%') SELECT id,depth,path FROM walk ORDER BY depth;
```

Ожидаемый результат; типы: `id: int4`, `depth: int4`, `path: text`.

| `id` | `depth` | `path` |
| --- | --- | --- |
| 1 | 0 | /1/ |
| 2 | 1 | /1/2/ |

## Типичные ошибки

JOIN по n.parent_id=w.id идёт вниз, а не вверх. Depth=1 у anchor нарушает условие. LIMIT 3 на внешнем запросе скрывает длинную цепочку. FK не доказывает ацикличность. Рекурсия без условий может занять весь бюджет; TTL/deadline защищают среду, но не исправляют алгоритм.

## Практика

Данные: используйте синтетические `nodes` из первого примера: 3→2→1→NULL; отсутствующий id — 99, новый узел — 4→3. Измените anchor синтетического примера на отсутствующий id и объясните пустой результат. Затем добавьте четвёртый узел и предскажите глубины. В циклическом примере сохраните защиту и проверьте, почему один UNION с включённым depth не устраняет повтор узла.

Сначала запишите ожидаемые столбцы, типы и строки вручную; затем используйте Run. Сравнивайте также пустой вход и повторные значения. Дополнительная практика не выдаёт статус основной задачи.

## Задача

**sql.subquery.32 — Цепочка менеджеров**

От пользователя с id=4 пройдите вверх по manager_id. Верните id,depth: старт на глубине 0, далее непосредственный руководитель. Сортировка depth по возрастанию. В проверочных данных цепочка ациклична; при отсутствии id=4 результат пуст.

Исходные таблицы смотрите в Explorer. Run выполняет запрос на публичных данных, Check проверяет отдельные наборы. Нужны все требуемые строки и только указанные столбцы. Принимаются эквивалентные SELECT независимо от выбранного синтаксиса. SQL XP отключён; черновик сохраняется в браузере.

<details>
<summary>Показать решение для самопроверки</summary>

```sql
WITH RECURSIVE chain AS (SELECT id,manager_id,0 depth FROM users WHERE id=4 UNION ALL SELECT u.id,u.manager_id,c.depth+1 FROM users u JOIN chain c ON u.id=c.manager_id) SELECT id,depth FROM chain ORDER BY depth;
```

Нужны все предки вверх, исходная строка на depth=0 и пустой результат без стартового пользователя.

</details>
