# ORDER BY, LIMIT и OFFSET: порядок и страницы результата

## Учебные цели

После урока ты сможешь:

- задать порядок строк через `ORDER BY`, `ASC` и `DESC`;
- объяснить, зачем нужен второй ключ при одинаковых значениях первого;
- ограничить результат и получить страницу через `LIMIT` и `OFFSET`;
- отличить стабильный порядок от неизменности данных между запросами;
- решить задачу о последних заказах в SQL Lab.

## Теория

### Что это

Без `ORDER BY` SQL не обещает порядок строк. Сегодня строки могут выглядеть отсортированными по ID, а после изменения данных или плана выполнения прийти иначе. Порядок вставки тоже не является контрактом результата.

Вспомни три разных вопроса: `WHERE` — какие строки подходят, `SELECT` — какие поля показать, `ORDER BY` — в какой последовательности вернуть строки. `LIMIT` и `OFFSET` выбирают часть полученной последовательности.

### Как работает

Для наших простых запросов полезна модель: источник → фильтр → поля результата → сортировка → пропуск строк → ограничение количества. Это объясняет результат, а не обещает конкретный физический план PostgreSQL.

### ASC и DESC

`ASC` означает возрастание и используется по умолчанию. `DESC` означает убывание. Например, товары от дешёвого к дорогому:

```sql
SELECT name, price
FROM products
ORDER BY price ASC;
```

На публичных данных получим Python Book — 30, SQL Book — 40, Keyboard — 90. Обратное направление:

```sql
SELECT name, price
FROM products
ORDER BY price DESC;
```

Теперь первой будет Keyboard, затем SQL Book и Python Book. Направление относится к тому выражению, после которого написано. `ORDER BY price, id DESC` означает цену по возрастанию, а ID по убыванию внутри одинаковых цен.

### Несколько ключей сортировки

Следующий ключ используется только при равенстве предыдущего:

```sql
SELECT id, country
FROM users
ORDER BY country ASC NULLS LAST, id ASC;
```

Публичный результат: сначала ID 4 со страной GE, затем ID 1 и 2 со страной KZ, затем ID 3 с NULL. Для двух пользователей KZ порядок задаёт `id`. Здесь `NULLS LAST` явно помещает неизвестную страну в конец. PostgreSQL по умолчанию использует NULLS LAST для ASC и NULLS FIRST для DESC.

Если основной ключ не уникален, добавь ключ, который делает весь порядок однозначным. У `users` и `orders` таким ключом может быть первичный ключ `id`. Сортировать только по времени недостаточно: несколько записей могут иметь одинаковый `created_at`.

Например, **возможная ситуация, не текущий seed**: пользователи с ID 7 и 9 зарегистрировались в один момент. `ORDER BY created_at ASC` не определяет, кто будет первым. Дополнительный `id ASC` ставит 7 перед 9. Для обратного порядка оба направления нужно задать явно.

### LIMIT: не больше указанного количества

Первая страница пользователей в порядке регистрации:

```sql
SELECT id, email
FROM users
ORDER BY created_at ASC, id ASC
LIMIT 2;
```

В публичном наборе это ID 1 и 2. `LIMIT 2` означает «не больше двух строк»: если подходящих строк одна, вернётся одна, если нет — пустой результат.

Сам по себе LIMIT не означает «самые новые», «самые дорогие» или «первые по ID». Сначала нужен соответствующий порядок. `WHERE` тоже важен: последние подходящие записи и последние записи вообще — разные условия.

### OFFSET и обычная пагинация

`OFFSET` пропускает указанное количество строк, после чего применяется LIMIT:

```sql
SELECT id, email
FROM users
ORDER BY created_at ASC, id ASC
LIMIT 2 OFFSET 2;
```

Это ID 3 и 4 — следующая страница публичного набора. Для страниц по две строки смещения равны 0, 2, 4 и так далее. Если смещение больше числа строк, результат пустой. `OFFSET 0` ничего не пропускает.

При равных датах без второго ключа соседние страницы могут получить повторяющиеся или пропущенные записи: две части запроса используют порядок, который не задан полностью. Уникальный дополнительный ключ устраняет эту неоднозначность **для неизменного набора данных**.

### Важный нюанс / ограничение

Даже полный ORDER BY не замораживает данные. Если между запросами другой пользователь добавит запись перед началом списка, границы OFFSET-страниц сдвинутся. Полный порядок и согласованный снимок данных — разные гарантии.

Большой OFFSET может быть дорогим: PostgreSQL всё равно приходится вычислять и пропускать предыдущие строки. Поэтому для длинных лент часто используют курсорную, или keyset-пагинацию.

### Идея keyset-пагинации

Вместо «пропусти две строки» передают значения последней строки предыдущей страницы. В нашем возрастающем списке после пользователя 2 с датой 2026-01-02 нужны более поздняя дата либо та же дата и больший ID:

```sql
SELECT id, email
FROM users
WHERE created_at > TIMESTAMPTZ '2026-01-02T00:00:00Z'
   OR (created_at = TIMESTAMPTZ '2026-01-02T00:00:00Z' AND id > 2)
ORDER BY created_at ASC, id ASC
LIMIT 2;
```

На публичных данных снова получим ID 3 и 4. Курсор должен включать оба ключа и соответствовать направлению сортировки. Подход может избежать большого пропуска строк при подходящем индексе. Но он не является общим обещанием неизменности списка: обновления ключей и удаления тоже требуют продуманного поведения API. Индексы и согласованность разберём отдельно.

### Где используется в backend

В API списка товаров пользователь может выбрать цену по убыванию. В API истории заказов обычно нужны свежие записи и стабильный порядок при одинаковом времени. В обоих случаях сначала зафиксируй фильтр, ключи сортировки и правило выбора страницы, затем проверь границы на маленьком наборе данных.

## Модель понимания

Представь полностью упорядоченную очередь подходящих строк. OFFSET убирает начало очереди, LIMIT забирает не больше указанного количества оставшихся строк. Если строки с одинаковым первым ключом не упорядочены вторым, граница страницы неоднозначна.

## Что нужно знать на Junior

### Обязательно

- Без ORDER BY порядок не гарантирован.
- ASC и DESC задаются отдельно для каждого ключа.
- Неуникальный первый ключ требует дополнительного уникального ключа для стабильного порядка.
- LIMIT ограничивает число строк, OFFSET пропускает строки.

### Полезно

Понимать разницу между OFFSET-страницей и курсором по последнему ключу, а также влияние конкурентных изменений списка.

### Можно не учить глубоко

Внутренности сортировки PostgreSQL и сложные схемы курсоров пока не нужны. Начни с правильного результата и понятного контракта API.

## Примеры кода

Сначала отбор, затем порядок и ограничение:

```sql
SELECT name, price
FROM products
WHERE price >= 40
ORDER BY price DESC, id DESC
LIMIT 1;
```

Книгу с ценой 30 исключает WHERE. Из оставшихся товаров сортировка и LIMIT выбирают Keyboard с ценой 90. Если изменить направление сортировки, первой станет SQL Book с ценой 40; условие отбора при этом останется прежним.

## Типичные ошибки

- Считать видимый порядок строк без ORDER BY гарантированным.
- Написать DESC только после второго ключа и ожидать убывания обоих.
- Сортировать по ID вместо даты: больший ID не обязан означать более поздний заказ.
- Забыть правило для одинакового времени.
- Заменить LIMIT условием по известным ID публичного набора.
- Считать OFFSET быстрым при любом размере списка.
- Обещать неизменные страницы при конкурентных вставках только благодаря ORDER BY.

## Практика

### Основная задача: последние два заказа

Верни два последних заказа из `orders` по `created_at`. Если время одинаковое, заказ с большим `id` должен идти первым. Покажи только `id`, затем `created_at`. Если заказов меньше двух, верни все имеющиеся.

Посмотри таблицу в Explorer. Напиши запрос и нажми **Run**, затем **Check**. Здесь важны и состав строк, и их позиции. Проверка использует другие даты, ID, одинаковые моменты времени и маленькие таблицы. Ручной список публичных заказов не заменяет запрос к данным.

```sql
SELECT id, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 2;
```

В публичном наборе первыми идут заказы 14 и 13. При одинаковом времени второй ключ определяет порядок ID и то, какие строки попадут в ограничение. OFFSET в этой задаче не нужен.

Выведи `name` и `price` второго по дороговизне товара. Используй цену по убыванию и ID по убыванию при равных ценах. Сначала предскажи результат, затем проверь его через Run.

## Хорошие ответы

<details>
<summary>Показать ответы для собеседования</summary>

### Короткий ответ

ORDER BY задаёт последовательность, LIMIT ограничивает количество, OFFSET пропускает начало. При одинаковых значениях первого ключа нужен дополнительный ключ, например ID.

### Ответ уровня Junior

Я задаю полный порядок результата и проверяю совпадения дат на границе страницы. LIMIT без такого порядка не определяет, какие строки я получу. Большой OFFSET требует пропустить предыдущие строки, поэтому для длинной ленты рассматриваю курсор по паре времени и ID.

### Follow-up

Полный порядок не защищает OFFSET-страницы от сдвига при вставке новых записей. Курсор решает часть этой проблемы, но требования к согласованности данных и изменениям ключей надо определить отдельно.

</details>

## Критерии хорошего ответа

- Различаются отбор, порядок и ограничение количества.
- Объяснены одинаковые значения ключа и роль ID.
- LIMIT допускает результат короче установленного числа.
- Нет обещания стабильных страниц при любых конкурентных изменениях.

## Шпаргалка

- Порядок — только через ORDER BY.
- Направление каждого ключа задаётся отдельно.
- Совпала дата — сравни следующий ключ.
- OFFSET пропускает, LIMIT ограничивает.
- Для длинной ленты рассмотрим курсор по последней паре ключей.
