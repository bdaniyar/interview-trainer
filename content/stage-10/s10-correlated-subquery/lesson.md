# Correlated subquery

## Учебные цели

После урока вы сможете объяснить механизм Correlated subquery, предсказать строки на пустых и граничных входах, написать запрос и проверить его контракт.

## Теория

### Что это

Коррелированный подзапрос использует значение текущей внешней строки. Для каждого заказа можно логически спросить: «какая последняя дата у заказов именно его владельца?» Без ссылки на владельца получается другой вопрос — о последнем заказе всего магазина.

### Как работает

Внешний alias o и внутренний i обозначают разные роли orders. Условие i.user_id = o.user_id ограничивает область внутреннего агрегата. MAX возвращает время, а сравнение внешнего created_at с этим временем сохраняет все совпадения. Если два заказа пользователя созданы в один последний момент, оба правильны. Нельзя незаметно заменить такую задачу на выбор одного заказа по максимальному id.

Логическая модель «проверка для каждой внешней строки» помогает понять результат, но не описывает обязательное число сканирований. PostgreSQL может применять разные планы. Эквивалентны соединение с агрегатом максимальных дат и оконный MAX с последующим внешним фильтром. ROW_NUMBER=1 эквивалентен только контракту «ровно один заказ» с отдельным правилом разрешения ties.

### Важный нюанс / ограничение

Банк исторически сортирует эту задачу только по user_id. Внутри пользователя все последние заказы имеют одинаковую дату, и дополнительного порядка контракт не задаёт. Check сравнивает последовательность групп user_id и мультимножество строк каждой группы. Он принимает любой порядок связанных максимумов, но отклоняет потерю строки, повтор и перестановку пользователей. Для production API, которому нужна стабильная пагинация, добавьте согласованный полный порядок.

## Модель понимания

Область сравнения задаёт корреляция. MAX времени возвращает время, а не выбранный id. Равные максимумы сохраняйте все, если контракт не требует одного победителя.

## Что нужно знать на Junior

### Обязательно

Один обозначает проверяемый заказ, второй — набор для сравнения. Ссылка внутреннего условия на внешний alias задаёт корреляцию.

Нет. Требуются реальные планы, объёмы, индексы и измерения. Синтаксическая вложенность сама по себе не определяет стратегию выполнения.

## Примеры кода

Все примеры ниже выполняются в PostgreSQL 17 на неизменном shop-v1 либо явно заданных синтетических VALUES. SQL NULL обозначает отсутствие значения; строка `NULL` была бы другим значением.

### Пример 1

Для books минимум 30, поэтому выбран 100; у hardware единственный товар 101.

```sql
SELECT p.id,p.category FROM products p WHERE p.price=(SELECT MIN(q.price) FROM products q WHERE q.category=p.category) ORDER BY p.id;
```

Ожидаемый результат; типы: `id: int8`, `category: text`.

| `id` | `category` |
| --- | --- |
| 100 | books |
| 101 | hardware |

### Пример 2

Без корреляции минимум общий: hardware больше не имеет своего победителя.

```sql
SELECT p.id FROM products p WHERE p.price=(SELECT MIN(q.price) FROM products q) ORDER BY p.id;
```

Ожидаемый результат; типы: `id: int8`.

| `id` |
| --- |
| 100 |

### Пример 3

Оконная запись сохраняет исходные строки, затем внешний запрос сравнивает цену с минимумом категории.

```sql
SELECT id FROM (SELECT id,price,MIN(price) OVER(PARTITION BY category) AS cheapest FROM products) p WHERE price=cheapest ORDER BY id;
```

Ожидаемый результат; типы: `id: int8`.

| `id` |
| --- |
| 100 |
| 101 |

## Типичные ошибки

Забыть ссылку на внешний alias — значит посчитать глобальный максимум. Условие i.user_id=i.user_id не является корреляцией. MAX(id) не обязан соответствовать MAX(created_at). DISTINCT ON оставляет одного победителя и не сохраняет все равные даты.

## Практика

Данные для самостоятельной проверки: категория A, цены 10,10,30; категория B, цены 7,9. Правильные победители: обе строки A с ценой 10 и строка B с ценой 7. На независимых VALUES создайте две категории, в одной две одинаковые минимальные цены. Верните всех победителей коррелированным подзапросом и соединением с MIN. Проверьте совпадение мультимножеств. Затем измените условие на ровно одного победителя и отдельно задайте tie-breaker.

Сначала запишите ожидаемые столбцы, типы и строки вручную; затем используйте Run. Сравнивайте также пустой вход и повторные значения. Дополнительная практика не выдаёт статус основной задачи.

## Задача

**sql.subquery.31 — Последний заказ пользователя**

Верните id,user_id всех заказов с максимальным created_at своего пользователя. При равных максимальных timestamps нужны все такие заказы. Сортировка по user_id; внутри одного пользователя порядок свободный.

Исходные таблицы смотрите в Explorer. Run выполняет запрос на публичных данных, Check проверяет отдельные наборы. Нужны все требуемые строки и только указанные столбцы. Принимаются эквивалентные SELECT независимо от выбранного синтаксиса. SQL XP отключён; черновик сохраняется в браузере.

<details>
<summary>Показать решение для самопроверки</summary>

```sql
SELECT o.id,o.user_id FROM orders o WHERE o.created_at=(SELECT MAX(i.created_at) FROM orders i WHERE i.user_id=o.user_id) ORDER BY o.user_id;
```

Сравнивайте дату в пределах своего пользователя; сохраните все максимальные совпадения и порядок групп user_id.

</details>
