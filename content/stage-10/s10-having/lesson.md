# HAVING: условия на итог группы

## Учебные цели

После урока ты сможешь:

- отделить фильтр исходных строк от фильтра групп;
- использовать HAVING с COUNT и SUM;
- совместить WHERE и HAVING, понимая влияние каждого;
- проверить границу «минимум два»;
- найти пользователей с несколькими заказами в SQL Lab.

## Теория

### Что это

WHERE отвечает на вопрос «какие строки взять в расчёт?». HAVING — «какие уже посчитанные группы оставить?». Эти условия применяются на разных логических этапах и не являются общей заменой друг другу.

Например, найдём категории, в которых минимум два товара:

```sql
SELECT category, COUNT(*) AS products_count
FROM products
GROUP BY category
HAVING COUNT(*) >= 2
ORDER BY category;
```

В публичном наборе останется books / 2. Категория hardware содержит один товар и не проходит условие на размер группы.

### Как работает

Сначала GROUP BY формирует существующие группы, затем HAVING проверяет их показатели. Как и WHERE, он оставляет только TRUE: FALSE и UNKNOWN не проходят.

Полезная логическая последовательность для наших запросов: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Это модель результата, а не физический план. PostgreSQL может выбрать разные алгоритмы и безопасно переставлять часть вычислений, сохраняя смысл запроса.

### Строим запрос по шагам

Задача для примера: оставить статусы, у которых общая сумма заказов не меньше 100. Сначала посчитаем все группы:

```sql
SELECT status, COUNT(*) AS orders_count, SUM(total) AS amount
FROM orders
GROUP BY status
ORDER BY status;
```

Публичные итоги: cancelled / 1 / 40.00, new / 1 / 80.00, paid / 3 / 350.00. Теперь добавим условие на сумму:

```sql
SELECT status, COUNT(*) AS orders_count, SUM(total) AS amount
FROM orders
GROUP BY status
HAVING SUM(total) >= 100
ORDER BY status;
```

Останется paid / 3 / 350.00. HAVING исключил две группы целиком. Он не оставляет внутри группы только отдельные заказы с total >= 100.

### WHERE и HAVING вместе

Теперь нужны пользователи, чьи **оплаченные** заказы в сумме дают минимум 150:

```sql
SELECT user_id, COUNT(*) AS paid_orders_count, SUM(total) AS revenue
FROM orders
WHERE status = 'paid'
GROUP BY user_id
HAVING SUM(total) >= 150
ORDER BY user_id;
```

WHERE убирает new и cancelled до группировки. По оставшимся заказам у пользователя 1 сумма 100.00, у пользователя 2 — 250.00. HAVING оставляет только пользователя 2 с двумя paid-заказами и суммой 250.00.

COUNT в этом запросе тоже считается **после WHERE**: это число оплаченных заказов, а не всех заказов пользователя. Если убрать WHERE, изменится смысл показателей и, возможно, состав подходящих групп.

### Почему не WHERE COUNT(*)

**Намеренно ошибочный пример:** этот запрос должен вызвать ошибку PostgreSQL.

```sql
SELECT user_id, COUNT(*) AS orders_count
FROM orders
WHERE COUNT(*) > 1
GROUP BY user_id;
```

Обычный WHERE проверяет исходные строки текущего уровня запроса. На этом логическом этапе агрегат группы ещё не определён, поэтому такое условие недопустимо. Условие на итог группы относится к HAVING.

Не пытайся исправить пример условием по одному известному user_id. Это заменит вопрос о количестве заказов вопросом о конкретном пользователе и не будет работать на других данных.

### Условия и точные границы

«Минимум два» означает `>= 2`:

- одна строка в группе не подходит;
- две подходят;
- три и больше тоже подходят.

`> 2` теряет группы ровно с двумя строками, а `= 2` теряет группы с тремя и больше. Проверяй все три ситуации, а не один публичный пример.

Аналогично для суммы: `SUM(total) >= 100` включает ровно 100. Сравнение `SUM(total) > 100` уже означает другое условие.

### Важный нюанс / ограничение

WHERE total >= 100 и HAVING SUM(total) >= 100 отвечают на разные вопросы. У пользователя могут быть два заказа по 60: каждый не проходит первый фильтр, но их общая сумма проходит второй. Это поясняющая ситуация, не текущий публичный seed.

В GROUP BY по полям нет группы для отсутствующих входных строк. Если orders пустая или ни одна группа не прошла HAVING, результат пустой. Не нужно добавлять выдуманную строку с count = 0. Для отдельного общего COUNT без GROUP BY действовало другое правило из урока 10.7.

### Где используется в backend

HAVING нужен для списка повторных покупателей, категорий с несколькими товарами и отчёта по клиентам, преодолевшим порог выручки. Но «повторный покупатель по всем заказам» и «повторный покупатель по paid-заказам» — разные определения. Фильтры статуса и периода должны быть частью явного контракта API.

## Модель понимания

Назови входные строки, ключ группы, показатель и порог. Построй запрос без HAVING, посмотри все итоги, затем добавь условие и проверь, какие группы исчезли. После этого задай порядок строк результата.

## Что нужно знать на Junior

### Обязательно

- WHERE фильтрует исходные строки, HAVING — группы.
- WHERE меняет вход для всех агрегатов этого уровня.
- HAVING может использовать COUNT, SUM и другие показатели группы.
- Обычный WHERE COUNT(*) недопустим.
- Пороги >=, > и = не взаимозаменяемы.

### Полезно

Проверять запрос по шагам, включая пустой вход и значения ровно на границе. Псевдоним SELECT обычно не заменяет агрегат в HAVING PostgreSQL: повтори выражение, если нужен фильтр на него.

### Можно не учить глубоко

Перенос условий оптимизатором и сложные вложенные запросы пока не нужны. Важно правильно сформулировать строковый и групповой фильтры.

## Примеры кода

Посмотрим, чем различаются фильтры на реальных данных. Сначала отдельные оплаченные заказы не дешевле 100:

```sql
SELECT user_id, COUNT(*) AS orders_count, SUM(total) AS revenue
FROM orders
WHERE status = 'paid' AND total >= 100
GROUP BY user_id
ORDER BY user_id;
```

Получим 1 / 1 / 100.00 и 2 / 1 / 200.00. Заказ пользователя 2 на 50 исчез до подсчёта. В примере с HAVING SUM(total) >= 150 он участвовал в общей сумме 250.00.

## Типичные ошибки

- Поместить агрегат в обычный WHERE текущего уровня.
- Перенести фильтр отдельных заказов в HAVING или наоборот, изменив смысл.
- Использовать > 2 или = 2 вместо «минимум два».
- Вернуть все группы без проверки показателя.
- Посчитать только paid-заказы, хотя условие требует все.
- Вернуть подходящих пользователей с неправильным count или без нужной сортировки.

## Практика

### Основная задача: пользователи с двумя заказами

Найди пользователей, у которых **минимум два заказа любого статуса**. Верни user_id и количество заказов под названием count. Столбцы должны идти в этом порядке, строки — по user_id по возрастанию.

Исследуй orders в Explorer, сначала посчитай группы, затем добавь условие. Выполни Run и Check. Скрытые наборы содержат пользователей без заказов, с одним, двумя и большим количеством заказов. Видимые ID и числа нельзя подставлять вместо расчёта.

<details>
<summary>Показать решение для самопроверки</summary>

```sql
SELECT user_id, COUNT(*) AS count
FROM orders
GROUP BY user_id
HAVING COUNT(*) >= 2
ORDER BY user_id;
```

На публичных данных подходят пользователи 1 и 2, у каждого count равен 2. В других наборах подходящие пользователи могут иметь три или больше заказов. Нужен фактический count, а не постоянное число 2.

</details>

### Дополнительная практика без отдельного Check

1. Найди категории товаров с суммой цен минимум 80. Верни category и price_sum, отсортируй по category.
2. В примере про paid-выручку измени порог с 150 на 100. Кто теперь проходит и почему?

<details>
<summary>Показать ответы к дополнительной практике</summary>

```sql
SELECT category, SUM(price) AS price_sum
FROM products
GROUP BY category
HAVING SUM(price) >= 80
ORDER BY category;
```

Останется hardware / 90.00; сумма цен books равна 70.00. В отчёте по paid-заказам порог 100 включает пользователей 1 и 2: их суммы равны 100.00 и 250.00.

</details>

## Вопросы с собеседований

1. В чём различие WHERE и HAVING?
2. Почему WHERE COUNT(*) > 1 не подходит для обычной группировки?
3. Что проверять у условия «минимум два»?

## Хорошие ответы

<details>
<summary>Показать ответы для собеседования</summary>

### Короткий ответ

WHERE отбирает исходные строки, HAVING отбирает группы по их показателям. Они действуют на разных логических этапах. Обычный WHERE текущего уровня не может проверять COUNT группы.

### Ответ уровня Junior

Я сначала уточняю, какие заказы участвуют в расчёте, затем группирую и проверяю итог. Например, WHERE status = 'paid' меняет и count, и сумму. Для условия «минимум два» тестирую один, два и три заказа, чтобы отличить >= 2 от > 2 и = 2.

### Follow-up

Группировка без строк не создаёт обычных групп. Если ни одна группа не подходит, корректен пустой результат; это не то же, что одна строка общего COUNT со значением 0.

</details>

## Критерии хорошего ответа

- Чётко разделены входные строки и готовые группы.
- Объяснено влияние WHERE на агрегаты.
- Проверена точная граница, пустой вход и порядок ответа.

## Задача

Получи Passed для «Пользователи с двумя заказами». Завершение независимо от предыдущих задач и не стирается неудачным повтором. Reset сохраняет SQL-черновик и прогресс. SQL Check пока не начисляет XP.

## Шпаргалка

- WHERE — строки до группировки.
- HAVING — группы после агрегирования.
- Уточни, какие строки входят в COUNT и SUM.
- «Минимум два» — >= 2.
- Без подходящих групп ответ пустой, а не выдуманная нулевая строка.
