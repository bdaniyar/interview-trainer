# Data modification

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

Изменение данных — операция над состоянием, а не только получение таблицы результата. INSERT создаёт строки, UPDATE меняет подходящие строки, DELETE удаляет их. RETURNING возвращает значения затронутых строк. После UPDATE это новые значения, после DELETE — значения удалённых строк. Для безопасного backend-кода нужно одновременно проверить ответ и то, что осталось в базе.

### Как работает

Явный список столбцов INSERT защищает от ошибочной зависимости от порядка колонок. UPDATE и DELETE без WHERE работают по всей таблице: перед изменением полезно выполнить SELECT с тем же условием и проверить ожидаемую кратность. RETURNING не заменяет фильтр. ON CONFLICT использует уникальный арбитр: DO NOTHING пропускает конфликтующую строку, DO UPDATE выполняет согласованное обновление; excluded обозначает предлагаемую строку. Это не универсальное исправление любых CHECK/FK ошибок.

Уникальность, CHECK и FK проверяет сама база. Нарушения дают соответственно 23505, 23514, 23503. В явной транзакции ошибка оставляет её в aborted-состоянии: нужен ROLLBACK либо возврат к SAVEPOINT. Вне явной транзакции отдельный успешный statement уже зафиксирован; ошибка следующего не откатывает предыдущий. Учебный профиль уничтожается после каждой попытки: здесь нет подключения к SQLite приложения или вашим проектам.

### Важный нюанс / ограничение

DML Check сравнивает состояние всех семи таблиц и возвращённые строки на шести наборах. UPDATE всех заказов и SELECT выдуманного ответа не проходят. BEGIN/ROLLBACK без фиксации изменения тоже не решает задачу на обычном входе.

## Модель понимания

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
INSERT INTO orders(id,user_id,status,total,created_at) VALUES (20,1,'new',25,'2026-01-01') RETURNING id,status;
```

Последний результат: типы `id: int8`, `status: text`.

| `id` | `status` |
| --- | --- |
| 20 | new |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario blocking-update
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

Нет WHERE — меняются все заказы. SELECT выдуманного ответа не меняет состояние. ON CONFLICT не скрывает FK/CHECK ошибки. Незавершённый BEGIN откатывается при cleanup.

## Практика

Откройте синтетический профиль dml: orders содержит id=10,status=new,total=10 и id=11,status=cancelled,total=99. Сохраните запрос в query.sql. Попробуйте INSERT id=20, UPDATE только id=11, DELETE только id=11 и UPSERT id=10 с новым статусом review — каждый Run начинается с новой копии. Проверьте ошибки FK для user_id=999 и UNIQUE для повторного id=10. Затем выполните graded task: переведите только заказ id=10 в paid и верните ровно id,status. Если id=10 отсутствует, ничего менять нельзя.
