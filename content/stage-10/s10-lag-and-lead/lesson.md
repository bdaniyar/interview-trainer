# `LAG` and `LEAD`

## Учебные цели

После урока вы сможете объяснить механизм `LAG` and `LEAD`, предсказать строки на пустых и граничных входах, написать запрос и проверить его контракт.

## Теория

### Что это

LAG и LEAD связывают событие с соседним событием той же последовательности. Они подходят для истории статусов, интервалов между запросами и сравнения показаний. Это соседство по порядку окна, а не арифметика id-1 или id+1.

### Как работает

LAG(value) берёт value предыдущей строки раздела, LEAD(value) — следующей. Offset по умолчанию равен 1; третий аргумент задаёт default при отсутствии соседней строки. Без default граница даёт SQL NULL. Default применяется при отсутствии строки, а не при NULL в существующей соседней строке. PostgreSQL 17 использует RESPECT NULLS; IGNORE NULLS для этих функций не реализован.

PARTITION BY определяет независимую историю пользователя. ORDER BY created_at,id определяет соседей при равных timestamps. Внешний ORDER BY нужен отдельно. Сортировка времени по убыванию меняет направление: «следующая строка» становится более ранним событием. Для первой/последней строки и одноэлементного раздела отсутствие соседа нормально.

### Важный нюанс / ограничение

Разность timestamptz даёт interval и отражает разницу моментов времени. Форматирование для UI — отдельная задача; не превращайте timestamp в текст ради сравнения. Фильтр перед окном может перескочить через удалённые события: последовательность только paid-заказов и последовательность всех заказов имеют разных соседей. Нельзя подменять отсутствующее будущее событие текущим timestamp, если контракт требует NULL.

## Модель понимания

Соседство определяет partition и полный оконный порядок. Граничный NULL нормален. Default не заменяет NULL существующей строки. PostgreSQL 17 не поддерживает IGNORE NULLS.

## Что нужно знать на Junior

### Обязательно

Default LAG/LEAD применяется только при отсутствии строки. Если строка существует и её value NULL, результат остаётся NULL.

Порядок внутри OVER. LAG идёт на указанное число позиций назад, LEAD вперёд относительно этого порядка, а не относительно абсолютного времени или величины id.

## Примеры кода

Все примеры ниже выполняются в PostgreSQL 17 на неизменном shop-v1 либо явно заданных синтетических VALUES. SQL NULL обозначает отсутствие значения; строка `NULL` была бы другим значением.

### Пример 1

Сосед id=10 — строка 30 с NULL. У 30 оба соседа существуют. У 50 предыдущая строка содержит NULL, а следующей строки нет: одинаковые значения NULL имеют разные причины.

```sql
SELECT id,value,LAG(value) OVER(ORDER BY id) AS previous,LEAD(value) OVER(ORDER BY id) AS following FROM (VALUES (10,5),(30,NULL::integer),(50,9)) v(id,value) ORDER BY id;
```

Ожидаемый результат; типы: `id: int4`, `value: int4`, `previous: int4`, `following: int4`.

| `id` | `value` | `previous` | `following` |
| --- | --- | --- | --- |
| 10 | 5 | SQL NULL | SQL NULL |
| 30 | SQL NULL | 5 | 9 |
| 50 | 9 | SQL NULL | SQL NULL |

### Пример 2

Default -1 используется только в последней строке. NULL существующего соседа не заменяется.

```sql
SELECT id,LEAD(value,1,-1) OVER(ORDER BY id) AS following FROM (VALUES (10,5),(30,NULL::integer),(50,9)) v(id,value) ORDER BY id;
```

Ожидаемый результат; типы: `id: int4`, `following: int4`.

| `id` | `following` |
| --- | --- |
| 10 | SQL NULL |
| 30 | 9 |
| 50 | -1 |

### Пример 3

Между заказами пользователя 1 проходит день. Первый интервал отсутствует, потому что нет предыдущего события.

```sql
SELECT id,created_at-LAG(created_at) OVER(ORDER BY created_at,id) AS gap FROM orders WHERE user_id=1 ORDER BY created_at,id;
```

Ожидаемый результат; типы: `id: int8`, `gap: interval`.

| `id` | `gap` |
| --- | --- |
| 10 | SQL NULL |
| 11 | 1 day, 0:00:00 |

## Типичные ошибки

id+1 не означает следующий заказ. Нет partition — чужой пользователь становится соседом. LEAD(total) вместо LEAD(created_at) возвращает неправильный столбец и тип. COALESCE скрывает нормальную границу. Одинаковый timestamp без id делает выбор следующей строки неоднозначным.

## Практика

Данные: `VALUES` первого примера id=10,30,50. Добавьте owner=2 со строками id=20,value=100 и id=40,value=200; старым строкам назначьте owner=1. Добавьте второй owner к синтетической истории и сначала предскажите неправильных соседей без PARTITION BY. Затем исправьте окно. Сравните LAG по возрастанию и LEAD по убыванию с полными противоположными порядками.

Сначала запишите ожидаемые столбцы, типы и строки вручную; затем используйте Run. Сравнивайте также пустой вход и повторные значения. Дополнительная практика не выдаёт статус основной задачи.

## Задача

**sql.window.38 — Следующий order time**

Верните id,user_id,next_created_at — created_at следующего заказа пользователя по created_at,id ASC. У последнего SQL NULL. Итог по user_id,created_at,id.

Исходные таблицы смотрите в Explorer. Run выполняет запрос на публичных данных, Check проверяет отдельные наборы. Нужны все требуемые строки и только указанные столбцы. Принимаются эквивалентные SELECT независимо от выбранного синтаксиса. SQL XP отключён; черновик сохраняется в браузере.

<details>
<summary>Показать решение для самопроверки</summary>

```sql
SELECT id,user_id,LEAD(created_at) OVER(PARTITION BY user_id ORDER BY created_at,id) AS next_created_at FROM orders ORDER BY user_id,created_at,id;
```

Нужна следующая строка своего пользователя с корректным tie-breaker id и SQL NULL на конце.

</details>
