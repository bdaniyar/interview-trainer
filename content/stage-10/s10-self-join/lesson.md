# SELF JOIN: одна таблица, две роли — пользователь и руководитель

## Учебные цели

После урока ты сможешь:

- читать самоссылочный внешний ключ users.manager_id;
- отличать роли сотрудника и руководителя в одном запросе;
- сохранять пользователей без руководителя через LEFT JOIN;
- замечать перевёрнутое условие связи;
- отличать один шаг иерархии от обхода произвольной глубины;
- получить email пользователя и его непосредственного руководителя.

## Теория

### Что это

Сотрудник и его руководитель могут быть пользователями одного приложения. Необязательно создавать две таблицы с одинаковыми полями: строка users хранит свой id и ссылку manager_id на другую строку той же users.

SELF JOIN — обычное соединение таблицы с собой. **Отдельного SQL-ключевого слова SELF JOIN нет.** Используются знакомые JOIN или LEFT JOIN, но источник users участвует в двух разных ролях.

### Исходные данные

Посмотри users.manager_id в Explorer. FK ссылается обратно на users.id. В публичном наборе:

```sql
SELECT id, email, manager_id
FROM users
ORDER BY id;
```

| id | email | manager_id |
| --- | --- | --- |
| 1 | a@example.com | NULL |
| 2 | b@example.com | 1 |
| 3 | c@example.com | 1 |
| 4 | d@example.com | 2 |

Прочитаем связи:

- Пользователь 1 — корень: непосредственный руководитель не указан.
- Пользователи 2 и 3 подчиняются пользователю 1.
- Пользователь 4 подчиняется пользователю 2, который сам подчиняется 1.

Внешний ключ проверяет существование **не-NULL** ссылки. NULL manager_id разрешён схемой и означает отсутствие указанного руководителя. FK сам по себе не запрещает все возможные циклы иерархии и не доказывает, что данные образуют дерево; это отдельное бизнес-ограничение.

### Две роли и два псевдонима

Мысленно положи один и тот же список перед собой дважды. В первом экземпляре выбираем человека, для которого строится строка ответа. Во втором ищем его руководителя.

| Роль | Удобный псевдоним | По какому полю используется |
| --- | --- | --- |
| Исходный пользователь | employee | employee.manager_id указывает на руководителя |
| Найденный руководитель | manager | manager.id должен совпасть с этой ссылкой |

Это не две физические копии таблицы. Псевдонимы различают ссылки на один источник в пределах запроса. Можно использовать другие имена, но читателю должно быть ясно, кто какую роль играет.

Для self join нужны разные имена ссылок: иначе непонятно, к какой роли относится id или email. Явно назвать обе роли — самый понятный вариант. Технически одну ссылку можно оставить под исходным именем users, а второй дать alias; две разные роли всё равно должны быть различимы.

### Как работает связь

Сначала выведем идентификаторы, чтобы было видно направление:

```sql
SELECT employee.id AS employee_id,
       employee.manager_id,
       manager.id AS matched_manager_id
FROM users AS employee
LEFT JOIN users AS manager ON manager.id = employee.manager_id
ORDER BY employee.id;
```

| `employee_id` | `manager_id` | `matched_manager_id` |
| --- | --- | --- |
| 1 | NULL | NULL |
| 2 | 1 | 1 |
| 3 | 1 | 1 |
| 4 | 2 | 2 |

Каждая строка относится к employee, а не к manager. Для employee 2 берётся ссылка 1 и находится строка manager с id 1. Для employee 4 берётся ссылка 2. Пользователь 1 не находит пару по NULL, но остаётся благодаря LEFT JOIN.

У manager.id первичный ключ, поэтому одна не-NULL ссылка может найти не больше одной строки. Именно для этой связи результат содержит каждого пользователя ровно один раз. Это следствие ключа, а не универсальное свойство любого LEFT JOIN.

### Почему INNER JOIN теряет корни

```sql
SELECT employee.id AS employee_id, manager.id AS manager_id
FROM users AS employee
INNER JOIN users AS manager ON manager.id = employee.manager_id
ORDER BY employee.id;
```

Останутся 2/1, 3/1, 4/2. Корень 1 исчез, поскольку у него нет совпавшего manager.id. Если задача требует каждого пользователя, нужна сохраняющая сторона соединения.

При пустой users оба варианта дают пустой результат. При одном пользователе без manager_id LEFT JOIN даст одну строку с NULL руководителем, а INNER JOIN — ни одной. Это удобные граничные случаи для самопроверки.

### Та же связь, но другой вопрос

Поменяем исходную роль: теперь хотим видеть руководителя и его прямых подчинённых:

```sql
SELECT manager.id AS manager_id, worker.id AS worker_id
FROM users AS manager
LEFT JOIN users AS worker ON worker.manager_id = manager.id
ORDER BY manager.id, worker.id;
```

| manager_id | worker_id |
| --- | --- |
| 1 | 2 |
| 1 | 3 |
| 2 | 4 |
| 3 | NULL |
| 4 | NULL |

У manager 1 два подчинённых, поэтому он повторяется. Пользователи 3 и 4 здесь рассматриваются как возможные руководители, но подчинённых у них нет. Название роли в запросе не означает, что в таблице появился новый тип пользователя.

Это правильный запрос для **списка подчинённых**, но не решение задачи «руководитель каждого пользователя». Если перепутать роли, можно получить похожие, но неверные пары и другое число строк.

### Не соединяй строку с ней самой по собственному id

Условие employee.id = manager.id сопоставит пользователя самому себе. Оно не читает manager_id и поэтому не описывает нужное отношение. Человек без руководителя в таком запросе тоже получит собственный email вместо NULL.

Не следует также использовать имя таблицы users после того, как этой ссылке дали псевдоним employee: в этом запросе нужная ссылка называется employee. Псевдоним столбца через AS — другое понятие: он меняет имя результата, а не роль источника.

### Неоднозначное поле

**Намеренно ошибочный пример:** email существует у обеих ролей. PostgreSQL должен вернуть SQLSTATE 42702.

```sql
SELECT email
FROM users AS employee
LEFT JOIN users AS manager ON manager.id = employee.manager_id;
```

Нужно явно выбрать employee.email или manager.email. Дальше уже отдельно решается, каким должно быть имя выбранного столбца ответа.

### Один уровень — не обход иерархии

У пользователя 4 непосредственный руководитель — 2, а руководитель его руководителя — 1. Один self join делает один шаг по manager_id и не должен незаметно заменять 2 на 1.

Для фиксированного следующего уровня можно добавить ещё одну роль. Обход произвольной глубины — отдельная задача, для которой позднее изучаются рекурсивные CTE, остановка обхода и циклы. В Phase 7 такого обхода нет; CHECK проверяет только **непосредственного** руководителя.

### Где это нужно в backend

Одинаковая схема встречается в категориях с parent_id, организационных подразделениях и комментариях с родительским комментарием. Здесь это только аналогии: исполняемые примеры используют реальные поля users, а не вымышленные таблицы shop-v1.

### Важный нюанс / ограничение

Один руководитель может встречаться у многих сотрудников. Нельзя схлопывать строки по manager_email: тогда исчезнут разные исходные пользователи. Сортировка по email руководителя тоже не равна сортировке по id исходного пользователя.

SQL NULL для отсутствующего руководителя отличается от текста 'NULL' и пустой строки. COALESCE может быть решением для отдельного отображения, но нарушает требуемый результат основной задачи.

## Модель понимания

Обозначь, для кого строится строка, затем прочитай его manager_id и найди строку с таким id во второй роли. При отсутствии ссылки сохрани исходного пользователя с NULL справа. Проверь, что итоговый ORDER BY относится к исходной роли.

## Что нужно знать на Junior

### Обязательно

- SELF JOIN — приём, а не отдельный тип SQL-команды.
- Псевдонимы различают роли одной таблицы.
- FK users.manager_id ссылается на users.id; NULL разрешён.
- LEFT JOIN сохраняет корни, INNER JOIN их исключает.

### Полезно

Рассматривать направление связи, кратность подчинённых, несколько корней и пустой набор отдельно.

### Можно не учить глубоко

Рекурсивный обход иерархии, вычисление путей и альтернативные модели хранения деревьев до отдельного урока.

## Примеры кода

Посчитаем прямых подчинённых у каждого пользователя, включая нули:

```sql
SELECT manager.id AS manager_id, COUNT(worker.id) AS direct_reports
FROM users AS manager
LEFT JOIN users AS worker ON worker.manager_id = manager.id
GROUP BY manager.id
ORDER BY manager.id;
```

Ответ: 1/2, 2/1, 3/0, 4/0. COUNT(worker.id) считает найденных подчинённых, а не NULL-расширенные строки. Здесь GROUP BY нужен потому, что строка отчёта должна означать одного возможного руководителя, а не отдельную пару с подчинённым.

## Типичные ошибки

- Соединить employee.id с manager.id и получить самого пользователя.
- Перевернуть ссылку и вывести подчинённых вместо руководителя.
- Применить INNER JOIN и потерять пользователей без manager_id.
- Сортировать по найденному руководителю вместо исходного пользователя.
- Вернуть несколько строк на одного пользователя или схлопнуть разных сотрудников одного руководителя.
- Подставить строку 'NULL' вместо отсутствующего manager_email.
- Принять один шаг связи за полный обход предков.

## Практика

### Основная задача: email непосредственного руководителя

Верни **каждого пользователя**: сначала его email, затем email непосредственного руководителя под названием manager_email. Если руководителя нет, верни SQL NULL. Сортируй по id исходного пользователя по возрастанию.

Назначь две понятные роли users, проверь направление FK в Explorer, выполни Run и Check. В скрытых наборах есть несколько корней, общий руководитель, цепочка из нескольких уровней, один пользователь и пустая таблица. Нельзя подставлять публичные email вручную.

<details>
<summary>Показать решение для самопроверки</summary>

```sql
SELECT u.email, m.email AS manager_email
FROM users AS u
LEFT JOIN users AS m ON m.id = u.manager_id
ORDER BY u.id;
```

| email | manager_email |
| --- | --- |
| a@example.com | NULL |
| b@example.com | a@example.com |
| c@example.com | a@example.com |
| d@example.com | b@example.com |

Пользователь 4 связан с 2, поэтому его manager_email равен b@example.com, а не a@example.com. Два сотрудника одного руководителя остаются двумя строками, потому что их исходные email различны.

</details>

### Дополнительная практика без отдельного Check

1. Найди всех пользователей, у которых manager_id не указан.
2. Выведи id и email непосредственных подчинённых пользователя 1.
3. По таблице direct_reports объясни, почему пользователь 2 может одновременно быть сотрудником и руководителем.

<details>
<summary>Показать ответы к дополнительной практике</summary>

```sql
SELECT id, email
FROM users
WHERE manager_id IS NULL
ORDER BY id;
```

Одна строка: 1/a@example.com. Если корней несколько, запрос должен вернуть все, а не только известный ID 1.

```sql
SELECT employee.id, employee.email
FROM users AS employee
JOIN users AS manager ON manager.id = employee.manager_id
WHERE manager.id = 1
ORDER BY employee.id;
```

Ответ: 2/b@example.com и 3/c@example.com. Пользователь 4 подчиняется 2, поэтому прямым подчинённым 1 не является. При известном ID руководителя здесь также достаточно фильтра по employee.manager_id; JOIN становится полезен, когда нужны поля найденного руководителя.

Пользователь 2 имеет manager_id = 1 и одновременно является руководителем 4. Роль определяется конкретным отношением, а не отдельной копией пользователя в таблице.

</details>

## Вопросы с собеседований

1. Зачем нужны псевдонимы при соединении таблицы с собой?
2. Как сохранить пользователя без руководителя и что будет справа?
3. Чем список прямых руководителей отличается от обхода всей иерархии?

## Хорошие ответы

<details>
<summary>Показать ответы для собеседования</summary>

### Короткий ответ

Таблица используется в двух ролях: исходный человек и его руководитель. Разные псевдонимы показывают происхождение каждого поля; условие связывает manager_id человека с id руководителя.

### Ответ уровня Junior

Для каждого человека я ищу не больше одной строки по первичному ключу руководителя. LEFT JOIN сохраняет строку при NULL manager_id, поэтому корень остаётся с отсутствующим manager_email. Порядок задаю по id исходного человека. Для списка подчинённых роли и кратность будут другими.

### Follow-up

Один self join даёт один уровень. Если руководитель сам кому-то подчиняется, это не повод перескакивать к верхнему корню. Произвольную глубину и циклы разбирают отдельно; FK сам не является полной проверкой дерева.

</details>

## Критерии хорошего ответа

- У каждой роли понятный смысл и правильно выбраны поля связи.
- Сохранены корни с настоящим SQL NULL.
- Различены прямые связи, кратность и обход нескольких уровней.

## Задача

Получи Passed для «Manager self join». Завершение этой задачи независимо от предыдущих одиннадцати SQL-уроков. Run не помечает задачу решённой; SQL XP остаётся отключённым.

## Шпаргалка

- Две роли users: исходный пользователь и найденный руководитель.
- Ищи manager.id по employee.manager_id.
- LEFT JOIN сохраняет корень с NULL справа.
- Общий руководитель не делает сотрудников одинаковыми строками.
- Один JOIN — один шаг, а не рекурсивный обход.
- Сортировка основной задачи относится к исходному пользователю.
