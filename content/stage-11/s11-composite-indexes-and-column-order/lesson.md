# Composite indexes and column order

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

Составной B-tree индекс упорядочивает ключи лексикографически: сначала первый столбец, при равенстве второй, затем третий. Поэтому индекс (user_id,created_at,id) естественно соответствует истории одного пользователя в хронологическом порядке.

### Как работает

Для PostgreSQL 17 равенства по ведущим колонкам и диапазон по первой колонке без равенства ограничивают просматриваемый участок B-tree. Условия правее могут отсеять строки индекса, но не обязательно сокращают этот участок. Индекс по (created_at,user_id) решает другую задачу: сначала задаётся диапазон времени всех пользователей. Утверждение «индекс совсем не может применяться без левого префикса» слишком категорично, но эффективный путь может требовать большого сканирования.

ORDER BY user_id,created_at,id и ORDER BY created_at,user_id,id не равнозначны. При WHERE user_id=константа ведущий столбец фиксирован, а следующие ключи могут помочь обойтись без отдельной сортировки. Каждый дополнительный индекс увеличивает место и работу записи; уникальный индекс также имеет функцию целостности. Выбор проверяют по реальным запросам, статистике и объёму, не по названию таблицы.

### Важный нюанс / ограничение

Профиль не даёт CREATE INDEX студенту. Готовый индекс и plain EXPLAIN позволяют изучить механизм безопасно; урок не обещает ускорение на маленьком fixture и не содержит выдуманных benchmark.

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
SELECT id FROM orders WHERE user_id=1 ORDER BY created_at,id;
```

Последний результат: типы `id: int8`.

| `id` |
| --- |
| 10 |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario indexes
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

Перестановка ключей меняет порядок. Отсутствие левого равенства не означает абсолютный запрет применения индекса. Каждый индекс замедляет запись и занимает место.
