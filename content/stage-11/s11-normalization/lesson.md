# Normalization

## Учебные цели

Найти функциональные зависимости в таблице, показать аномалии и разделить
схему по фактам. Собрать исходное представление через JOIN и объяснить,
какие условия позволяют без потерь восстановить строки.

## Теория

### Что это

Нормализация переносит независимые факты в отдельные отношения с проверяемыми ключами.

### Как работает

### Один факт в одном месте

В выгрузке `sales(order_id, product_id, product_name, customer_id, customer_city, quantity)`
название одного продукта повторяется во многих строках. Если продукт
переименовали только в части строк, таблица хранит два ответа. В этой модели
`product_id → product_name` означает, что одинаковому product_id соответствует
одно название. Зависимость следует из правил предметной области. Три случайно
совпавших строки её не доказывают. Из правила заказа следует
`order_id → customer_id`, а из правила профиля `customer_id → customer_city`.

Если сохранить все факты в sales, невозможно добавить продукт без продажи.
Удаление его последней продажи уберёт название продукта. Переименование
требует изменения множества строк. Это аномалии вставки, удаления и обновления.

### Нормальные формы

В 1NF таблица описывает строки с одним значением из домена в каждой колонке.
Не храните список идентификаторов товаров через запятую, если товары нужны
как самостоятельные элементы с количеством и ссылками. JSON или массив может
представлять осознанно выбранный единый документ. Это отдельное решение о
границах модели и проверках.

Для 2NF неключевой атрибут зависит от полного кандидатного ключа, а не от его
части. Если ключ строки продажи — `(order_id, product_id)`, количество зависит
от пары, тогда как название — только от product_id. В 3NF устраняем транзитивные
зависимости неключевых полей: у заказа город определяется через клиента.
Формально для нетривиального X → A в 3NF X является суперключом либо A входит
в какой-то кандидатный ключ. BCNF требует, чтобы X всегда был суперключом.
Кандидатный ключ минимален, суперключ может содержать лишние поля.

### Что делает backend

Сохраняйте продукты, клиентов, заказы и позиции отдельно. FK соединяют их,
PK защищают уникальность строк. Цена на момент заказа — исторический факт
позиции, даже если тогда совпала с ценой каталога. Копия текущего названия для
поиска — другая задача. Если для производительности создаёте проекцию,
определите источник истины, обновление, допустимое отставание и восстановление.

### Важный нюанс / ограничение

Нормальная форма сама по себе не измеряет стоимость JOIN. Если чтение требует проекции, задайте допустимое отставание и способ её восстановления.

## Модель понимания

Представьте товар как карточку, которую открывают несколько позиций заказа. Изменение карточки читается всеми позициями через связь. Цена покупки остаётся отдельной заметкой на позиции.

## Что нужно знать на Junior

### Обязательно

Функциональные зависимости выводятся из предметной области. Проверьте кандидатные ключи до разделения и сохранность данных после JOIN.

## Примеры кода

Практика проверяется командой `scripts/test_stage11_examples.sh` на синтетической PostgreSQL 17.11. Запускайте изменения в отдельной учебной базе.

```sql
CREATE TABLE products (id integer PRIMARY KEY, name text NOT NULL);
CREATE TABLE customers (id integer PRIMARY KEY, city text NOT NULL);
CREATE TABLE orders (
    id integer PRIMARY KEY,
    customer_id integer NOT NULL REFERENCES customers
);
CREATE TABLE items (
    order_id integer REFERENCES orders,
    product_id integer REFERENCES products,
    quantity integer NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, product_id)
);
INSERT INTO products VALUES (7, 'Чай');
INSERT INTO customers VALUES (1, 'Алматы'), (2, 'Астана');
INSERT INTO orders VALUES (40, 1), (41, 2);
INSERT INTO items VALUES (40, 7, 2), (41, 7, 1);
UPDATE products SET name = 'Чёрный чай' WHERE id = 7;
SELECT o.id, p.name, c.city, i.quantity
FROM items i
JOIN orders o ON o.id = i.order_id
JOIN products p ON p.id = i.product_id
JOIN customers c ON c.id = o.customer_id
ORDER BY o.id;
```

Две строки: `(40, 'Чёрный чай', 'Алматы', 2)` и
`(41, 'Чёрный чай', 'Астана', 1)`. Типы integer, text, text, integer.
Три ссылки существуют для каждой позиции и ведут к уникальным ключам, поэтому
JOIN восстанавливает ровно одну строку на позицию.

## Типичные ошибки

Новый суррогатный id не устраняет зависимость product_id → name.
Разделение таблицы без FK и уникальности может терять или умножать строки
при JOIN. Изменение города в профиле клиента не должно менять адрес доставки
уже оплаченного заказа, если это исторический снимок.

## Практика

Нарисуйте исходную таблицу до разделения. Сымитируйте удаление последней
продажи продукта. В нормализованной версии удалите позицию и проверьте,
что запись каталога остаётся. Добавьте столбец `unit_price_at_purchase` в
items и объясните, почему его следует читать оттуда, даже если каталог хранит
`current_price`.
