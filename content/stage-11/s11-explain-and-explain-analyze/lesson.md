# EXPLAIN and EXPLAIN ANALYZE

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

EXPLAIN показывает выбранный план выполнения. Он отвечает, как PostgreSQL собирается получить строки: сканирование, фильтрация, соединение, сортировка. План полезен для проверки гипотезы об индексе, но не является универсальным отчётом о скорости сервиса.

### Как работает

Узел плана описывает оценку стоимости, числа строк и ширины строки. Cost — условные единицы модели, не миллисекунды. Верхний узел потребляет результаты дочерних. Filter и Index Cond имеют разную роль: первое может проверяться после чтения, второе помогает найти записи по индексу.

EXPLAIN ANALYZE действительно выполняет запрос и добавляет фактические наблюдения. Для UPDATE/DELETE это означает настоящие изменения; ROLLBACK не отменяет абсолютно все внешние эффекты или выделенные sequence values. BUFFERS помогает исследовать работу буферов, loops меняет интерпретацию количества строк. Разница estimate/actual может указывать на статистику или корреляцию, но требует контекста. В нашем минимальном профиле разрешён только plain EXPLAIN над SELECT; ANALYZE, произвольные настройки планировщика и DDL не открыты.

### Важный нюанс / ограничение

Тест проверяет реальный текстовый результат plain EXPLAIN и ожидаемые свойства запроса, а не закрепляет нестабильные cost или обязательный конкретный scan node. План может измениться от статистики и размера данных.

## Модель понимания

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
SELECT id,total FROM orders WHERE user_id=1 ORDER BY created_at,id;
```

Последний результат: типы `id: int8`, `total: numeric`.

| `id` | `total` |
| --- | --- |
| 10 | 10.00 |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario indexes
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

Cost не равен времени. Маленький fixture не является benchmark. ANALYZE реально исполняет запрос; не запускайте изменение данных как безвредную диагностику.

## Практика

Данные dml Run: `orders` содержит id=10 у user_id=1 и id=11 у user_id=2. Запустите scenario indexes. Найдите orders, фильтр user_id и порядок created_at,id. Не сравнивайте cost с миллисекундами. Предскажите, какой индекс подходит истории одного пользователя, и объясните, почему маленький fixture не доказывает performance improvement. Для отдельного production исследования нужны репрезентативные объёмы, статистика и безопасная среда.
