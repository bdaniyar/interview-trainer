# Locks

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

Блокировка согласует действия, которые нельзя безопасно выполнять одновременно. SELECT FOR UPDATE удерживает строковые блокировки до завершения транзакции; обычный UPDATE тоже блокирует изменяемые строки. Важно знать, какую строку и на какое время вы удерживаете.

### Как работает

Когда A удерживает строку, конфликтующая операция B обычно ждёт. NOWAIT вместо ожидания возвращает 55P03. SKIP LOCKED пропускает занятые строки и подходит для конкурентного разбора очереди: разные workers могут выбрать разную доступную работу. Полученный набор намеренно неполон, поэтому такой режим не является универсальным способом читать согласованный отчёт.

COMMIT/ROLLBACK освобождают блокировки. Корректность должна опираться на защищённый инвариант и транзакционную границу, а не на задержку между запросами. FOR UPDATE с LIMIT в очереди нужно сочетать с записью ownership в той же транзакции; выбрать строку, закрыть транзакцию и только потом пометить running — значит снова открыть гонку. В lab момент ожидания подтверждается pg_blocking_pids доверенным scheduler; студентам эта административная функция не разрешена.

### Важный нюанс / ограничение

blocking-update фиксирует зависимость B→A по реальному состоянию PostgreSQL перед освобождением A. Фиксированные sleeps не определяют порядок событий. Все соединения закрываются, а sandbox удаляется после сценария.

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
BEGIN; SELECT id FROM inventory ORDER BY id FOR UPDATE SKIP LOCKED; ROLLBACK;
```

Последний результат: типы `id: int8`.

| `id` |
| --- |
| 1 |
| 2 |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario skip-locked
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

SKIP LOCKED даёт неполный набор и не подходит произвольному отчёту. Выбор и пометка running разными транзакциями снова открывают гонку. Случайная пауза не доказывает блокировку.
