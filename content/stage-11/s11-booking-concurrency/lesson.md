# Booking concurrency

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

Проверка «свободно ли место» и создание бронирования должны образовывать одну корректную операцию. Два запроса могут прочитать одинаковый последний остаток. HTTP-процессы, разные workers и несколько экземпляров API не разделяют один Python Lock.

### Как работает

В учебной базе inventory хранит остаток, reservations — результат бронирования. CHECK запрещает отрицательный available. Уникальный partial index допускает не больше одного active бронирования комнаты, что соответствует этой модели одной единицы, а FK связывает запись с существующей комнатой. Для интервальных бронирований одного UNIQUE(room_id) недостаточно: обычно обсуждают exclusion constraint по пересекающимся диапазонам и состоянию. Отдельный controlled scenario exclusion показывает перекрытие целочисленных диапазонов [1,3) и [2,4): вторая транзакция ждёт первую, затем получает 23P01. Это синтетические интервалы одной ресурсной линии, а не готовая модель календарных дат; расширения студенту недоступны.

Согласованная стратегия может использовать условный атомарный UPDATE с RETURNING, блокировку строки с повторной проверкой или SERIALIZABLE с обработкой конфликтов. Изменение остатка и вставка бронирования должны фиксироваться вместе. Отсутствие строки из UPDATE RETURNING является нормальным бизнес-конфликтом доступности, а не поводом всё равно вставлять бронь. Ошибка 23505 от ограничения может служить ещё одной защитой, если вся транзакция откатывается.

### Важный нюанс / ограничение

Check требует максимум одну новую бронь при одной единице и ровно одну, когда она доступна; остаток должен уменьшиться ровно на число созданных броней. Проверяются ответы обоих запросов, все таблицы и освобождение транзакций. Хардкод ответа и UPDATE всех комнат не проходят.

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
UPDATE inventory SET available=available-1 WHERE id=2 AND available>0 RETURNING id,available;
```

Последний результат: типы `id: int8`, `available: int4`.

| `id` | `available` |
| --- | --- |
| 2 | 0 |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario blocking-update
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

Python Lock не защищает разные процессы. UPDATE всех комнат меняет чужой остаток. Возврат fake reservation не доказывает вставку. SQL-транзакция не включает внешнюю оплату.

## Задача

В booking Run два независимых запроса одновременно выполняют ваш SQL. В файле используйте точный текстовый маркер `REQUEST_KEY` в одинарных кавычках: runner подставит разные synthetic request keys. Задача: бронировать только room id=1 при наличии единицы, вернуть request_key,room_id либо пустой результат при конфликте; не менять другие комнаты и shop-таблицы. Запустите Check на шести изолированных состояниях, включая sold-out, отсутствие комнаты и существующую бронь.

Run и Check выполняются локальным transaction CLI, а не кнопками Python Workspace:

```sh
python3 -m transaction_lab.cli run --exercise booking --file query.sql
python3 -m transaction_lab.cli check --exercise booking --file query.sql
```

У Check шесть отдельных синтетических баз. Он не начисляет XP и не записывает результат в SQLite; JSON-отчёт можно сохранить локально. Основной read-only SQL Lab остаётся неизменным. SQL не отправляется в Python Runner.

```sql
BEGIN;
WITH claimed AS (
 UPDATE inventory SET available=available-1 WHERE id=1 AND available>0 RETURNING id
)
INSERT INTO reservations(request_key,room_id)
SELECT 'REQUEST_KEY',id FROM claimed RETURNING request_key,room_id;
COMMIT;
```
