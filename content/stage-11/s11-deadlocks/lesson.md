# Deadlocks

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

Deadlock — цикл ожидания: A держит то, что нужно B, а B держит то, что нужно A. Простое увеличение таймаута не разрушает цикл. PostgreSQL обнаруживает его и отменяет одну транзакцию с SQLSTATE 40P01.

### Как работает

В воспроизводимом сценарии A обновляет inventory id=1, B обновляет id=2. Затем A пытается обновить 2; scheduler проверяет фактическое ожидание A от B. Только после этого B пытается обновить 1. Цикл уже построен независимо от скорости потоков. Жертва не обязана быть конкретной сессией, поэтому тест требует ровно один 40P01 и успешное освобождение остальных блокировок.

Профилактика — единый порядок получения нескольких блокировок, короткие транзакции и корректные индексы/условия. Даже с профилактикой обработчик 40P01 обычно должен откатить и повторить всю бизнес-транзакцию с ограничением числа попыток. Повтор не должен дублировать внешний платёж или отправку email: для внешних эффектов требуется отдельная стратегия идемпотентности.

### Важный нюанс / ограничение

Одиночный пример ниже показывает согласованный порядок, он не демонстрирует deadlock. Реальный сценарий использует две независимые транзакции и проверку lock dependency. После жертвы делается rollback; финальное закрытие соединений не оставляет блокировок.

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
BEGIN; SELECT id FROM inventory WHERE id IN (1,2) ORDER BY id FOR UPDATE; ROLLBACK;
```

Последний результат: типы `id: int8`.

| `id` |
| --- |
| 1 |
| 2 |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario deadlock
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

Увеличение lock_timeout не устраняет цикл. Нельзя ожидать, что жертвой всегда будет B. Retry без границы всей транзакции и идемпотентности может дублировать эффекты.

## Практика

Откройте Transaction Lab справа. Выберите «Deadlock». Найдите жертву с SQLSTATE 40P01 и проверьте, какую транзакцию нужно повторить.

Нарисуйте цикл A→B→A для двух строк 1,2. Запустите deadlock, найдите 40P01 в timeline, затем убедитесь, что следующий отдельный Run может обновлять обе строки. Перепишите две операции так, чтобы обе сессии брали блокировки сначала 1, затем 2.
