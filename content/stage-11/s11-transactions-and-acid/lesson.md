# Transactions and ACID

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

Транзакция объединяет несколько изменений в один результат: все они фиксируются либо все откатываются. Представьте перевод денег: списание без зачисления недопустимо. BEGIN открывает границу, COMMIT подтверждает её, ROLLBACK отбрасывает незавершённую работу.

### Как работает

ACID означает atomicity, consistency, isolation и durability. Atomicity относится к общей фиксации изменений; consistency — к сохранению заданных инвариантов, а не к способности базы угадать бизнес-правила. Isolation задаёт допустимые взаимодействия конкурентных транзакций. Durability означает сохранность подтверждённого результата при оговорённых настройках и отказах. Наш tmpfs-профиль намеренно одноразовый и не является тестом долговечности при потере диска.

SAVEPOINT отмечает промежуточную точку. ROLLBACK TO отменяет работу после неё и позволяет продолжить транзакцию. RELEASE убирает savepoint, но не заменяет внешний COMMIT. Ошибка SQL без восстановления делает дальнейшие команды транзакции недопустимыми (25P02). Удерживать транзакцию во время долгого HTTP-вызова плохо: блокировки и старый snapshot живут дольше, а внешняя операция не становится частью PostgreSQL atomic commit.

### Важный нюанс / ограничение

В сценарии rollback-savepoint A внутри видит (1,0),(2,1), B до фиксации — (1,1),(2,1); после полного ROLLBACK обе строки снова равны 1. Это наблюдается через разные соединения.

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
BEGIN; UPDATE inventory SET available=0 WHERE id=1; ROLLBACK; SELECT id,available FROM inventory ORDER BY id;
```

Последний результат: типы `id: int8`, `available: int4`.

| `id` | `available` |
| --- | --- |
| 1 | 1 |
| 2 | 1 |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario rollback-savepoint
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

RELEASE SAVEPOINT не фиксирует внешнюю транзакцию. После ошибки нельзя просто продолжить UPDATE. Открытая транзакция вокруг HTTP-вызова удерживает ресурсы и не обеспечивает атомарность HTTP.

## Практика

Откройте Transaction Lab справа. Выберите «SAVEPOINT и ROLLBACK». Сравните промежуточное изменение и итог после полного отката.

На inventory=(1,1),(2,1) откройте BEGIN, измените первую строку, поставьте SAVEPOINT, измените вторую, откатитесь к точке и выполните COMMIT. Ожидаются (1,0),(2,1). Затем после savepoint попытайтесь записать available=-1, получите 23514, выполните ROLLBACK TO и продолжите допустимым UPDATE. Сравните видимость для сессии B до и после COMMIT.

## Хорошие ответы

<details>
<summary>Раскрыть ответы</summary>

SAVEPOINT отмечает точку частичного отката внутри незавершённой транзакции. COMMIT фиксирует транзакцию; RELEASE SAVEPOINT его не заменяет.

Транзакция остаётся aborted. Нужен полный ROLLBACK или ROLLBACK TO заранее созданной точке; иначе следующие команды получают 25P02.
