# Index mental model

## Учебные цели

Связать индекс с конкретным запросом backend. Сравнить чтение без индекса
и с индексом на типичных данных, а затем найти операции записи, которые
платят за его обслуживание.

## Теория

### Что это

Индекс хранит поисковые ключи и ссылки на строки, позволяя перейти к части таблицы.

### Как работает

Представьте таблицу с тысячами заказов. Чтобы найти заказы клиента, PostgreSQL
может прочитать таблицу последовательно и проверить условие на каждой строке.
Если есть индекс на customer_id, PostgreSQL может сначала найти указатели на
нужные строки в индексе и затем прочитать соответствующие страницы таблицы.
Этот путь особенно полезен, когда совпадений мало. При большом числе
совпадений стоимость обращений в разные страницы может превысить
стоимость одного последовательного прохода.

Индекс — отдельная структура данных. Запись в таблицу обслуживает и
подходящие индексы. Добавляются дисковое место, WAL, работа по очистке
старых версий и иногда page split. Обновление индексируемого поля меняет
его ключ. PostgreSQL может оптимизировать некоторые обновления без изменения
индекса при выполнении условий HOT. Даже если индекс редко нужен API, сам
факт его существования влияет на запись.

Не выбирайте индекс из списка полей модели. Выпишите запрос, его WHERE,
ORDER BY и LIMIT, частоту и объём результата. Проверьте EXPLAIN с данными,
похожими на реальные по размеру и распределению. Уникальный индекс может
быть нужен для бизнес-правила независимо от частоты чтения.

### Важный нюанс / ограничение

Планировщик оценивает стоимость, поэтому индекс на customer_id не обещает Index Scan для всех наборов или списков клиентов.

## Модель понимания

Сравните поиск по оглавлению с чтением всех страниц. Если нужны почти все страницы, сначала читать оглавление и затем открывать страницы вразнобой может быть дороже.

## Что нужно знать на Junior

### Обязательно

Сопоставляйте индекс с предикатом, сортировкой и нагрузкой записи. Читайте EXPLAIN до утверждений о производительности.

## Примеры кода

Практика проверяется командой `scripts/test_stage11_examples.sh` на синтетической PostgreSQL 17.11. Запускайте изменения в отдельной учебной базе.

У списка заказов клиента запрос возвращает последние три записи. Данные
синтетические. Выполните блок в одноразовой PostgreSQL-базе.

```sql
CREATE TABLE orders (id integer PRIMARY KEY, customer_id integer NOT NULL);
INSERT INTO orders SELECT i, i % 100 FROM generate_series(1, 20000) AS g(i);
ANALYZE orders;
EXPLAIN SELECT id FROM orders WHERE customer_id = 7 ORDER BY id DESC LIMIT 3;
CREATE INDEX orders_customer_feed ON orders (customer_id, id);
ANALYZE orders;
EXPLAIN SELECT id FROM orders WHERE customer_id = 7 ORDER BY id DESC LIMIT 3;
SELECT id FROM orders WHERE customer_id = 7 ORDER BY id DESC LIMIT 3;
```

Итоговые integer id: 19907, 19807, 19707. Сравните в двух планах условия
индекса, фильтр и сортировку. Наличие PK на id уже даёт возможный обратный
проход с фильтрацией. Составной индекс даёт другой путь: перейти к ключу
клиента и прочитать только несколько упорядоченных записей. Не делайте вывод
об ускорении из числа строк плана.

## Типичные ошибки

Индекс на каждое поле увеличивает работу записи и число вариантов планирования.
Измерение один раз после прогрева смешивает эффект индекса и кэша.
Фильтр, который проверяется после чтения, не всегда ограничивает индексный
поиск. Удаляя «неиспользуемый» индекс, сначала проверьте уникальность и
период наблюдения.

## Практика

Откройте индексную лабораторию. Сравните план поиска пользователя по `lower(email)` после обычного индекса и после индекса на выражении. Учтите, что два сохранённых адреса могут совпасть после приведения регистра. Check сверяет конструкцию индекса и фактическую выборку.

Сравните план поиска одного клиента с запросом всех строк. Подсчитайте долю
совпадений для customer_id=7. Затем предложите один индекс для чтения ленты
и объясните, что добавляется к каждой вставке. В отдельной копии сравните
повторные EXPLAIN (ANALYZE, BUFFERS) и выпишите узлы и буферы, а не обещание
фиксированного ускорения.

## Вопросы с собеседований

1. Почему последовательное чтение иногда выгоднее индекса?
2. Что стоит поддержка индекса таблице с частыми INSERT и UPDATE?

## Хорошие ответы

<details>
<summary>Раскрыть ответы</summary>

Если нужно много строк, индекс добавляет переходы по таблице и работу чтения
своих страниц. Планировщик сравнивает ожидаемые стоимости доступных путей.

Индекс занимает место и поддерживается при записи. Операции меняют страницы
индекса и WAL, повышая write amplification. Некоторые UPDATE могут
использовать HOT при выполнении условий.

</details>

## Задача

Для запроса по 100 клиентам одновременно сравните оба плана. Проверьте число строк независимо. Объясните, почему вывод по запросу с LIMIT 3 не переносится на выгрузку.

## Шпаргалка

Выводите индекс из запроса. Индекс и heap читаются и обслуживаются отдельно.
Прежде чем заключать, сравните форму плана, результат, объём чтения и нагрузку записи.
