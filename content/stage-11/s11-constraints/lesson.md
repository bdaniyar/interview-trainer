# Constraints

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

Ограничение — исполняемое правило целостности базы. Проверка только в Python оставляет окно между чтением и записью: два процесса могут одновременно решить, что уникальное значение свободно. UNIQUE, FK и CHECK работают и при конкуренции.

### Как работает

PRIMARY KEY объединяет уникальность и запрет NULL. UNIQUE задаёт уникальность значения/набора; стандартное поведение PostgreSQL допускает несколько NULL, если явно не выбран NULLS NOT DISTINCT. FK требует существующую связанную строку и не заменяет проверку бизнес-состояния. CHECK проверяет условие строки, причём UNKNOWN сам по себе не нарушает CHECK: для обязательного значения нужен также NOT NULL.

В учебной inventory available имеет NOT NULL и CHECK(available>=0). В reservations room_id ссылается на inventory, а partial unique index запрещает две active записи одной комнаты. Это одна дискретная единица, не модель временных интервалов. Exclusion constraint может запретить пересекающиеся интервалы: нужно правильно выбрать операторы, тип диапазона и состояние, иногда требуется расширение btree_gist. Не подменяйте интервальную задачу одним UNIQUE(room_id).

### Важный нюанс / ограничение

Сценарий `exclusion` отдельно исполняет EXCLUDE по перекрывающимся int4range в двух соединениях: после COMMIT A вставка B завершается 23P01. Ошибка ограничения не означает, что приложение нужно автоматически повторить: 23505 может быть ожидаемым бизнес-конфликтом или признаком неверного ключа. Выбирайте обработку по контракту операции.

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

Намеренно ошибочный пример: ожидается SQLSTATE 23514, состояние не меняется.

```sql
UPDATE inventory SET available=-1 WHERE id=1;
```

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario exclusion
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

CHECK без NOT NULL допускает UNKNOWN. FK не доказывает отсутствие циклов. UNIQUE одной комнаты не моделирует интервальную занятость.
