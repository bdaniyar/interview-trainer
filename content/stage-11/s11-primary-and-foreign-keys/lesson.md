# Primary and foreign keys

## Учебные цели

Спроектировать идентификатор строки и связать дочернюю таблицу с родительской.
Проверить, как составной ключ защищает связь в пределах арендатора и когда
удаление родителя останавливается ограничением.

## Теория

### Что это

Ключ — выбранное значение или набор значений, по которым схема однозначно адресует строку.

### Как работает

### От идентичности к ссылке

Если два человека имеют одинаковое имя, имя не поможет однозначно найти их
учётные записи. Первичный ключ задаёт такую идентичность. В PostgreSQL
`PRIMARY KEY` требует уникальность и `NOT NULL` у всех входящих столбцов.
Таблица имеет один первичный ключ, а альтернативных `UNIQUE` может быть несколько.
При обычном `UNIQUE` PostgreSQL допускает несколько NULL, если отдельно не
указано `NULLS NOT DISTINCT` или `NOT NULL`.

Внешний ключ проверяет, что значение у ребёнка соответствует существующему
уникальному ключу родителя. Обычный FK допускает несколько детей одного
родителя. Чтобы получить связь «не более одного», добавьте `UNIQUE` у ребёнка.
Чтобы ссылка была обязательной, добавьте `NOT NULL`. У составного FK по умолчанию
`MATCH SIMPLE`: если хотя бы один компонент NULL, проверка пары пропускается.
У `MATCH FULL` допустимы либо все NULL, либо полностью заполненная пара.

### Удаление и индексы

`ON DELETE NO ACTION` по умолчанию требует сохранения целостности к моменту
проверки. Для отложенного ограничения проверку можно перенести до конца
транзакции. `RESTRICT` нельзя отложить. `CASCADE` удаляет детей вместе с родителем.
`SET NULL` подходит для необязательной ссылки и конфликтует с NOT NULL, если
обнуляемые столбцы обязательны. Выбирайте по смыслу данных. Например, корзина
может исчезнуть вместе с сессией, а оплаченный заказ нужен для истории.

PostgreSQL создаёт индекс для PK и UNIQUE у родителя. На ссылающихся столбцах
индекс автоматически не создаётся. Он может ускорить поиск детей при проверке
удаления родителя и запросы backend. Его цена — место и работа на каждой записи.

### Важный нюанс / ограничение

NOT NULL на каждом компоненте делает составную ссылку обязательной. Для отложенного FK проверка может произойти только при COMMIT.

## Модель понимания

Нарисуйте таблицу заказов как множество пар (shop_id, order_no). Каждая доставка должна указывать на одну имеющуюся пару, даже если номера повторяются между магазинами.

## Что нужно знать на Junior

### Обязательно

Составной FK ссылается на совместимый уникальный ключ. Каскад и запрет удаления выбираются по жизненному циклу ребенка.

## Примеры кода

Практика проверяется командой `scripts/test_stage11_examples.sh` на синтетической PostgreSQL 17.11. Запускайте изменения в отдельной учебной базе.

В одноразовой базе создайте одинаковый номер заказа для двух магазинов.
Таблица доставки ссылается на пару `(shop_id, order_no)`.

```sql
CREATE TABLE orders (
    shop_id integer NOT NULL,
    order_no integer NOT NULL,
    PRIMARY KEY (shop_id, order_no)
);
CREATE TABLE shipments (
    id integer PRIMARY KEY,
    shop_id integer NOT NULL,
    order_no integer NOT NULL,
    FOREIGN KEY (shop_id, order_no)
      REFERENCES orders (shop_id, order_no) ON DELETE CASCADE
);
CREATE INDEX shipments_order ON shipments (shop_id, order_no);
INSERT INTO orders VALUES (1, 42), (2, 42);
INSERT INTO shipments VALUES (10, 1, 42), (20, 2, 42);
DELETE FROM orders WHERE shop_id = 1 AND order_no = 42;
SELECT id, shop_id, order_no FROM shipments ORDER BY id;
```

Одна строка `(20, 2, 42)`, все три поля integer. Удаление затронуло только
магазин 1. Попытка вставить `(30, 1, 42)` после удаления получит `23503`.
Уникальность одного `order_no` здесь нарушила бы контракт нумерации.

## Типичные ошибки

Ссылка только на номер при многопользовательской нумерации соединяет разные
магазины. Каскад без проверки модели может удалить историю. Проверка
`SELECT` перед вставкой без FK оставляет гонку с удалением родителя.
В API переводите нарушение известного FK в понятную ошибку, а транзакцию
после ошибки откатывайте.

## Практика

В своей базе замените CASCADE на RESTRICT. Повторите DELETE и проверьте
`23503` и обе дочерние строки после отката. Затем добавьте второй shipment
для магазина 2. Зафиксируйте, какое ограничение нужно, если бизнес разрешает
ровно один shipment на заказ. Сверьте DDL и фактическое число строк.

## Вопросы с собеседований

1. Чем отличаются PK, UNIQUE и обязательный FK?
2. Почему индекс внешнего ключа на дочерней стороне нужно обдумывать отдельно?

## Хорошие ответы

<details>
<summary>Раскрыть ответы</summary>

PK идентифицирует строку уникальным непустым ключом. UNIQUE задаёт
альтернативную уникальность и может допускать NULL. FK связывает значения с
родительским ключом, а обязательность задаёт NOT NULL.

Родительский уникальный индекс проверяет существование и уникальность
родителя. Дочерний индекс нужен для отдельных запросов и поиска детей
при изменении родителя. PostgreSQL не выбирает его автоматически за автора схемы.

</details>

## Задача

Добавьте к orders поле invoice_no и сделайте его альтернативным обязательным уникальным ключом в пределах магазина. Проверьте отдельно, что две одинаковые пары отклоняются и что один номер счёта у двух магазинов допустим.

## Шпаргалка

PK определяет идентичность. FK защищает ссылку. UNIQUE ограничивает
повторяемость. NOT NULL задаёт обязательность. Каскад — бизнес-решение
об удалении. Проверьте индекс на столбцах ссылки по реальным запросам.
