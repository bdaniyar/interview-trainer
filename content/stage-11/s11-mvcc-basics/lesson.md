# MVCC basics

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

MVCC позволяет читателю видеть подходящую версию строки, пока другой запрос создаёт новую версию. Чтение обычного SELECT и UPDATE поэтому часто могут идти одновременно. Это основа snapshot semantics, а не обещание отсутствия любых блокировок.

### Как работает

Каждый statement проверяет видимость версий относительно своего snapshot и транзакций, которые эти версии создали или завершили. READ COMMITTED может получить другой snapshot при следующем чтении; REPEATABLE READ сохраняет транзакционный snapshot. Старый читатель может продолжать видеть прежнее значение после COMMIT писателя. Удалённые/заменённые версии не исчезают немедленно: vacuum должен учитывать ещё нужные snapshots.

Длинная транзакция может удерживать старые версии и мешать очистке. Обычный SELECT не блокируется строковым UPDATE как SELECT FOR UPDATE, но DDL и другие table locks всё равно могут конфликтовать. MVCC также не разрешает двум UPDATE бесконтрольно переписать одну версию: запись требует согласования и может ждать или завершиться конфликтом.

### Важный нюанс / ограничение

Ожидается first=1, second=1, current=0. В сценарии lost-update два чтения 1 выполняются до двух записей значения 2: финал 2, хотя два последовательных инкремента дали бы 3. MVCC не исправляет read/compute/write бизнес-алгоритм автоматически.

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT id,available FROM inventory ORDER BY id; ROLLBACK;
```

Последний результат: типы `id: int8`, `available: int4`.

| `id` | `available` |
| --- | --- |
| 1 | 1 |
| 2 | 1 |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario mvcc
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

Старый snapshot — не потеря COMMIT. MVCC не означает отсутствие locks и не исправляет read/compute/write. Старые версии не очищаются мгновенно при наличии долгого reader.

## Практика

Откройте Transaction Lab справа. Выберите «MVCC». Сравните версию строки в старом снимке и в новой транзакции.

В сценарии mvcc A читает 1 и удерживает snapshot. B фиксирует 0. Предскажите второе чтение A и текущее чтение observer. После ROLLBACK A создайте новую транзакцию: теперь она должна увидеть 0. Объясните, почему это не dirty read и не потеря зафиксированной записи.
