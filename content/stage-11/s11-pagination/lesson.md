# Pagination

## Учебные цели

Реализовать стабильную сортировку, сформировать курсор из всех ключей порядка
и проверить границу страницы при одинаковых датах. Сравнить поведение OFFSET
и keyset при вставках.

## Теория

### Что это

Страница — часть заданного порядка выборки. Номер страницы и курсор задают разные способы найти её начало.

### Как работает

LIMIT ограничивает число возвращаемых строк. Без ORDER BY порядок не входит
в контракт запроса. Даже ORDER BY created_at не задаёт порядок между строками
с одной датой. Добавьте уникальный tie breaker, например id.

OFFSET пропускает первые N строк в порядке выборки. На глубокой странице
серверу может потребоваться пройти много записей, хотя клиент увидит десять.
При независимых запросах на страницы новый заказ перед смещением может
сдвинуть уже показанный заказ на следующую страницу. При удалении перед
смещением может пропасть ещё не показанный заказ.

Курсор keyset хранит ключ последней показанной строки. Для DESC по обоим полям
следующая страница ищет пары меньше прежней пары. PostgreSQL сравнивает
кортежи слева направо. Столбцы в примере NOT NULL. Для NULL и смешанного
направления нужен согласованный предикат, включая правила NULLS FIRST/LAST.
Индекс с таким же порядком и совместимыми фильтрами даёт серверу возможность
начать с границы, а не считать смещение.

### Важный нюанс / ограничение

Keyset не сохраняет единый snapshot. Изменение ключа сортировки или фильтра между запросами влияет на видимые строки.

## Модель понимания

Курсор играет роль сохранённой пары сравнения. Запись, на которую он указывает, может исчезнуть. Пара всё ещё остаётся границей порядка.

## Что нужно знать на Junior

### Обязательно

Уникальный tie breaker входит в ORDER BY, индекс и курсор. Проверьте строгий знак сравнения и соответствие направлениям.

## Примеры кода

Практика проверяется командой `scripts/test_stage11_examples.sh` на синтетической PostgreSQL 17.11. Запускайте изменения в отдельной учебной базе.

```sql
CREATE TABLE feed (
    id bigint PRIMARY KEY,
    created_at timestamptz NOT NULL
);
CREATE INDEX feed_cursor ON feed (created_at DESC, id DESC);
INSERT INTO feed VALUES
    (11, '2026-11-04 10:00:00+00'),
    (12, '2026-11-04 10:00:00+00'),
    (13, '2026-11-04 11:00:00+00'),
    (10, '2026-11-03 12:00:00+00');
SELECT id FROM feed ORDER BY created_at DESC, id DESC LIMIT 2;
INSERT INTO feed VALUES (14, '2026-11-04 12:00:00+00');
SELECT id FROM feed ORDER BY created_at DESC, id DESC LIMIT 2 OFFSET 2;
SELECT id FROM feed
WHERE (created_at, id) < (TIMESTAMPTZ '2026-11-04 10:00:00+00', 12)
ORDER BY created_at DESC, id DESC LIMIT 2;
```

Первая страница: 13, 12. OFFSET после вставки: 12, 11, так что 12 повторился.
Страница после курсора: 11, 10. Все значения bigint. Новая строка 14 выше
границы выдачи в смысле позиции: она окажется перед курсором. Обновите
первую страницу, чтобы увидеть её. Удаление самой курсорной строки не
ломает сравнение с её сохранённой парой.

### Контракт API

Верните значение следующего курсора только когда есть следующая страница.
Один вариант — запросить limit+1, показать limit строк и строить курсор
по последней показанной, а не по лишней. Кодируйте оба значения, UTC и
точность времени, версию порядка и область фильтра. Привязывайте параметры
как типизированные SQL-значения. Клиент может менять непрозрачную строку,
поэтому валидируйте курсор, а при необходимости подписывайте его. Повторяйте
фильтр tenant_id из авторизованного запроса независимо от курсора.

Keyset задаёт стабильную границу, но не держит общий снимок между HTTP
запросами. Изменяемый ключ сортировки может переместить запись через границу
и дать пропуск или повтор. Для точного экспорта нужен отдельный согласованный
снимок или зафиксированный набор идентификаторов.

## Типичные ошибки

Курсор только из timestamp теряет строки с одинаковым временем.
`<=` повторяет граничную строку. Курсор от другого фильтра меняет страницу.
OFFSET даёт удобный произвольный переход к номеру страницы, но требует
понимания стоимости и сдвигов.

## Практика

Добавьте третью запись с временем 10:00 и id меньше 12. Проверьте, что место
определяется парой. Удалите запись id=12 после создания курсора и повторите
запрос второй страницы. Затем предложите индекс для tenant_id и тех же
ключей и объясните, почему ведущий tenant_id нужен в WHERE.

## Вопросы с собеседований

1. Зачем id в ORDER BY и в курсоре при неуникальной дате?
2. Гарантирует ли keyset один снимок между запросами?

## Задача

Сделайте выборку по возрастанию created_at и id с таким же количеством строк. Вычислите новую границу первой страницы, проверьте следующую и объясните изменение знака сравнения.

## Шпаргалка

Стабильный ORDER BY, строгий предикат, все ключи в курсоре, прежние фильтры.
LIMIT+1 помогает узнать о продолжении. Ограничьте размер страницы и тестируйте
одинаковые даты и конкурентные изменения отдельно.
