# Isolation levels

## Учебные цели

Объяснить механизм, выбрать транзакционную границу, предсказать наблюдения A/B и проверить инвариант исполняемым сценарием.

## Теория

### Что это

Уровень изоляции определяет, какие изменения других транзакций может увидеть текущая работа. «У нас есть BEGIN» ещё не означает, что два чтения увидят одинаковый набор строк или что две проверки остатка безопасны.

### Как работает

READ COMMITTED в PostgreSQL получает snapshot для каждого statement. Если B зафиксировала UPDATE между двумя SELECT сессии A, второе чтение A может увидеть новое значение. REPEATABLE READ использует snapshot транзакции, установленный первым подходящим statement, и повторное чтение сохраняет прежнюю версию. При конкурентной записи возможен 40001: повторяют всю транзакцию с новым snapshot, а не только последний UPDATE.

SERIALIZABLE отслеживает опасные зависимости чтений/записей и может отменить одну транзакцию, чтобы итог успешных транзакций был совместим с последовательным выполнением. Это не обещание «ошибок больше не бывает». Write skew при чтении общего инварианта и записи разных строк может быть допустим при REPEATABLE READ; один из способов защиты — SERIALIZABLE с retry. READ UNCOMMITTED в PostgreSQL ведёт себя как READ COMMITTED, а PostgreSQL REPEATABLE READ также не допускает phantom reads.

### Важный нюанс / ограничение

Один SQL-блок ниже показывает только синтаксис одной сессии. Изоляцию доказывает controlled scenario с двумя отдельными соединениями: RC даёт 1→0, RR даёт 1→1 при текущем значении 0, SSI отклоняет опасную транзакцию.

## Примеры кода

Это отдельный локальный профиль `pg-transaction-v1`, а не read-only SQL Workspace. Сохраните SQL в `query.sql` и выполните из корня репозитория после сборки transaction image:

```sh
python3 -m transaction_lab.cli run --exercise dml --file query.sql
```

Каждый Run создаёт новую синтетическую базу. `inventory` начинается со строк `(1,1),(2,1)`. В dml Run есть два orders: `(10,1,new,10.00)` и `(11,2,cancelled,99.00)` с временем 2026-01-01 UTC. Зафиксированные изменения не переходят в следующий запуск.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT available FROM inventory WHERE id=1; ROLLBACK;
```

Последний результат: типы `available: int4`.

| `available` |
| --- |
| 1 |

Для реального конкурентного наблюдения запустите controlled scenario:

```sh
python3 -m transaction_lab.cli scenario read-committed
```

В конкурентных сценариях timeline содержит отдельные записи `session=A` и `session=B`, statements, результаты и SQLSTATE. Сценарий indexes показывает только план одной сессии и не демонстрирует изоляцию. Число соединений указано в JSON; одно соединение не выдаётся за демонстрацию изоляции. Блокирующие сценарии ждут подтверждённой lock dependency, а не случайного интервала времени.

| Шаг | Сессия A | Сессия B | Что проверить |
| --- | --- | --- | --- |
| 1 | Читает или удерживает строку 1 | Независимое соединение | Исходное available=1 |
| 2 | Продолжает свою транзакцию | Читает/изменяет по выбранному сценарию | Snapshot, ожидание либо SQLSTATE |
| 3 | COMMIT или ROLLBACK | Завершает/откатывает работу | Итог и освобождение блокировок |

## Типичные ошибки

Один BEGIN не выбирает SERIALIZABLE. Повтор только последнего UPDATE после 40001 использует неверную границу. Отсутствие dirty reads не исключает все бизнес-аномалии.

## Практика

Откройте Transaction Lab справа. Сравните «Read Committed», «Repeatable Read» и «Serializable». Отметьте момент появления нового снимка или SQLSTATE.

Сравните отдельные сценарии read-committed, repeatable-read и serializable на исходных остатках 1,1. В первых двух A читает id=1, B меняет его на 0 и фиксирует, затем A читает снова. Предскажите обе пары наблюдений до запуска. В serializable обе сессии сначала читают SUM, затем уменьшают разные строки: одна должна получить 40001.
