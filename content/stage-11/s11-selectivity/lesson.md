# Selectivity

## Учебные цели

Оценить долю строк по предикату, сравнить оценку планировщика с фактом и
объяснить выбор плана на перекошенных данных.

## Теория

### Что это

Селективность — доля строк, отобранных условием. Кардинальность — ожидаемое или фактическое количество строк.

### Как работает

Если из 10 000 заказов только 10 новые, фильтр `status = 'new'` выбирает 0,1%.
Кардинальность результата — 10 строк, селективность предиката в расчётах
планировщика — доля 0,001. В разговоре «высокоселективный фильтр» обычно
означает узкое условие. Для ясности сообщайте фактическую долю.

PostgreSQL не выполняет запрос при обычном EXPLAIN. Он оценивает количество
строк из статистики и условий. ANALYZE собирает статистику выборкой.
`most_common_vals` и `most_common_freqs` описывают частые значения и их
частоты. Гистограмма помогает оценивать диапазоны среди остальных значений.
`n_distinct` задаёт количество разных значений или долю от числа строк.
Это приближения. После крупной загрузки статистика может отставать. Autovacuum
обычно запускает autoanalyze, а в лаборатории запускайте ANALYZE явно.

Предикаты по городу и региону могут быть связаны: из города часто следует
регион. Ошибка предположения о независимости меняет оценку JOIN и порядок
обработки. Расширенная статистика PostgreSQL помогает отдельным случаям
зависимых условий, но полезность проверяют сравнением оценки с actual rows.

### Важный нюанс / ограничение

ANALYZE получает выборку. Скошенные и связанные признаки могут требовать дополнительной статистики или объяснения расхождений.

## Модель понимания

Сравнивайте estimate и actual на одном узле. Большое расхождение до JOIN влияет на дальнейший выбор порядка и алгоритма соединения.

## Что нужно знать на Junior

### Обязательно

Сопоставьте частоту значения, ожидаемую кардинальность, actual rows и loops. Не подгоняйте план под наличие индекса.

## Примеры кода

Практика проверяется командой `scripts/test_stage11_examples.sh` на синтетической PostgreSQL 17.11. Запускайте изменения в отдельной учебной базе.

```sql
CREATE TABLE events (id integer PRIMARY KEY, status text NOT NULL);
INSERT INTO events
SELECT i, CASE WHEN i <= 10 THEN 'new' ELSE 'archived' END
FROM generate_series(1, 10000) AS g(i);
CREATE INDEX events_status ON events (status);
ANALYZE events;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT id FROM events WHERE status = 'new';
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT id FROM events WHERE status = 'archived';
SELECT status, count(*) AS n FROM events GROUP BY status ORDER BY status;
```

Результат последнего запроса: `('archived', 9990)`, `('new', 10)`. Типы
text и bigint. Найдите rows в оценке и actual rows в выполненном узле.
Смотрите loops: actual rows у узла — среднее за проход. Buffers отражают
работу со страницами. Для archived Seq Scan может быть самым дешёвым путём,
даже при наличии индекса. Не фиксируйте название узла как часть контракта.

## Типичные ошибки

Сравнивать таблицу с тысячей равномерных строк и production с сильным
перекосом. Смотреть только общий Execution Time и пропустить ошибку оценки
в раннем узле. Принудительно отбрасывать Seq Scan в приложении. Путать долю
условия WHERE с долей, остающейся после LIMIT или JOIN.

## Практика

Поменяйте соотношение с 10/9990 на 5000/5000. Снимите EXPLAIN до и после
ANALYZE, запишите выбранные узлы, оценки и фактические числа. Не
сравнивайте лишь время. Объясните, почему одинаковый запрос для двух
значений статуса может заслуживать разные планы.
