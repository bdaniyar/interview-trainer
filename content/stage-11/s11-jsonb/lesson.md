# JSONB

## Учебные цели

Выбрать между JSONB и реляционными полями, прочитать вложенный атрибут,
проверить containment, изменить путь и объяснить, какие операции поддержит GIN.

## Теория

### Что это

JSONB хранит разобранное JSON-значение, над которым PostgreSQL поддерживает операторы и индексы.

### Как работает

Иногда backend хранит общую структуру объекта и небольшие дополнительные
атрибуты, которые различаются по типу клиента. Например, у товара обязательны
id, tenant_id, price и created_at, а параметры упаковки различаются по категории.
Первые поля удобно проверять ограничениями, связывать ключами и сортировать.
Гибкая часть может жить в JSONB с проверкой разрешённых ключей на входе.

Тип `json` хранит исходный текст, включая пробелы, порядок ключей и повторы.
`jsonb` хранит разобранную структуру. Пробелы и порядок ключей не сохраняются,
при дублированном ключе остаётся последнее значение. Порядок элементов
массива сохраняется. Если внешний провайдер подписал исходные bytes,
храните их отдельно от разобранной структуры.

`->` возвращает JSONB, `->>` возвращает text. `#>` и `#>>` читают вложенный путь.
Отсутствующий путь даёт SQL NULL. JSON null внутри существующего поля —
значение JSON. При `->>` оно тоже превращается в SQL NULL, поэтому для различия
проверяйте `?` и `jsonb_typeof`. `@>` проверяет containment. При containment
массива порядок и повторяемость элементов не учитываются так, как при сравнении
обычных упорядоченных списков. `?` ищет ключ или строковый элемент верхнего уровня.

### Важный нюанс / ограничение

Изменение пути фиксируется новой версией строки. У большого документа и GIN есть цена записи, а гибкий тип не заменяет FK и проверку бизнес-правил.

## Модель понимания

Проследите одно поле от входного JSON через оператор извлечения до типа SQL. Отдельно подпишите отсутствующий ключ, JSON null и строку 'null'.

## Примеры кода

Практика проверяется командой `scripts/test_stage11_examples.sh` на синтетической PostgreSQL 17.11. Запускайте изменения в отдельной учебной базе.

Запустите пример в одноразовой PostgreSQL 17 базе. Веб-SELECT и Transaction Lab
используют собственные ограничения SQL, для этого блока предназначен отдельный
стенд проверенных примеров.

```sql
CREATE TABLE products (id integer PRIMARY KEY, attrs jsonb NOT NULL);
INSERT INTO products VALUES
    (1, '{"shipping":{"days":2},"tags":["fragile","gift"],"note":null}'),
    (2, '{"shipping":{"days":5},"tags":["standard"]}');
CREATE INDEX products_attrs_gin ON products USING gin (attrs);
SELECT id, attrs #>> '{shipping,days}' AS delivery_days,
       attrs ? 'note' AS note_present
FROM products
WHERE attrs @> '{"tags":["gift"]}'
ORDER BY id;
UPDATE products
SET attrs = jsonb_set(attrs, '{shipping,days}', '3'::jsonb)
WHERE id = 1
RETURNING id, (attrs #>> '{shipping,days}')::integer AS delivery_days;
SELECT id, attrs -> 'note' IS NULL AS absent,
       jsonb_typeof(attrs -> 'note') AS json_type
FROM products ORDER BY id;
```

Первый результат: `(1, '2', true)`, типы integer, text, boolean.
UPDATE возвращает `(1, 3)`, два integer. В последней выдаче у id=1
`absent=false`, `json_type='null'`; у id=2 `absent=true` и SQL NULL.
В `jsonb_set` путь до изменяемого элемента должен существовать. Последний ключ
можно создать при заданном флаге, но отсутствующий промежуточный объект
автоматически не строится.

### Индексация и запись

GIN строит обратное отображение ключей или значений на строки. Стандартный
`jsonb_ops` поддерживает containment, операторы существования и часть JSONPath.
`jsonb_path_ops` поддерживает containment и JSONPath, но не операторы
существования. Он индексирует комбинации пути и значения и часто менее
громоздок для конечного набора условий. Для частого сравнения одного
извлечённого поля может быть разумнее выражение B-tree, например по
`(attrs ->> 'category')`. План зависит от данных и статистики.

UPDATE JSONB создаёт новую версию строки, даже при изменении одного пути.
Большой документ может увеличить работу записи и рост WAL. Операция
`jsonb_set(attrs, ...)` работает над значением в UPDATE, но два процесса,
которые прочитали документ в Python и записали свои копии целиком, могут
потерять изменение. Добавьте условие версии или защитите нужную транзакцию.

## Типичные ошибки

Путать `'2'` и JSON number 2. Ожидать, что `?` ищет произвольную вложенность.
Использовать `->>` как число без проверки и приведения. Переносить в JSONB
поля, которым нужны FK, частое сортирование или строгий тип.
Рассматривать GIN как гарантию конкретного плана на крошечной таблице.

## Вопросы с собеседований

1. Чем `->` отличается от `->>`, как различить отсутствующее поле и JSON null?
2. Когда разумно взять GIN и когда стоит выбрать обычную колонку?

## Хорошие ответы

<details>
<summary>Раскрыть ответы</summary>

`->` сохраняет тип JSONB, `->>` возвращает text. У отсутствующего поля
оператор `->` возвращает SQL NULL. У существующего JSON null
`jsonb_typeof` возвращает строку 'null'.

GIN помогает искать документы по поддерживаемым условиям containment или
существования. Обычная колонка удобна для ограничений, связей, типизированных
вычислений и регулярной сортировки. Выбор проверяют по запросам и модели данных.

</details>
