# Chat API на FastAPI

Готовый к вызову сервис должен отвечать и на простой запрос, и на неудачу. Разработчик контролирует схему, время ожидания, идентификатор операции и то, какие данные попадут наружу. Модель контролирует только собственный результат.

## Учебные цели

- Собрать протестированный POST /chat на FastAPI.
- Вернуть типизированные исходы с request ID.
- Проверить DTO, таймаут и отсутствие утечки между запросами.

## Теория

Входной DTO описывает вопрос и предел длины. Он не содержит URL провайдера, ключи или роль пользователя. Provider dependency подставляется конфигурацией. **Request ID** — идентификатор одной операции, полезный при связке клиента и метрик. Генерируй его один раз, не вместо авторизации. Прикладной ответ содержит `status`, `text` и опциональные usage. Pydantic response model ограничивает форму, но если сырой ключ уже оказался внутри поля text, тип строки его пропустит. Поэтому граница редактирует источники: только допустимый результат и безопасное сообщение об ошибке.

| Outcome | HTTP в упражнении | Что получает клиент |
| --- | --- | --- |
| completed | 200 | Непустой текст и optional usage |
| refusal, incomplete | 200 | Тип outcome, без случайно слитого partial текста |
| empty | 502 | Провайдер объявил завершение без пригодного текста |
| unavailable | 503 | Обобщённая ошибка зависимости |
| timeout | 504 | Превышен срок ожидания приложения |
| invalid request | 422 | Короткий статус, сырые входы скрыты |

В потоке результат сообщается terminal-событием. В непотоковом вызове есть возможность выставить HTTP-код до отправки. Сохраняй per-request state в локальных переменных. Общий provider имеет соединения, а не текущую историю. Не держи запрос к PostgreSQL открытым до прихода результата. Сохраняй только необходимое и после возврата снова проверяй права. В P1 данных реального пользователя нет.

## Модель понимания

Схема отвечает за форму. Use case отвечает за статус и правила публикации. Adapter отвечает за сеть и тип provider ошибки. Если TestClient вернул 200, проверь status и содержание. Если исключение содержит header или key, исключение служит диагностикой внутри адаптера, а клиент получает только `unavailable` и request ID.

## Что нужно знать на Junior

Проверь параллельно два разных входа и сравни request ID, текст и отсутствие чужих полей. Два последовательных запроса демонстрируют только часть требований. Таймаут ограничивает ожидание, но не доказывает отсутствие выполнения со стороны провайдера. Тест закрывает fake ресурс для обоих исходов.

## Примеры кода

Небольшой TestClient проверит другой endpoint. В примере нет провайдера; цель — увидеть validation и неизменяемый ответ DTO.
```python
from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

class Search(BaseModel):
    term: str = Field(min_length=1, max_length=12)

class Found(BaseModel):
    term: str

app = FastAPI()

@app.post("/lookup", response_model=Found)
def lookup(value: Search):
    return {"term": value.term, "internal_rank": 3}

with TestClient(app) as client:
    assert client.post("/lookup", json={"term": "курс"}).json() == {"term": "курс"}
    assert client.post("/lookup", json={"term": ""}).status_code == 422
    assert client.post("/lookup", json={"term": "a" * 13}).status_code == 422
print("валидация и фильтр ответа подтверждены")
```
Результат содержит только term, потому что response_model описывает это поле. Этот пример не тестирует генерацию и не экранирует секреты, уже записанные непосредственно в term.

## Типичные ошибки

- Принимать провайдерский ключ от браузера.
- Указывать async route с блокирующим вызовом клиента.
- Логировать сырое исключение и вход.
- Возвращать HTTP 200 и completed для пустого результата.

## Хорошие ответы

Провайдерский адаптер и схема ограничивают поля. Timeout прекращает локальное ожидание. Для изоляции запусти два разных запроса одновременно, сравни результаты и проверь, что ни один не читает изменяемое состояние другого.

## Критерии хорошего ответа

Назови схему, инъекцию провайдера, поля результата и соответствие с HTTP кодом. Продемонстрируй отсутствие сырого сообщения ошибки или входа в ответе.

## Задача

Напиши `create_app(provider, *, timeout=0.5, id_factory=...)` с `POST /chat`. DTO принимает только `question` — после strip 1–500 символов. При ошибке возвращается HTTP 422 и `{"status":"invalid_request"}` без входа. Вызывай асинхронный `provider.generate(trimmed_question)` через зависимость, получай `Generation` либо `ProviderUnavailable`. Ответ имеет `request_id` (строка от id_factory, по умолчанию UUID), `status`, `text` и `usage`. Сохрани известный расход. При неизвестном usage возвращай null. Status и HTTP соответствуют таблице, для ошибок без результата usage null. Не публикуй partial text или подробности исключений. Внешняя отмена проходит и освобождает ресурсы fake.

Пример: `Generation("completed", "Курс найден", 7)` маппится в HTTP 200 с текстом и `usage=7`. Run запускает TestClient. Check проверяет другой текст, ошибочные поля, разные исходы, timeout и изоляцию двух запросов.
