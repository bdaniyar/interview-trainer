# Повторы и лимиты запросов

Endpoint обращается к модели и получает 429. Если повторить немедленно, многие клиенты повторят одновременно. Если ждать без лимита, API держит обещание пользователю уже дольше, чем тот готов ждать. Повторы требуют общего бюджета.

## Учебные цели

- Различить временные, постоянные и неопределённые исходы.
- Сочетать backoff, jitter, Retry-After, попытки и deadline.
- Проверить количество сетевых обращений без реального сна.

## Теория

HTTP 429 означает слишком много запросов, 503 — временную недоступность сервиса. Они могут разрешать повтор при подходящем контракте. HTTP 401 означает проблему аутентификации, и повтор с теми же данными обычно её не исправит. Отдельно есть неопределённый исход. Таймаут может случиться после выполнения внешнего действия, но раньше получения ответа. Повтор способен создать вторую генерацию, вторую плату или повторный побочный эффект. Для внешнего эффекта нужна доказанная политика повторяемости, например поддерживаемый ключ идемпотентности. Наши учебные 429/503 — синтетические отказы до обработки, неизвестный timeout не повторяется.

**Exponential backoff** увеличивает интервал между запросами. Для индекса неудачи `i` от нуля потолок равен `min(cap, base · 2**i)`. **Full jitter** берёт долю этого потолка по случайному числу из `[0,1)`, чтобы клиенты не проснулись вместе. `Retry-After` по HTTP может содержать целое число секунд или дату. Секунды неотрицательны. Дату сопоставь с временем UTC. Часы UTC могут корректироваться, поэтому общий deadline удобнее считать монотонными часами, которые не идут назад. В задаче при валидном заголовке выбираем максимум указания сервера и jitter.

Лимит попыток включает первую отправку. Deadline покрывает полную длительность ожиданий и попыток. Если следующая разрешённая пауза заканчивается прямо на deadline, времени на попытку уже нет. Если SDK повторяет дважды, а приложение даёт три попытки, число отправок может стать девять. С очередью оно может вырасти ещё. В учебном клиенте SDK attempts отключены, retry policy одна.

## Модель понимания

При `base=1`, `cap=4`, RNG 0,5 и серии 429, 503, success задержки будут 0,5 и 1 при отсутствии Retry-After. Если 429 сообщает 5, ждём не менее 5, но прекращаем при оставшемся сроке 4. Retry exhaustion фиксирует последнюю допустимую причину. Приложение не выдаёт сырой provider exception пользователю.

## Что нужно знать на Junior

Раздели часы, сон и случайность. В hidden tests сон просто изменяет fake clock, чтобы измерить суммарное ожидание. Для зависшего вызова добавь настоящий общий `asyncio.timeout` с остатком, иначе deadline ограничит только паузы. CancelledError должен выйти сразу.

## Примеры кода

Сравним задержки двух синтетических клиентов с одним ceiling. В примере RNG задан явно для воспроизводимого расчёта.
```python
def pauses(base, cap, random_draws):
    return [min(cap, base * 2 ** i) * draw for i, draw in enumerate(random_draws)]

assert pauses(1, 4, [0.2, 0.5, 0.75, 0.5]) == [0.2, 1.0, 3.0, 2.0]
assert pauses(1, 2, [0.0]) == [0.0]
assert pauses(1, 2, []) == []
print(pauses(1, 4, [0.2, 0.5, 0.75, 0.5]))
```
Вывод — четыре паузы. Последняя не превосходит cap: потолок ограничил экспоненту. Это только расчёт задержек, без дат, таймеров и отправки.

## Типичные ошибки

- Повторять все исключения.
- Обрезать Retry-After до cap и выполнить раньше разрешённого срока.
- Считать max_attempts числом повторов без первой отправки.
- Расположить проверки deadline только перед sleep.

## Хорошие ответы

Deadline применяется ко всему сценарию и остаток — к сетевой попытке. Jitter разводит повторные обращения. При неопределённом исходе полезны request ID и класс ошибки, без заявления об отсутствии эффекта.

## Критерии хорошего ответа

Посчитай максимум отправок и пауз для выбранного бюджета. Объясни, почему 401, отмена и timeout не обрабатываются как временный 503.

## Задача

Реализуй `async call_with_retry(send, *, clock, sleep, rng, max_attempts, budget, base=1, cap=8, now_utc=None)`. `clock()` — монотонное время, `sleep(seconds)` — async, `rng()` возвращает долю. `now_utc()` — опциональный aware datetime для HTTP-date. Установи deadline разово. Попытайся вызвать `send()`, ограничив ожидание остатком. Повторяй только `HTTPFailure` со статусом 429/503. Остальные ошибки включая исходный TimeoutError вызова и отмену передаются. Локальный истёкший deadline и исчерпание попыток поднимают `RetryExhausted` (если известен последний HTTPFailure, сохрани его причиной). После deadline не возвращай и запоздавший результат, даже если fake не ожидал.

Разбирай Retry-After из строки после strip. ASCII digits — неотрицательные секунды. Дата без UTC clock и повреждённые заголовки игнорируются. Для даты в прошлом используй 0. Например, `[429, 503, success]` без заголовка с RNG 0,5, base 1, cap 8 даёт паузы 0,5 и 1. Откажи при nonpositive max_attempts или нечисловых/нефинитных или отрицательных лимитах. Budget 0 допускает ноль вызовов. Run показывает пример. Check проверяет часы, фактические вызовы, cancel, дедлайн и ошибочные заголовки.
