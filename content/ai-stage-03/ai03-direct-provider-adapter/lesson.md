# Прямой адаптер провайдера

Сервис показывает первый элемент ответа модели. На демонстрации он получил строку, а в следующем запуске элементом оказалась запись о ходе генерации. Нужно изучить контракт API до того, как связывать его с HTTP-ответом своего приложения.

## Учебные цели

- Сопоставить HTTP, SDK и прикладной тип.
- Разобрать несколько output items, статус и optional usage.
- Проверить вызов через fake и отдельно настоящий SDK через mock transport.

## Теория

**LLM provider API** позволяет по HTTP отправить вход и получить результат языковой модели. При прямом HTTP ты формируешь JSON, разруливаешь ошибки и проверяешь типы сам. **SDK** — библиотека клиента с методами, моделями входа/выхода и управлением transport. Авторизация, лимиты, разбор статуса результата и схема твоего приложения остаются отдельными задачами.

В Responses API полезно читать `status`, `output` и `usage` отдельно. `output` содержит элементы, например message или сведения о reasoning. У сообщения есть список content parts. Тип `output_text` содержит строку, `refusal` — отказ, а другие типы не являются ответом пользователю. Свойства SDK облегчают доступ. `output_text` агрегирует текст, но наличие строки ещё не означает completed. При `incomplete` мог закончиться бюджет вывода. В этом упражнении приложение скрывает фрагмент, зато сохраняет тип исхода. При неизвестном usage возвращай `None`. Поля реального протокола могут обновляться, поэтому версия зафиксирована отдельно.

В синхронном коде ожидание блокирует текущий поток. В async route ожидай async-метод и переиспользуй клиент через lifecycle. Названия полей в Chat Completions, Gemini и Anthropic отличаются от Responses. Они могут иметь свои events и роли, даже если все возвращают текст. Тренировочный fake эмулирует небольшую часть объекта Responses. Он не проверяет качество и доступность модели.

## Модель понимания

В адаптере выполняются две отдельные трансляции. Запрос получает модель и текст из конфигурации приложения. Возвращаемое значение извлекает текст и метаданные без предположения о позиции. Из HTTP 429 приложение получает контролируемый исход; в AI3.4 подобная граница разрешит решить, когда пробовать ещё раз. Сырое сообщение исключения может раскрыть внутренние данные или вход. Его не выводим в приложение.

## Что нужно знать на Junior

Сделай ровно один scoped вызов и возвращай ровно один тип результата. SDK, provider response и наш `GenerationResult` имеют разные жизненные циклы. Демо настоящего SDK использует `AsyncOpenAI` и HTTPX2 MockTransport версии, проверенной отдельно. В Python Runner достаточно stdlib.

## Примеры кода

Упростим один элемент до списка частей. Родственный transport mapper читает только известный тип, игнорируя вложенные метаданные.
```python
def visible_fragments(parts):
    return "|".join(part["value"] for part in parts if part["kind"] == "paragraph")

packet = [{"kind": "metadata", "value": "размер"},
          {"kind": "paragraph", "value": "Въезд"},
          {"kind": "paragraph", "value": "Выезд"}]
assert visible_fragments(packet) == "Въезд|Выезд"
assert visible_fragments([packet[0]]) == ""
assert visible_fragments([]) == ""
print(visible_fragments(packet))
```
Вывод содержит два фрагмента, а metadata не попала в текст. Это пример нормализации вообще. Реальные имена элементов Responses описаны выше и проверяются в отдельном SDK-тесте.

## Типичные ошибки

- Считать каждый элемент текстом или брать только первый.
- Сливать refusal и transport failure в успешный пустой ответ.
- Делать синхронный SDK-вызов прямо в async route.
- Маркировать неизвестный usage числом 0.

## Вопросы с собеседований

1. Что отдаёт SDK сверх HTTP?
2. Почему нужен отдельный status?
3. Чем ожидаемая ошибка провайдера отличается от ошибки кода адаптера?

## Хорошие ответы

SDK предоставляет клиент, протокол и типы. Адаптер обязан читать статус вместе с полями. Ожидаемые ошибки преобразуются в исходы приложения, а неожиданные требуют диагностики, а не выдачи ложного успеха.

## Критерии хорошего ответа

Назови способ извлечения текста, действия для отсутствующего usage и порядок работы со статусом. Объясни, что доказал текущий mock-transport тест.

## Задача

Реализуй `async generate(client, question) -> GenerationResult`. Fake имеет `client.responses.create(model="fixture-model", input=question)`. Объект результата предоставляет `status`, `output` и `usage`. Спецификация в `contracts.py`. Прочитай все элементы с `type="message"` и их части в порядке ответа. Для completed склей содержимое `output_text` без дополнительного разделителя. Например, «Въезд» и « утром» дают «Въезд утром». Если есть явный refusal, верни `refusal` без текста. Пробельный результат верни как `empty`, incomplete как `incomplete`, failed как `unavailable`. Usage — пара `(input_tokens, output_tokens)`, если оба значения известны, иначе None. Оба нуля могут быть наблюдаемыми.

`WireError` становится `unavailable` с неизвестным usage. Не изменяй вход и не повторяй вызов. Ошибка неизвестного типа и внешняя отмена продолжают распространяться. Run проверяет публичный случай, Check — другие элементы, ошибки, неполные поля и число отправок.

## Шпаргалка

### Краткий конспект

Responses содержит список элементов, а сообщения — отдельные части. Сначала обработай статус, затем извлеки текст и отдельно usage. В ответе с reasoning перед сообщением текст всё равно берётся из message. Неизвестный расход не считается нулём. Для текущей формы клиента разработчик проверяет mock transport, приложение работает с собственным типом.
