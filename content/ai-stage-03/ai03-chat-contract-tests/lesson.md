# Контрактные тесты Chat API

В предыдущем уроке заработал POST /chat. Один тест с 200 не ловит сервис, который всегда возвращает одно и то же. Как сделать тесты, которые реагируют на настоящие сбои и помогают другому разработчику понять контракт?

## Учебные цели

- Различить test double, контрактный тест и live eval.
- Проверить 11 наблюдаемых исходов сервиса.
- Объяснить, почему сломанная реализация должна провалить конкретное утверждение.

## Теория

**Test double** — замена зависимости. Fake выполняет предсказуемое правило, spy записывает обращения. **Contract test** использует реальные границы приложения: HTTP, форму результата, количество вызовов, отмену. Fake управляет исходом, а не отвечающей веткой сервиса. **Live eval** оценивает реальную модель на репрезентативных данных по метрикам. В этой работе ни качество модели, ни внешний биллинг не проверяются.

Проверка нужна на успех, пустой результат, отказ, incomplete, unavailable, timeout, отмену, неверный вход, изоляцию запросов, cleanup потока и отсутствие сетевого доступа/секретов. Две части последнего свойства можно сверить отдельными наблюдениями одного сценария. Пример переменной, которую не надо логировать, — ключ из исключения. Пример нужной информации — безопасный статус и request ID.

**Negative control** намеренно нарушает одно свойство. Например, fake даёт отказ, но сломанный адаптер превращает его в completed. Test утверждает отказ и отсутствие публичного текста. Та же проверка должна проходить на здоровом обработчике. Критерий правильности — поведение, поэтому число строк или наличие конкретного `assert` внутри функции само по себе ничего не доказывает. Из-за дорогого inference offline тесты выполняются на синтетических входах и закрытом transport.

## Модель понимания

Разверни пример как исследование. Подготовка задаёт состояние и значения. Действие вызывает endpoint или генератор. Наблюдения проверяют HTTP, статус, число обращений и cleanup. Если проверка отсутствует, мутант проходит. Если тест всегда падает даже на рабочем коде, он тоже бесполезен.

## Что нужно знать на Junior

Для передачи проекта опиши команду запуска, ожидаемый исход, место подмены адаптера и ограничения теста. Если найдёшь ошибку, добавь воспроизводимый failure: он падает на прежней версии и проходит после исправления. Открой `projects/chat_api/README.md` и запусти suite P1 на локальном fake. Измени ограничение длины вопроса и добавь тесты на двух соседних значениях. Тест контракта не требует знать точный текст всех возможных моделей. Для scripted fake конкретная строка известна и подтверждает, что request state принадлежит этому запросу.

## Примеры кода

Сначала проверим тестовую идею без FastAPI. Сломанная функция всегда выдаёт готово, поэтому контракт отказа должен это заметить.
```python
def verify_outcome(make):
    response = make("denied")
    assert response["state"] == "refused" and response["text"] is None

def normal(reason):
    return {"state": "refused", "text": None}

def broken(reason):
    return {"state": "done", "text": "secret"}

verify_outcome(normal)
for candidate in (broken, lambda _: {"state": "refused", "text": "secret"}):
    try:
        verify_outcome(candidate)
    except AssertionError:
        print("контракт поймал дефект")
    else:
        raise AssertionError("negative control escaped")
```
Две одинаковые строки вывода подтверждают, что проверка ловит отдельно неверный статус и утечку поля. В задании наблюдения проходят через HTTP, отмену и поток.

## Типичные ошибки

- Проверить только 200 или только ненулевой JSON.
- Подменить сам route и тем самым убрать проверяемую логику.
- Использовать предопределённый текст как доказательство качества живой модели.
- Считать безошибочное завершение доказательством закрытия upstream.

## Вопросы с собеседований

1. Как понять, что контрактный тест обнаруживает дефект?
2. Почему fake не доказывает качество?
3. Как измерить cleanup?

## Хорошие ответы

Проверь здоровый и намеренно сломанный вариант одного контракта. Fake делает результат воспроизводимым. Cleanup покажет finally с сигналом или наблюдаемым счётчиком после API вызова.

## Критерии хорошего ответа

Объясни, какая зависимость заменена и где виден реальный контракт. Проверь отрицательный контроль для одного поля и независимость тестов. Назови то, что верифицируется только отдельной live оценкой.

## Задача

Напиши `async verify_contract(probe)`. Каждый вызов `await probe(case)` выполняет сценарий и возвращает `Observation` из `harness.py`. Обязательны все 11 сценариев. Для success проверяй HTTP 200, completed, ровно один вызов и текст `expected_text` из fixture. Для empty, refusal, incomplete, unavailable и timeout проверяй HTTP, статус, пустой text и один вызов. Для timeout ещё нужен cleaned. Для invalid — 422, invalid_request и ноль вызовов. Для cancellation — сигнал отмены и cleanup. Для isolation — два завершённых ответа со своими разными ID, соответствующими `expected_text` и `expected_second`, и ровно два вызова. Для stream_cleanup — один непустой delta и закрытие без дочитывания. Для offline — 503, unavailable, ноль socket calls, отсутствие marker секрета в ответе или логах.

Например, слишком добрый адаптер возвращает HTTP 200 и completed при refusal. Твой suite должен поднять AssertionError. Здоровый fixture обязан пройти. Run вызывает оба. Hidden Check подставляет другие искусственные входы и разные одиночные дефекты. Не подменяй наблюдения или их ожидаемые значения.
