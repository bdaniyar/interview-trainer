# Данные, признаки и жизненный цикл модели

В момент оформления брони API хочет оценить риск отмены. В исторической базе уже есть и дата брони, и факт возврата. Если передать модели всё, что известно сегодня, она покажет высокий балл на истории и ошибётся на новых запросах.

## Учебные цели

- Различить признак, метку и доступные на момент решения данные.
- Объяснить train, validation и test и выбрать границу по времени и группе.
- Реализовать воспроизводимое разделение без потерь идентификаторов.

## Теория

**Feature**, или признак, — измерение, которое получает модель. Для прогноза отмены это могут быть цена и число ночей. **Label**, или метка, — позднее наблюдаемый исход. Например, отменена ли бронь в течение семи дней. В момент прогноза метки ещё нет. Если прогнозируется вероятность, отношение к метке проверяют на множестве случаев.

На **train** алгоритм подбирает параметры. На **validation** мы сравниваем варианты, например глубину дерева. После выбора **test** оценивает, насколько решение работает на новых примерах. **Generalization** — способность переносить результат на данные, которых модель не видела. **Overfitting** — модель подстроилась под частности train, поэтому хорошо воспроизводит прошлое и плохо работает на новых данных. Если постоянно выбирать вариант по test, test сам становится частью настройки.

**Data leakage** — попадание в обучение или оценку данных, которых не должно быть в этом месте. Случайное деление строк ломает оценку по времени, если прошлое смешивается с будущим. Одна и та же группа, например клиент с несколькими бронями, может оставить узнаваемые признаки по обе стороны. Достаточно совпадения клиента и тарифа, чтобы модель запомнила частный шаблон.

| Вопрос оценки | Пригодная схема | Ограничение |
| --- | --- | --- |
| Как сработает на более поздней неделе? | Разделить по времени | Отдельно решить, считаются ли повторные клиенты допустимыми |
| Как сработает на новом клиенте? | Разделить по владельцу группы | Прошлое и будущее могут смешаться, если времени не уделить внимания |
| Как сработает на новых клиентах позже? | Одновременно дата и группа | Клиенты на границах могут уменьшить размер пригодных наборов |

Обучение должно знать метку. Рабочий inference получает только признаки. Параметры загружаются из выпуска модели и меняются при отдельном процессе обучения и публикации. API может записывать данные для будущего обучения без перестройки параметров на каждом запросе.

## Модель понимания

Выгрузка SQL отвечает на вопрос «что записано к моменту предсказания». Иногда событие произошло раньше, но стало доступно позже. Например, оплата пришла вчера, а процесс синхронизации записал её сегодня. Для разделения зафиксируй момент, когда сервис мог прочитать признак. Граница времени между пакетами защищает от утечки из будущего, а фильтр каждого признака защищает внутри одной строки.

## Что нужно знать на Junior

Держи наборы и версию признаков отдельно. Начинай с простого прогнозного правила и сравнивай одной метрикой на одинаковой выборке. Карантин группы означает, что её записи сохранены для аудита. Смещение, вызванное исключением частых клиентов, нужно измерить отдельно.

## Примеры кода

Снимок значения показывает, почему факт возврата нельзя увидеть при создании брони. Второе число в паре — время доступности.
```python
def known_at(entries, moment):
    return {name: value for name, (value, available_at) in entries.items()
            if available_at <= moment}

signals = {"nights": (3, 10), "fee_paid": (True, 11), "refund": (True, 18)}
assert known_at(signals, 10) == {"nights": 3}
assert known_at(signals, 9) == {}
assert "refund" not in known_at(signals, 17)
print(known_at(signals, 10))
```
Вывод — `{'nights': 3}`. Ровно в момент 10 признак уже доступен. Тесты на 9 и 17 проверяют, что фильтр действительно использует границу. Здесь время целое, в приложении потребуется единая зона и правило о моменте видимости записи.

## Типичные ошибки

- Случайно перемешать строки и заявить проверку на будущей неделе.
- Смотреть на test после каждого изменения.
- Удалять пограничные группы без отчёта. Так исчезает часть данных и меняется выборка.
- Вычислить среднюю цену по всему файлу до разделения и объявить её признаком без утечки.

## Вопросы с собеседований

1. Когда используешь разбиение по времени?
2. Как отличить переобучение от утечки?
3. Что происходит с моделью во время inference?

## Хорошие ответы

Граница по времени имитирует наблюдение данных в будущем. Переобучение оценивается по разнице train и независимых данных. Утечку ищут по происхождению и времени признаков. При inference параметры применяются без обязательного обновления.

## Критерии хорошего ответа

Назови единицу разбиения, момент видимости признака, правило для пограничного клиента и способ обнаружить дубликат. Объясни, каким бизнес-вопросам соответствует test.

## Задача

Реализуй `split_bookings(rows, validation_at, test_at)`. Каждая запись имеет уникальный целый `id`, строку `user_id`, целое `booked_at`, `features` со значениями `(value, available_at)` и `label`. Верни `train`, `validation`, `test`, `quarantine` как ключи словаря со списками записей. Для примера `booked_at=12` при границах 12 и 18 попадает в validation, если клиент не пересекает несколько периодов.

Периоды полуоткрытые: train до первой границы, validation до второй, test от второй. Пользователь, чей набор броней попал бы в несколько периодов, целиком в quarantine. В выходной записи оставь только видимые признаки, в исходных данных ничего не меняй. Каждый список упорядочи по `(booked_at, id)`. Отклони повторный ID и `validation_at >= test_at`. Run запускает публичный пример. Для самопроверки попробуй случайный порядок, пересечение периодов и признак ровно в момент брони.

## Шпаргалка

### Краткий конспект

Train подбирает параметры, validation сравнивает решения, test фиксирует результат после выбора. В прогнозе срабатывает только то, что реально было доступно к предсказанию. Для брони в 22 признак с отметкой 23 недоступен, даже если строка скачана месяц спустя. Фиксируй уникальные ID и сохраняй карантин для анализа выборки.
