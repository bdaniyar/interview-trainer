# История беседы и бюджет контекста

Пользователь открывает чат с ноутбука и телефона. HTTP-запросы независимы, но оба относятся к одной беседе. Нужно восстановить допустимую историю без чужих сообщений и сохранить смысл вызовов при сокращении контекста.

## Учебные цели

- Отличить историю приложения от provider-managed state.
- Собрать контекст с выходным резервом и неизменной политикой.
- Сохранить многовызовный обмен целиком и проверить доступ к беседе.

## Теория

**Stateless HTTP** не переносит состояние приложения автоматически между запросами. Беседа живёт в хранилище. Сначала приложение проверяет `conversation_id` вместе с tenant и subject. Идентификатор ответа или сессии провайдера может упростить продолжение, но он остаётся внешней ссылкой. Связь с владельцем и политика хранения принадлежат приложению. Для удаления нужно закрыть доступ в своей БД и отдельно проверить правила удаления и retention у используемого провайдера.

Контекст — данные, которые потребуются модели на этом шаге. Context window включает вход и место под выход. Если capacity равно 12 и reserve равно 3, входу доступны 9 условных токенов. Политика приложения и свежий вопрос обязательны. Если они уже заняли 10, нужно отклонить запрос до вызова модели. Студенческий счётчик детерминирован для теста, а реальный tokenizer зависит от модели, UTF-8, ролей, структуры items и tool schemas. Отдельно учитывай model-reported usage.

История состоит из групп. Обычное сообщение — одна группа. Модельный turn с несколькими tool calls, всеми результатами и при необходимости opaque provider items — один обмен. Если оставить один result после обрезки, модель потеряет его вызов или перепутает ситуацию. Для этой лаборатории берём самый свежий **непрерывный суффикс** полных групп. Сломанная группа отклоняется даже в старой части истории. Сводка может занимать меньше места, но теряет детали. Для неё фиксируют источники, время, версии и правила допуска; вывод сводки не определяет права.

## Модель понимания

Сохраняй «политика → свежие полные группы → текущий вопрос». Перед совместным обновлением истории выбери политику конкуренции: serialize или reject второй turn. Снимок истории неизменяем, а сохранение выполняется после завершения. Так два устройства не перемешивают arguments и results.

## Что нужно знать на Junior

Не считай пустой ответ успешным компромиссом. Позволь клиенту отправить короткий вопрос, если mandatory context превышает budget. Слабое место write policy — неочищенный provider thread ID, ссылающийся на предыдущую беседу.

## Примеры кода

```python
capacity, reserve, mandatory = 17, 3, 5
groups = [("старый вопрос", 4), ("два calls и outputs", 7)]
left = capacity - reserve - mandatory
sizes = [cost for _, cost in groups[::-1]]
assert sizes[0] <= left and sum(sizes) > left
print(groups[-1][0], left - sizes[0])
```

Вывод `два calls и outputs 2`. Остаётся две единицы входного бюджета, старый вопрос требует четыре.

## Типичные ошибки

- Считать долгоживущий thread ID доказательством прав пользователя.
- Обрезать границу после первого tool result.
- Тратить резерв на историю и оставлять модели нулевой выход.
- Разделять изменяемый список messages между запросами.

## Практика

При `capacity=13, reserve=3` политика и вопрос стоят суммарно 4. Свежайший обмен стоит 7, предыдущая фраза — 2. Что останется в контексте?

## Вопросы с собеседований

1. Как строится context budget для беседы?
2. Почему хранить provider thread недостаточно?

## Хорошие ответы

**Как строится context budget для беседы?**

Резерв выхода вычитается из ёмкости, обязательный policy/current сначала проходит admission. Из остатка берутся неделимые группы с конца. Точный count зависит от модели и представления message.

**Почему хранить provider thread недостаточно?**

Thread ID служит указателем, а tenant, ownership и право на удаление определяет приложение. Репозиторий обрабатывает конкуренцию и создаёт контекст только после object check.

## Критерии хорошего ответа

Покажи расчёт остатка, обратный порядок отбора и пример недопустимого orphan result.

## Задача

Реализуй `build_context(history, conversation_id, principal, policy, current, *, capacity, reserve, count)`. Несуществующая или чужая беседа даёт `PermissionError`. `Conversation.units` — новые к старым при чтении справа налево: хранятся хронологически. Группа — одиночный user/assistant-текст без IDs либо assistant с непустыми уникальными `call_ids` и ровно одним tool message по каждому ID. Tool results могут быть в обратном порядке. Пустая, неполная, неизвестная или смешанная группа вызывает `ValueError` даже если не войдёт в контекст. Создай обязательные system и current user, учти их размеры и reserve. При переполнении обязательного контекста верни `ValueError`. Добавь самый свежий непрерывный суффикс целых групп, не меняй исходные fixtures. Результат `Context` содержит messages, суммарный input и сохранённый reserve. Пример Run оставляет полный обмен, а Check варьирует размер резерва, owner, состав и порядок results. При `capacity=4`, `reserve=2` и двух сообщениях по одной единице история будет пустой.

## Шпаргалка

### Краткий конспект

Привязывай ID к tenant и subject. Контекст — policy, история группами, текущий вопрос и место для ответа. Если свежий обмен не помещается целиком, останови обрезку. Тестовый счётчик подтверждает arithmetic и границы, а фактические токены подтверждает провайдер.

1. Что считается malformed exchange?
2. Что происходит при конкурентном сохранении?
3. Где проверяются права на provider thread?

<details>
<summary>Сверить конспект</summary>

Один вызов без своего результата, повтор или чужой ID. Сохранение одного turn должно завершиться до второго или второй отклоняется. Права проверяет репозиторий приложения до передачи внешней ссылки.
</details>
