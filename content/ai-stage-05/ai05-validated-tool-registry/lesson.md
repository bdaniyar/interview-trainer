# Реестр инструментов и проверка аргументов

Модель предлагает `get_booking` с аргументом `booking_id`. В ответе иногда приходит строка вместо числа, дополнительное поле или результат, который содержит лишние сведения. Один исполнитель должен одинаково обработать все эти случаи.

## Учебные цели

- Собрать allowlist функций с отдельными входной и выходной схемами.
- Передавать trusted principal отдельно от model arguments.
- Ограничить сериализованный результат и сохранить отмену.

## Теория

**Реестр инструментов** — словарь известных серверу имён. Запись хранит тип входа, async функцию и тип выхода. Имя из model output лишь выбирает запись. Функцию устанавливает приложение при сборке сервиса. Таким образом, новый инструмент появляется изменением конфигурации и кода, а не присланным пользователем путём к модулю.

Проверка имеет несколько границ. JSON parser проверяет корректность документа. Pydantic проверяет форму и strict типы, поэтому `"42"` и `true` не проходят как `int`. Домен отдельно проверяет положительное значение ID. `extra="forbid"` отклоняет попытку добавить поле владельца. Principal — удостоверенный контекст вызова, переданный приложением в отдельном аргументе. Право на конкретную запись проверяет следующий слой по этому контексту.

Сервис может вернуть `None`, выбросить исключение или вернуть данные неверного типа. До сериализации проверяем DTO выхода. Полную ошибку заменяем категорией. Размер проверяем после сериализации в UTF-8: строка с кириллицей и строка из ASCII одинаковой длины могут занимать разное количество байтов. Cancellation, сигнал отзыва выполняемой задачи, должен пройти до вызывающего кода. В Python 3.12 `CancelledError` наследуется от `BaseException`; обычный `except Exception` его пропускает.

## Модель понимания

Для call `x5` с ID 42 шаги такие: найти tool → проверить аргументы → вызвать функцию с principal и typed args → провалидировать view → измерить байты → вернуть исход `x5`. На невалидном вводе spy, наблюдающий число вызовов, останется пуст.

## Что нужно знать на Junior

Не используй `eval`, dynamic import и универсальный shell/SQL tool. Бизнес-интеграция получает только разрешённую операцию. Успешный тест должен увидеть side effect в spy или реальное чтение, иначе ответ можно подделать константой.

## Примеры кода

```python
from pydantic import BaseModel, ConfigDict, StrictInt, ValidationError

class Window(BaseModel):
    model_config = ConfigDict(extra="forbid")
    nights: StrictInt

for raw in ('{"nights": 3}', '{"nights": "3"}', '{"nights": 3, "role": "admin"}'):
    try:
        print(Window.model_validate_json(raw).nights)
    except ValidationError as error:
        print(error.errors()[0]["type"])
```

Вывод — `3`, `int_type`, `extra_forbidden`. Длительность проживания ещё нужно проверить правилами домена, например верхней границей и допустимыми датами.

## Типичные ошибки

- Считать одну provider schema валидатором приложения.
- Принимать имя функции как Python import path.
- Возвращать `str(exception)` в model context.
- Измерять размер строки до сериализации.

## Вопросы с собеседований

1. Как доказать, что неизвестный инструмент не исполнился?
2. Как обработать отмену и исключение функции?

## Хорошие ответы

**Как доказать, что неизвестный инструмент не исполнился?**

Передать несколько зарегистрированных функций-spy, вызвать неизвестное имя и проверить типизированный отказ и ноль записей во всех spies. Затем показать, что правильное имя действительно передаёт DTO и principal выбранной функции.

**Как обработать отмену и исключение функции?**

Приложение скрывает внутреннюю причину, возвращая безопасную категорию ошибки. Отмену передаёт дальше, чтобы await и finally на уровне функции освободили ресурсы.

## Критерии хорошего ответа

Раздели parse, schema, domain, execution и output budget. Покажи, кто создаёт principal, и опиши проверку отсутствия вызова при ошибке ввода.

## Задача

Реализуй `async execute_tool(call, principal, registry) -> ToolResult`. При неизвестном имени верни `unknown_tool`. Аргументы — строка JSON максимум 512 байт UTF-8, проходят Pydantic input schema из записи реестра в strict режиме. Невалидный документ даёт `invalid_arguments`. Вызови ровно один раз `await tool.read(principal, args)`. `None` даёт `not_found`. Провал output validation или исключение дают `tool_error` без текста исключения; cancellation пробрасывается. Выход — JSON строки DTO в UTF-8 до 512 байт, превышение даёт `output_limit`. Успех — `ok` с JSON, остальные статусы без output. Во всех случаях сохрани исходный call ID. Run показывает реальный fake для верного ID и отказ на строковом ID; Check проверяет вызовы spies, неожиданные поля и байтовую границу.

Пример `{"booking_id":42}` в открытой fixture возвращает `ok` и `{"city":"Астана"}`. Передача `{"booking_id":"42"}` даёт `invalid_arguments` до чтения.

## Шпаргалка

### Краткий конспект

Allowlist хранит серверные функции, проверенные входы и выходы. Principal передаётся отдельно. Validation ограничивает тип и форму до исполнения, permission — набор разрешённых данных, serialization budget — объём ответа. Cancellation сохраняет семантику async, а безопасный код ошибки защищает внутренние детали.

1. Пройдёт ли `true` как положительный strict integer?
2. Что делать с blob после чтения?
3. Как отличить успевшую отмениться функцию от ошибки провайдера?

<details>
<summary>Сверить конспект</summary>

Bool отклоняется. Проверить DTO, сериализовать и ограничить размер. Отмена остаётся исключением задачи, а ошибка провайдера отображается в безопасную категорию.
</details>
