# Ограниченный цикл инструментов

После вызова функции модель может потребовать ещё один. Приложение должно закончить обработку даже тогда, когда модель каждый раз придумывает новый ID. У каждого завершения есть причина, пригодная для метрик и ответа клиенту.

## Учебные цели

- Реализовать конечный async цикл с явными исходами.
- Различить шаг модели, вызов инструмента и размер observation.
- Использовать общий deadline, отдельный timeout инструмента и отмену.

## Теория

**Turn** — один ответ модели. Один turn может содержать финальный текст или пакет инструментов. Executor возвращает наблюдение, то есть строковое представление результата по call ID. Модель получает накопленные наблюдения в следующем turn. Список предложений надо проверить целиком до первой функции в пакете: повтор идёт как ошибка протокола и не получает второй execution.

**Бюджет** ограничивает независимые ресурсы. На три шага модели может приходиться четыре вызова. Ещё один инструмент не допускается, если свой предел calls исчерпан, даже при свободном step. Байты результата ограничиваются отдельно. Проверяй, остался ли бюджет до tool execution, и помещай в контекст только результат, который полностью помещается в лимит. Счётчики хранят фактически начатые работы.

**Deadline** — абсолютный момент конца, вычисленный один раз по монотонным часам. Новый turn не выдаёт дополнительные секунды. Для долгого await нужен настоящий ограничитель, например `asyncio.timeout`, плюс проверка бюджета перед началом новых операций. У отдельного tool может быть меньший timeout. Если клиент отменил задачу, исключение отмены пробрасывается и `finally` освобождает ресурс. Сетевое ожидание модели начинается после выхода из DB-транзакции.

Успех требует непустой финальный текст. Отказ, неполный ответ, пустой финал, ошибка провайдера, повторный ID и exhaustion — разные исходы. Если tool выбросил обычную ошибку, можно добавить безопасное observation и продолжить. Timeout внешнего действия не доказывает отсутствие эффекта. Повтор чтения имеет свою политику; для записи нужны idempotency и reconciliation, выходящие за пределы этого упражнения.

## Модель понимания

Turn 1 просит list и lookup, поэтому steps=1, calls после выполнения равен 2. Turn 2 получает пару observations. Если вместо текста приходит новый lookup с прежним ID, завершаем до следующего исполнения. Если пришёл текст и deadline не истёк, возвращаем `completed`.

## Что нужно знать на Junior

Бюджет — часть сервера. В тесте можно заменить clock и управлять изменением времени без sleep. Чтобы проверить отмену, инструмент сигнализирует о начале через Event, ждёт и отмечает cleanup во finally.

## Примеры кода

```python
deadline = 15.0
for now in (10.0, 13.5, 15.1):
    print(round(max(0, deadline - now), 1))
assert len("да".encode("utf-8")) == 4
```

Вывод `5.0`, `1.5`, `0`. Третий момент вышел за общий срок. Строка из двух букв занимает четыре байта, поэтому счётчик символов здесь недостаточен.

## Типичные ошибки

- Сбрасывать timeout при каждом вызове модели.
- Учитывать только steps, разрешая сотни tools на одном шаге.
- Проверять duplicate IDs после запуска первого инструмента.
- Превращать отмену в retry или применять retry при неизвестном результате записи.

## Вопросы с собеседований

1. Где начинается общий deadline?
2. Что происходит после повторного call ID?

## Хорошие ответы

**Где начинается общий deadline?**

До первого model call. Отдельные таймауты вложены в общий предел; ожидание одного шага уменьшает остаток следующего. При внешней отмене loop не возобновляется.

**Что происходит после повторного call ID?**

Уникальность проверяется в пакете и для предыдущих шагов до работы. Loop завершает эту ветку явно. Для внешних эффектов долговременная идемпотентность проектируется отдельно.

## Критерии хорошего ответа

Разведи deadline, per-tool timeout, step/call/byte limits. Покажи тест с event и последовательность, где отказ приходится до исполнения.

## Задача

Реализуй `async run_loop(model, execute, budget=Budget(), *, clock=...)`. `model(history)` получает tuple observations; `execute(call)` возвращает строку. Успех — `completed` с непустым текстом. Пустой финал — `empty_final`, отказ или неполный ответ — `refusal`/`incomplete`, неверный Reply — `invalid_reply`. Проверь пустые/повторные IDs между шагами и внутри пакета до исполнения; результат `duplicate_or_missing_id`. Пакет сверх лимита даёт `call_limit`. Предельные шаги дают `step_limit`, выход за накопленный UTF-8 лимит — `output_limit`. Ошибка tool превращается в строку `tool_error` с ID, per-tool timeout — `tool_timeout`, ошибка модели — `provider_error`. Общий timeout — `timeout`. Пробрасывай cancellation. `Outcome` содержит фактически начатые steps/calls и только принятые observations. Пример Run делает два вызова в первом шаге и получает `completed` на втором. Check подменяет ответы, время и порядок событий.

## Шпаргалка

### Краткий конспект

Один turn может вызвать несколько tools. Будущий пакет проверяем целиком до работы, output budget проверяем по сериализованным байтам. Deadline один на весь запрос, а tool может иметь более короткий timeout. Отмена должна дойти до caller. Call IDs уникальны в пределах текущей операции и связывают observations с исполнением.

1. Почему свободный step не даёт право вызвать любой пакет?
2. Можно ли считать внешний effect отсутствующим после timeout?
3. Как остановить зависший await?

<details>
<summary>Сверить конспект</summary>

Steps и calls — разные лимиты. Timeout оставляет исход неопределённым, поэтому политика эффекта нужна отдельно. Лимит часов проверяет admission, `asyncio.timeout` прерывает await, `finally` завершает cleanup.
</details>
