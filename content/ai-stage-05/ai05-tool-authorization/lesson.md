# Авторизация инструментов backend

Два клиента знают адрес страницы бронирования и могут догадаться о соседнем числовом ID. Возможность угадать ID ничего не говорит о праве читать запись. Это свойство должно быть одинаковым для обычного HTTP endpoint и для tool, который вызывает модель.

## Учебные цели

- Разделить аутентификацию, scope и права на объект.
- Проверить владельца и tenant до чтения бизнес-данных.
- Оставить наблюдаемые доказательства нуля запрещённых чтений и записей.

## Теория

**Аутентификация** отвечает на вопрос, кто вызвал endpoint. **Авторизация** определяет, какие действия этому субъекту разрешены. Trusted principal — созданное приложением удостоверенное описание субъекта, tenant и прав. Tenant — отдельная область данных одной организации. Даже одинаковые user ID в двух tenant обозначают разные субъекты.

RBAC назначает разрешения через роль. Scope передаёт область действия, например `booking:read`. Право читать брони вообще ещё не даёт право на конкретную бронь. Объектная проверка сверяет tenant, владельца и текущую политику. Отсутствие проверки называется Broken Object Level Authorization, BOLA; IDOR описывает распространённую форму с подстановкой ID объекта. Аргументы модели содержат только `booking_id`; неизвестные ключи отклоняет strict DTO.

Иногда авторизация требует прочитать метаданные. В этом упражнении `policy(id)` получает только tenant, владельца и revoked-флаг. `read(id)` читает уже бизнес-запись. Для чужой, отозванной или отсутствующей брони возвращается один безопасный статус `not_found`. Это не обещание одинакового времени ответа, но клиент не видит явной разницы в contract. В production зазор между отдельной проверкой и protected read закроет одна атомарная операция репозитория, например SQL с фильтром по актуальным правам в том же запросе.

## Модель понимания

Для ID 91 сначала проверь principal и scope → валидацию DTO → политику объекта → только затем бизнес-данные. Синтетический spy ведёт два разных списка. Строка `policy_ids=[91]` допустима на отказе; `protected_reads=[91]` на отказе означает дефект.

## Что нужно знать на Junior

Отдельный UUID уменьшает угадываемость, но не даёт прав. Отзыв разрешения проверяется при чтении. Минимизируй выход: город и ID полезны пользователю, внутренняя заметка и чужие сведения остаются внутри.

## Примеры кода

```python
from collections import Counter

grants = {19: ("org-a", "lee"), 27: ("org-b", "lee")}
events = Counter()
caller = ("org-a", "lee")
for key in (27, 19, 905):
    events["policy"] += 1
    if grants.get(key) == caller:
        events["read"] += 1
print(events["policy"], events["read"])
assert tuple(events.values()) == (3, 1)
```

Вывод `3 1`. Чужая запись с тем же именем пользователя и отсутствующая запись прошли только этап чтения policy.

## Типичные ошибки

- Брать tenant, роль или user ID из вызова модели.
- Читать полную запись, чтобы потом решить, можно ли её показать.
- Возвращать разные публичные результаты для чужой и отсутствующей записи.
- Считать, что одно разрешение сохраняется после отзыва.

## Вопросы с собеседований

1. Чем отличаются аутентификация и объектная авторизация?
2. Почему spy различает policy lookup и protected read?

## Хорошие ответы

**Чем отличаются аутентификация и объектная авторизация?**

Токен или серверная сессия позволяет установить principal. Политика проверяет, разрешена ли этому principal конкретная операция над конкретной записью в нужном tenant. Правила исполняются перед доступом к данным.

**Почему spy различает policy lookup и protected read?**

Метаданные могут понадобиться для решения, но условия доступа не должны вынуждать раскрыть бизнес-данные. Сигналы фиксируются отдельно, иначе тест пропустит запретное чтение, скрытое за правильным ответом 404.

## Критерии хорошего ответа

Покажи trusted principal, scope и ownership как разные проверки, назови защиту от race и наблюдаемый критерий отсутствия доступа.

## Задача

Реализуй `async get_my_booking(arguments, principal, store) -> Outcome`. `None` principal даёт `unauthenticated`, отсутствие `booking:read` — `forbidden`. До lookup проверяй `BookingArgs`, ошибка — `invalid_arguments`. Через `await store.policy(id)` проверяй tenant/owner/revoked; чужой, отозванный или отсутствующий ресурс даёт одинаковое `not_found`. Только после разрешения вызови `await store.read(id)`. Если запись отсутствует, `not_found`; успех содержит ровно `booking_id` и `city`. Ни один путь не пишет в booking store. Пример Run для ID 42 показывает `ok` владельцу и `not_found` соседу, всего одно protected read. Check использует другие IDs, два tenant, параллельные обращения и попытки добавить role/identity.

## Шпаргалка

### Краткий конспект

Principal устанавливает приложение, scope ограничивает операцию, tenant и ownership ограничивают запись. Проверка прав выполняется перед чтением. Политика и бизнес-данные раздельны, публичный отказ совместим с отсутствующей записью. В production границу check/read защищает атомарный запрос с актуальным предикатом.
