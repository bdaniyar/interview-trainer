# Недоверенные данные и предложение отмены

В заметке к брони хранится текст, похожий на просьбу отменить бронь. Заметку мог написать сторонний источник. Даже если модель воспримет её как указание, сервер применит те же правила, что при прямой просьбе пользователя.

## Учебные цели

- Различить прямую и косвенную prompt injection.
- Реализовать безопасное чтение и предложение отмены с точными аргументами.
- Проверить отсутствие эффекта и утечки на наблюдаемом поведении.

## Теория

**Prompt injection** возникает, когда недоверенный текст влияет на инструкции модели. При прямой инъекции текст приходит в запросе; при косвенной он находится в документе или результате инструмента. Шаблон может обозначить источники данных, но модель не становится проверяющей стороной. Безопасность строится на том, что приложение допускает только известные операции и проверяет trusted caller и объект перед чтением.

**Proposal** — ожидающее рассмотрения предложение. Его идентификатор создаёт сервер. Оно содержит владельца, действие, ID ресурса, точные валидированные аргументы и safe explanation. Текст `"approved": true` в предложении модели не является согласием. Вариант написанного убеждения и вариант подставленного tool name не должны влиять на разрешения. `propose_cancel` не вызывает ни одной booking mutation. Одобрение человеком и выполнение synthetic write появятся в P7: решение о действии должно быть связано с actor, ресурсом, args, сроком и проверкой отзыва.

Для аудита пригодны request/call IDs, safe outcome и категория операции. Частные заметки или provider errors не должны попадать в логи. Даже алфавитно безопасная строка ID иногда содержит секрет, поэтому P3 использует публичные correlation aliases отдельно от wire call IDs. DTO выходов выбирает минимальные поля, а лимит защищает от случайного слишком большого результата.

## Модель понимания

Model text → имя из allowlist → strict args → trusted scope → проверка объекта → чтение или создание pending proposal. Ветка для записи отсутствует. Контрольная ошибка, добавляющая write в этот путь, должна обнаруживаться счётчиком вызовов, даже если внешний HTTP ответ выглядит правильно.

## Что нужно знать на Junior

Тестируй поведение, а не наличие слова «опасно» в промпте. Можно проверить одно и то же запрещённое действие с разными текстами, затем подтвердить результат на фактических вызовах репозитория.

## Примеры кода

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Decision:
    status: str
    effect_count: int

def status_for(requested):
    if requested == "request_review":
        return Decision("pending", 0)
    return Decision("unsupported", 0)

for name in ("request_review", "apply_change"):
    print(status_for(name))
```

Первый вывод содержит `pending`, второй `unsupported`. В обоих случаях эффектов ноль. В проекте дополнительно проверяется право на конкретную бронь, а proposal привязывается к точным аргументам.

## Типичные ошибки

- Выдавать ложному approval полномочия из содержимого заметки.
- Разрешать произвольный URL или команду через универсальный tool.
- Брать actor и действие из model arguments.
- Отправлять сырую ошибку в ответ или trace.

## Вопросы с собеседований

1. Чем прямой prompt injection отличается от косвенного?
2. Какие поля привязывают предложение к операции?

## Хорошие ответы

**Чем прямой prompt injection отличается от косвенного?**

Источником прямой инъекции служит пользовательский ввод, источником косвенной — данные из документа или инструмента. Тесты моделируют оба пути до границы исполнения и проверяют отсутствие запрещённых reads/writes.

**Какие поля привязывают предложение к операции?**

Серверный ID, tenant и субъект, действие, resource ID и точные аргументы. Предложение ожидает рассмотрения. Когда появится approval, нужны свежая проверка прав, срок и защита от повторного выполнения.

## Критерии хорошего ответа

Объясни, как вызов модели без доверия достигает gate, и назови негативный тест, у которого именно эффект ломает проверку.

## Задача

Реализуй `async dispatch(name, arguments, principal, store, new_id) -> Outcome`. Только `get_booking` и `propose_cancel` разрешены. Используй scope `booking:read` или `booking:propose`. Неизвестное имя даёт `unknown_tool`, отсутствие scope — `forbidden`. Валидация JSON до 512 байт с `Args` даёт `invalid_arguments` на ошибке. Через `store.ownership(id)` сравни tenant и subject; чужой или отсутствующий объект даёт `not_found`. Чтение возвращает ровно city и ID, при превышении 512 байт UTF-8 сериализованного результата — `output_limit`. Без записи сформируй `Proposal` со статусом `pending`, `action="cancel_booking"`, ID от `new_id()`, trusted owner и неизменными `arguments=(("booking_id", id),)`. Ответ имеет `status="pending"`. Подробности внутренних ошибок заменяются `tool_error`; отмена проходит дальше. Пример Run для ID 44 печатает безопасное чтение, предложение и запрет прямой отмены, затем `booking writes: 0`. Check меняет данные, actor, неподдерживаемые инструменты и признаки поддельного approval.

## Шпаргалка

### Краткий конспект

Данные могут предложить опасное действие, но не могут добавить callable, изменить caller или выдать scope. Proposal — typed object, созданный сервером со статусом pending. Безопасность проверяется по наблюдаемым чтениям, записям и минимальному выводу. Ошибка транспорта и approval — разные события.
