# Read-only Booking Assistant

## Учебные цели

- Проследить путь запроса от FastAPI до типизированного ответа и найти владельца каждой проверки.
- Собрать диалог из двух ответов scripted provider и реальных чтений через внедрённый репозиторий.
- Проверить, что смена пользователя, отказ tool или изменение порядка результатов не нарушают контракт.

## Теория

В P3 пользователь сначала создаёт диалог, затем отправляет его ID и сообщение в `POST /assistant/chat`. FastAPI через dependency выбирает учебного пользователя из серверной таблицы. Подлинность заголовка в реальном приложении проверяла бы система аутентификации. ID диалога только указывает запись. Репозиторий истории сверяет владельца, а context builder сохраняет policy, текущее сообщение и место под вывод. Starter этой лаборатории начинается после HTTP и проверки диалога. Он получает доверенный `Principal` явно, как сервис FastAPI получает его через dependency.

### Последовательность запроса

```text
Client → FastAPI               POST /assistant/chat + conversation_id
FastAPI → Auth dependency     trusted principal
FastAPI → History service      claim conversation for tenant + subject
History → Context builder      policy + complete recent turns + current input
Assistant → Model              application context; maximum steps enforced here
Model → Assistant              get_booking(call_x, {"booking_id":42})
Assistant → Policy index       verify owner and permission for booking 42
Assistant → Booking repository load booking 42
Assistant → Model              tool result for call_x (safe projection)
Model → Assistant              final text, refusal or incomplete response
Assistant → Client             typed response and redacted trace
```

### Границы доверия

```text
Недоверенный ввод                       Приложение                           Данные
HTTP body ────────────→ FastAPI ───────→ principal ← серверный реестр
model function call ──→ DTO/allowlist ─→ owner и scope ────────────────────→ booking read
tool result ──────────→ минимизация ───→ новое обращение к модели
provider error ───────→ код ошибки ────→ response / redacted trace
```

Данные от модели проходят обе проверки. Даже строгий `booking_id: int` ничего не говорит о праве чтения. Данные из репозитория тоже могут содержать инструкцию, например в поле заметки. Модель видит только разрешённую проекцию. При отказе второго model call уже выполненное чтение не повторяется автоматически.

## Модель понимания

Сравните с FastAPI endpoint для заказа. DTO отвечает «правильно ли оформлен запрос?», policy — «может ли этот клиент видеть заказ?», repository — «какие данные нужно прочитать?». Для tool шаги те же. Модель добавляет один источник запросов и может попросить несколько независимых чтений за раз. Если бронь B вернулась до A, приложение всё равно связывает каждый результат с ID исходного вызова.

P3 отвечает кодом 404 для чужого или отсутствующего диалога. Недоступная бронь внутри разрешённого диалога даёт наблюдение `unavailable`: остальные независимые вызовы могут завершиться, а модель сформулирует ответ. Ошибка провайдера сама по себе не делает результат `completed`.

## Что нужно знать на Junior

- `Request ID` помогает искать события HTTP-запроса. `Call ID` связывает два сообщения tool protocol. В trace P3 используются серверные алиасы, чтобы не переносить произвольный текст из provider ID.
- Общий timeout охватывает первый запрос, чтение и продолжение. У чтения может быть собственный более короткий timeout. Отмену должен наблюдать ожидающий I/O.
- Точный ответ на вопрос «сработала ли отмена?» даёт доменный статус. `pending` у предложения означает ожидание, при этом запись о брони не меняется.
- В P3 историю хранит память одного процесса. При рестарте записи исчезают, а одновременный запрос к тому же диалогу получает явный конфликт.

## Примеры кода

Упрощённая трассировка для двух независимых чтений. Ожидаемый порядок исходных tool calls известен, но условия возвращают результаты в противоположном порядке.

```python
calls = ["lookup-a", "lookup-b"]
completed = [("lookup-b", "недоступно"), ("lookup-a", "подтверждено")]
by_id = dict(completed)
for step, key in enumerate(calls, 1):
    print(f"call-{step}", by_id[key])
```

Первая строка — `call-1 подтверждено`, вторая — `call-2 недоступно`. В приложении проверяют уникальность ID до исполнения и передают провайдеру исходные значения, а в trace пишут алиасы.

Пример trace для успешного поиска. В ответе модели есть номер разрешённой брони, но в трассе остаются тип события, псевдоним, статус и расход бюджета. `18` и `23` ниже иллюстрируют задержку в миллисекундах.

```text
req=demo step=1 model  outcome=tools     calls=0 elapsed_ms=6
req=demo step=1 tool   name=get_booking alias=call-1 outcome=ok calls=1 elapsed_ms=18
req=demo step=2 model  outcome=final     calls=1 elapsed_ms=23
req=demo step=2 terminal outcome=completed calls=1 elapsed_ms=23
```

## Типичные ошибки

- Передать модели токен авторизации или позволить ей прислать `user_id`. Используйте principal из зависимости.
- Прочитать запись, а затем проверить владельца. Сначала нужен индекс разрешений, потом чтение содержимого.
- Собрать индекс по `enumerate(completed)`. При изменении порядка чужое наблюдение попадёт в другой call.
- Записать полный prompt или exception в trace. Достаточно безопасных категорий и длительности.
- Продолжать после любого ответа модели. Refusal и incomplete завершают работу и имеют разные коды.

## Вопросы с собеседований

1. Зачем в одном запросе могут понадобиться request ID и wire call ID?
2. Что доказывает успешный сценарий со scripted provider?
3. Где проверяются права на диалог и на конкретную бронь?

## Хорошие ответы

Почему два ID? Серверный correlation ID относится ко всему запросу. Wire call ID относится к одному вызову, поэтому значение из исходного tool call переносится в наблюдение. Публичный trace использует отдельный безопасный алиас.

Когда тест с мок-моделью проходит, что проверено? Контракт приложения. Сценарий воспроизводит команды, наблюдает вызовы репозитория и причину завершения. Он не измеряет способность реальной модели понять формулировку.

Где проверяются права? Хранилище истории сравнивает владельца диалога с principal. Tool заново проверяет конкретную запись по tenant и владельцу до чтения.

## Критерии хорошего ответа

- Покажите, где источник principal и где проверяется владелец ресурса.
- Приведите пример двух вызовов с обратным порядком завершения.
- Различите отсутствие записи, отказ в доступе и внутреннюю ошибку в публичном контракте.
- Назовите данные, доступные клиенту, провайдеру и trace.

## Задача

Реализуйте `async run_assistant(prompt: str, principal: Principal, provider: Provider, repository: Repository) -> Result` в `main.py`. DTO и интерфейсы в `contracts.py`, fixtures в `fixtures.py`.

1. Первый `provider.reply(prompt, ())` может вернуть финальный ответ или пачку до трёх вызовов. Пустая пачка, отсутствующий/повторный ID или аргументы не в виде `dict` дают `invalid_provider` до любого чтения. Пачка больше трёх даёт `call_budget`.
2. Разрешите `get_booking` только с одним положительным целым `booking_id` без bool. `list_my_bookings` принимает пустой объект и берёт ID через `repository.owned_ids(principal)`. Для каждого ID сначала проверяйте `owner_of`, затем читайте запись. Чужая либо отсутствующая запись даёт `unavailable`. Исключение репозитория даёт `tool_error`. Разрешённая проекция — кортеж пар `(id, status)`. Неизвестное имя даёт `unknown_tool`.
3. Независимые вызовы могут завершиться в любом порядке. Соберите результаты по ID и передайте их в порядке исходных вызовов в единственное продолжение `provider.reply(prompt, observations)`. При отмене активный I/O должен завершиться отменой.
4. Непустой финальный текст даёт `completed`. `refusal` и `incomplete` сохраняют причину без текста. Исключение провайдера даёт `provider_error`. Пустой текст или некорректное финальное сообщение даёт `invalid_provider`. Новая пачка после продолжения даёт `step_budget` без чтения.
5. Trace на каждый обработанный вызов — `Trace(step=1, tool, alias, outcome)` в исходном порядке, с алиасами `call-1`, `call-2` и так далее. Для неизвестного инструмента имя `unknown`.

Пример запуска demo после реализации — `completed Бронь 42: confirmed`. Check меняет ID, владельцев, порядок, поведение провайдера и содержимое репозитория. Проверяется наблюдаемая работа внедрённых зависимостей.

## Шпаргалка

### Краткий конспект

1. HTTP получает principal → история сверяет владельца → context builder сохраняет обязательные блоки.
2. Backend валидирует целую пачку → исполняет ограниченные чтения → связывает результат с wire ID.
3. Продолжение получает безопасную проекцию → возвращает typed terminal outcome.
4. Trace содержит серверные алиасы и категории. Тест меняет владельца, порядок, поведение инструмента и результат провайдера.
5. P3 повторяет путь через FastAPI и добавляет бюджеты, историю и воспроизводимую оценку. Например, только владелец брони 42 получает `call-1 · get_booking · ok`. Для другого tenant наблюдение будет `unavailable`, а число чтений останется нулевым.
