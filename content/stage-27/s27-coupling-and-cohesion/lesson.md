# Coupling and cohesion

## Суть

Coupling описывает, сколько чужих деталей нужно знать для изменения компонента. Cohesion описывает, насколько его части работают на одну ответственность. Цель — не максимальное число абстракций, а понятная область изменения.

## Учебные цели

Оценить область изменения при замене хранения или способа уведомления. Найти случайную зависимость от чужой schema и отличить полезную узкую абстракцию от дополнительной прослойки без ответственности.

## Теория

### Что это

Coupling описывает, сколько чужих деталей нужно знать для изменения компонента. Cohesion описывает, насколько его части работают на одну ответственность. Цель — не максимальное число абстракций, а понятная область изменения.

### Как работает

BookingService знает, что нужно записать booking intent, но не должен знать HTTP routing RabbitMQ или SQL schema чужой notification DB. BookingEvents — точка зависимости; adapter реализует выбранную инфраструктуру. Notification module сам хранит inbox и effect.

Слишком широкий generic repository или event object со всеми полями системы связывает модули сильнее, чем короткий явный use case. Слишком мелкие wrappers добавляют переходы без уменьшения знания. Измените один контракт и посмотрите, какие файлы и tests действительно потребовали правки.

Сетевой вызов не уменьшает coupling автоматически. Синхронная цепочка пяти сервисов может иметь больше runtime coupling по доступности, чем локальный вызов функции. Отдельно различайте coupling данных, compile-time imports, releases и времени выполнения.

### Важный нюанс / ограничение

Loose coupling не означает отсутствие dependencies. Важно, чтобы зависимость была явной, узкой и соответствовала нужному контракту отказов.

## Модель понимания

Проследите один booking от HTTP до durable state. Подпишите владельца данных и каждый COMMIT. На сетевой границе отдельно отметьте timeout, возможный повтор и наблюдаемое состояние receiver.

## Что нужно знать на Junior

### Обязательно

Cohesion оценивается общей причиной изменения компонента, coupling — знанием внешних деталей. Общая утилита или DTO тоже создаёт зависимость. Согласование поведения при отказе важнее формального совпадения сигнатуры.

## Типичные ошибки

Создать универсальный service для несвязанных операций — собрать разные причины изменения в одном месте. Разнести каждый метод в отдельный класс — увеличить навигацию без улучшения границ. Убрать импорт через HTTP, сохранив зависимость от чужой schema, — перенести сцепление в runtime.
