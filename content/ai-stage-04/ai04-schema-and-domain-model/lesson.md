# JSON Schema и правила поездки

Модель вернула аккуратный объект с датой выезда до въезда. JSON разобрался, схема совпала, а бронь создавать нельзя. Чтобы найти ошибку в правильном месте, разделим формат, доменное правило и проверку фактов.

## Учебные цели

- Различить JSON, JSON Schema и бизнес-валидацию.
- Объяснить required, nullable, strict type и вложенность.
- Реализовать строгий TripRequest без догадок.

## Теория

JSON описывает значения: объект, список, строка, число, bool и null. **JSON Schema** описывает допустимую форму. Объект имеет properties, required задаёт обязательные ключи. Nullable разрешает null в значении. Это отдельные свойства. Например, ключ city должен быть, но его значение может быть null. В Pydantic `city: str | None` без default требует ключ, а с `= None` разрешает отсутствовать.

Тип `int` с нестрогим переносом может принять строку «3» и привести её к числу. Для гостей нужен строго целый положительный int, bool также отклоняется. Граница для даты принимает ISO `YYYY-MM-DD` с годом и валидным календарём. Для полной доменной модели checkout должен быть позже checkin. Такое межполевое условие удобно проверить model_validator после разбора двух полей.

Вложенное поле trip позволяет добавить метаданные рядом с поездкой, сохранив контракт самой поездки. Во внешнем API поддержка JSON Schema ограничена. Например, строгие Structured Outputs требуют явного набора ключей и запрета дополнительных полей в объектах, а поддержка отдельных keywords зависит от схемы и модели. Для провайдера можно отправить ограниченную схему с city/date как nullable строки, а домен сам проверяет формат и порядок дат. Локально допустимы более сложные правила. Всегда отдельно проверь, что провайдер или модель поддерживает нужный schema subset.

Фактическая верность требует отдельного сравнения с запросом и разрешёнными данными. Если пассажир написал «Алматы» и модель вернула валидный TripRequest с городом «Астана», schema validator не имеет факта для сравнения. Оценивай это через тесты и отдельную бизнес-логику, если факт можно надёжно проверить.

## Модель понимания

Прочитай три слоя проверки. Синтаксис говорит, что это JSON. Schema читает тип и ключ. Domain проверяет строгий календарь и интервал. Затем факт сверяется с исходным текстом. Неполный структурированный результат может быть валидным и требовать уточнения.

## Что нужно знать на Junior

Не вводи текущий год как default. Для «10 декабря» неизвестность сохраняется, пока не введена явная политика reference date. Не принимай лишние ключи с данными истории или секретами.

## Примеры кода

```python
from pydantic import BaseModel, ConfigDict, StrictInt, ValidationError

class Party(BaseModel):
    model_config=ConfigDict(extra="forbid")
    size: StrictInt|None

assert Party.model_validate({"size":None}).size is None
for invalid in ({}, {"size":"2"}, {"size":2,"extra":1}):
    try:
        Party.model_validate(invalid)
    except ValidationError:
        continue
    raise AssertionError(invalid)
print(Party.model_json_schema()["required"])
```

Вывод `['size']`. Null допустим, а отсутствие ключа, строка и extra дают ошибку. Ограничения интервала здесь не показаны, поскольку Party описывает только один атрибут.

## Хорошие ответы

**Что значит обязательный nullable ключ?**

В provider-схеме удобно требовать одинаковый набор ключей, даже если значения неизвестны. Дай default, если пропуск тоже допустим.

**Где проверять порядок дат?**

Это отношение между полями. Типовой provider schema его не гарантирует. Схема видит форму, а не исходный текст.

## Критерии хорошего ответа

Назови точную причину отказа для строкового guests, пропущенного key и выходной даты раньше входной. Приведи контрпример валидного JSON с неверным городом.

## Задача

Реализуй Pydantic `TripRequest` с обязательными ключами `city`, `check_in`, `check_out`, `guests`. Их значения nullable. Непустой city после strip до 120 символов. Даты — date или строгая календарная ISO-строка, в результате date. datetime, число и форма без года запрещены. guests StrictInt больше нуля. Extra запрещены. Если обе даты известны, check_out строго позже. Пример `TripRequest.model_validate({"city":"Караганда","check_in":None,"check_out":None,"guests":2})` сохраняет обе даты неизвестными. Check использует другие города, leap year, равенство дат, строковые и логические значения.

## Шпаргалка

### Краткий конспект

Required управляет ключом, nullable — значением. Сначала parse и schema, после — доменный validator. `2028-02-29` валиден, у `2027-02-29` календарной даты нет. Отсутствующий год остаётся null при извлечении. Структура не доказывает факт.
