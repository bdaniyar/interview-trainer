# Воспроизводимая оценка и защита P2

Сервис сохраняет форму ответа после изменения промпта. В новой версии пустой город иногда становится «Алматы». Проверим изменения по отдельным метрикам и примем решение о выпуске.

## Учебные цели

- Повторить offline runner P2 с замороженным split.
- Посчитать diff из отчётов и найти новые случаи ошибок.
- Обосновать дальнейшую проверку и решение о rollout.

## Теория

**Regression** — измеряемое ухудшение ранее работавшего свойства. Форма может улучшаться, а угадывание города вырасти. Сначала сохрани dataset hash, версии модели, схемы и промпта. Затем запусти baseline и одну контролируемую замену. Сравни те же ID на dev. Holdout оценивает уже выбранную замену, его вывод не используют для подбора новых правил. В учебном отчёте обе версии вычислены на исходном frozen наборе.

В P2 настроенный scripted provider даёт стабильный ответ. Версия v2-regression вводит ложные defaults для неизвестного города и гостей. Это модель дефекта. Если schema validity не изменится, а unknown correctness снизится, проверка показывает, где первоначальный gate был слишком узок. Запиши минимум два ID и порядок применения исправления. После отказа от candidate проверь, что исходная версия всё ещё проходит HTTP и контрактные тесты.

При защите нарисуй последовательность DTO → prompt → adapter → wire parser → domain validation → API → evaluator. Объясни, где появляются refusal, incomplete и unknown. Покажи пример с датами без года и скажи, какая политика нужна до попытки разрешить их. Не выводи из фикстур точность живой модели, стоимость или безопасность всех входов. Rollout, поэтапный выпуск, требует независимой проверки на подходящих данных.

## Модель понимания

Хороший отчёт содержит входные версии, команды и raw counts. Сравни каждый знаменатель. Снижение 4/4 до 4/5 — другой набор возможностей, чем падение 4/4 до 3/4. Undefined отмечай null.

## Что нужно знать на Junior

Отклоняй candidate при регрессии критичного правила. В README покажи, как воспроизвести контрольный запуск и как вернуться к baseline. Reviewer отдельно читает обоснование.

## Примеры кода

```python
cases = {"a": [], "b": ["city"]}
candidate = {"a":["guests"], "b":["city"], "c":[]}
new = sorted(key for key in candidate if candidate[key] and not cases.get(key))
assert new==["a"]
assert "b" not in new
assert "c" not in new
print(new)
```

Вывод `['a']`. Новая проблема отличается от уже известной. Поддерживай одинаковые ID при сравнении отчётов.

## Типичные ошибки

- Переписывать holdout после ошибки.
- Объявлять static shape измерением фактов.
- Менять одновременно prompt, schema и fixtures.
- Убирать старые нарушения из отчёта.

## Вопросы с собеседований

1. Зачем сохранять hash данных?
2. Чем offline report полезен при rollout?

## Хорошие ответы

**Зачем сохранять hash данных?**

Hash фиксирует тексты, разметку и разбиение. Если он изменился, разница в метрике может быть вызвана новыми данными. Версии модели, промпта и схемы позволяют связать разницу с тем компонентом, который намеренно изменили.

**Чем offline report полезен при rollout?**

Offline отчёт помогает быстро выявить нарушения контракта. В нашем опыте схема проходит с прежней долей, а сохранение unknown ухудшилось. Поэтому candidate останавливается до оценки на живом провайдере. После исправления можно повторить тот же сценарий и отдельно оценить модель на подходящих данных.

## Критерии хорошего ответа

Защити выбор baseline, объясни 2–3 строки diff, покажи связанный invariant и сформулируй ограничение офлайн-оценки. Это ручная проверка.

## Задача

Открой `projects/trip_extraction/README.md`. Выполни `python evaluate.py --output /tmp/p2-report.json`: сравнивает baseline и специально изменённый prompt. Пример контрольного изменения — добавить к policy defaults для пропущенного города и гостей, сохранив исходную схему и fixtures. Сначала изучи dev, затем открой holdout. Не меняй frozen файлы. Запусти тесты с исходной версией API и запиши решение. В workspace реализуй `compare(before, after)` для отчётов одной партиции. Верни `{"delta": {metric: rate_after - rate_before или None}, "new_errors": sorted_ids}`, где new_errors — ID с ошибками после, отсутствовавшими или пустыми до. None в любом rate даёт None. Несовпадение набора ID или metric keys вызывает ValueError. Официальный report CLI и Run дают примеры для самопроверки.

## Шпаргалка

### Краткий конспект

Фиксируй dataset и immutable версии. Сначала baseline, затем одно изменение, затем counts и ID. Пример 8/8→5/8 работает при неизменной форме. Сохрани holdout, отклоняй candidate при потере unknown и объясняй границы.

1. Что требует повторяемость?
2. Что такое новый сбой?
3. Что доказывает fake?
