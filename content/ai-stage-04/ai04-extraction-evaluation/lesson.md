# Оценка извлечения по полям и исходам

Одна версия промпта улучшила вид ответов и стала вписывать город по умолчанию. Тест Pydantic по-прежнему зелёный. В этом уроке построим отчёт, где угадывание неизвестного поля видно сразу.

## Учебные цели

- Посчитать независимые метрики с numerators и denominators.
- Сохранить ошибку каждого случая и разделение dev/holdout.
- Найти регрессию при неизменной schema validity.

## Теория

**Evaluation dataset** — набор входов с ожидаемыми исходами и полями. Development set помогает менять правила и отлаживать. Holdout откладывается для отдельной оценки: после просмотра ошибок из него не составляют few-shot и не подгоняют пороги. Если требуется новая итерация, сохраняют историю и планируют независимый набор.

Для каждого случая известны ожидаемый status и trip либо отсутствие trip. Метрики отвечают на разные вопросы. Schema validity проверяет форму среди ответов с шансом получить структуру. В отчёте её знаменатель — результаты с наблюдаемым признаком schema_valid. Этим не скрываем refusal: считаем их отдельным счётчиком. Domain validity считает долю безопасных бизнес-значений среди тех, у кого shape разобран. Сравнивай и знаменатели: переход многих ответов в incomplete может оставить высокий schema ratio на малой подвыборке.

**Field accuracy** считает совпадения из всех ожидаемых известных полей. Обязательные для извлечения данные теряются при отказе, поэтому знаменатель известного поля сохраняется. **Missing-field correctness** считает совпадения null на местах, где ожидается неизвестность. Отсутствие всего объекта не равно валидному null. **Exact match** требует совпадения всех полей и ожидаемого статуса. Для refusal отдельно считаем, выполнен ли ожидаемый отказ без payload. Outcome accuracy сравнивает status у каждого случая. Ложный отказ обнаруживается здесь даже вне refusal-набора.

Представь два валидных ответа на «Алматы, число гостей ещё не знаю» и «Осло, трое». Первый добавил 2 гостей, второй вернул «Берген, трое». Для двух полей на запрос schema=2/2, известные поля=2/3 (Алматы и трое; Берген неверен), неизвестные=0/1, exact match=0/2. При нуле наблюдений доля null. Она не означает провал или успех.

**Per-case errors** показывают, какие ID и поля изменились. Сравнение baseline и candidate делают на одной версии данных. Складывать качество схемы и релевантность в усреднённую строку опасно: неизвестные поля, отказы и ошибки городов имеют разные последствия.

## Модель понимания

Точность одной версии не объясняет причину изменений. Сначала сравни количественные ошибки, затем по ID прочитай, какая операция перешла из частичного ответа в полный. Отдельно проверь, не изменилась выборка допустимых полей.

## Что нужно знать на Junior

Для реальных поездок даты приводят к календарному формату только при известных годе, месяце и дне. Выбирай заранее нормализацию города и словарь псевдонимов. Здесь синтетический equality точный, поэтому aliases должны обсуждаться отдельно.

## Примеры кода

```python
known = [("Алматы","Алматы"),("Осло","Берген"),(3,3)]
unknown = [(None,2)]
accuracy = sum(a==b for a,b in known), len(known)
null_accuracy = sum(a==b for a,b in unknown), len(unknown)
assert accuracy==(2,3) and null_accuracy==(0,1)
assert (sum([])/len([]) if [] else None) is None
print(accuracy,null_accuracy)
```

Вывод `(2, 3) (0, 1)`. Известные сведения и неизвестность оцениваются раздельно. В учебном наборе достаточно субсчётчиков, статистические выводы о модели требуют более широких данных.

## Типичные ошибки

- Переносить holdout во few-shot.
- Заменять пустые метрики 100%.
- Учитывать только ответы, где заполнены все поля.
- Считать подходящий JSON доказательством фактов.

## Вопросы с собеседований

1. Зачем у метрики знаменатель?
2. Где видно подмену города?

## Хорошие ответы

**Зачем у метрики знаменатель?**

Один верный случай из одного и сто из ста дают одинаковую долю с разной опорой. Например, один правильно обработанный отказ подтверждает обработку конкретного отказа. Если ожидаемых отказов вообще нет, показатель равен `null`, потому что проверить это свойство на данной выборке невозможно.

**Где видно подмену города?**

Схема принимает любое допустимое название города. Если эталон содержит Осло, а результат содержит Берген, поле `city` снижает точность известных фактов и exact match. Если город по эталону неизвестен, придуманное значение снижает unknown correctness. В обоих случаях ID остаётся в списке ошибок для разбора.

## Критерии хорошего ответа

Перечисли каждую возможность подсчёта и покажи одно различие между schema, exact и unknown. Решение о качестве объясни на ID кейса.

## Задача

Реализуй `score(cases, outputs)` для одной партиции. Case имеет id, status и trip (словарь четырёх полей или None). Outputs — ID→словарь со status, trip и флагами schema_valid/domain_valid (True/False/None). Верни `{"metrics": {name: {"passed": n, "total": d, "rate": n/d или None}}, "errors": {id: [ярлыки]}}`. Имена метрик в fixtures. Schema/domain считаются на bool-флагах. Поля считаются на всех ожидаемых trip, даже если actual отсутствует; одинаковый None засчитывается только при присутствующем ключе. Exact match также требует status. Refusal handling учитывает ожидаемые отказы и отсутствие payload. Outcome accuracy — все случаи. В errors сначала status, затем имена четырёх полей в порядке FIELDS; при неожиданном trip для expected=None используем refusal_payload или unexpected_payload. Дубли ID дают ValueError. Например, пустой набор возвращает для каждой rate=None. Run сравнивает RU/EN dataset 12 dev + 8 holdout. Check использует другую разметку.

## Шпаргалка

### Краткий конспект

Schema показывает форму, domain — допустимость значений, field accuracy — известные факты, unknown correctness — сохранение пропусков, exact — совпадение всей записи. Отказ — измеряемый исход. Для n=0 доля null. Dev и holdout считаются раздельно.

1. Может ли schema вырасти при потере качества?
2. Как посчитать пропущенный trip?
3. Что делать с holdout после отчёта?
