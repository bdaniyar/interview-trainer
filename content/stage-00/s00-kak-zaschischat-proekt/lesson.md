# Как защищать проект

> [!IMPORTANT]
> **P0 · вероятность на интервью: very_high · 12 минут.** Interview foundation; приоритет подтверждён целью Junior screening.

## Learning objectives

После урока ты сможешь:

- объяснить `Как защищать проект` своими словами и связать с backend-сценарием;
- распознать типичную ошибку и предложить проверяемое исправление.

## Theory

Собеседование проверяет не объём терминов, а способность построить точное объяснение и применить его к сценарию.

В теме **Как защищать проект** важно уверенно объяснять следующие части:

### Как защищать проект

Зафиксируй, какую способность оценивает пункт `Как защищать проект`, и подготовь короткое доказательство из своего кода вместо перечисления терминов.

## Mental model

Сначала классифицируй вопрос, затем дай определение, механизм, минимальный пример и ограничение.

Проверь модель вопросами: кто владеет состоянием, где проходит граница операции, что увидит вызывающий код и как выглядит безопасный отказ.

## Code examples

### Как защищать проект: отдельный пример

```text
Проблема: live-события между API-инстансами.
Моё решение: WebSocket + Redis Pub/Sub.
Граница: PostgreSQL хранит durable history.
Проверка: reconnect читает пропущенные события из БД.
```

Защита проекта связывает конкретное решение с ограничением и способом проверки.

## Common mistakes

**Ошибка:** Перечислять технологии без связи с решённой проблемой.

**Симптом:** код проходит простой happy path, но ломается при повторном вызове, конкурентном запросе, ошибке зависимости или изменении данных.

**Причина:** механизм и границы ответственности не были проговорены до реализации.

**Исправление:** зафиксируй контракт, сделай state/transaction boundary явной и добавь тест на failure path.

## Interview questions

1. Объясни **Как защищать проект** по схеме «определение → механизм → пример → ограничение».
2. Сценарий: Сформулируй ответ как определение → механизм → пример → trade-off. Какие уточнения ты задашь и как проверишь решение?
3. Какой слабый ответ по этой теме создаст риск в первой backend-задаче?

## Expected answer rubric

### Must mention

- Как защищать проект
- Сначала классифицируй вопрос, затем дай определение, механизм, минимальный пример и ограничение.

### Good additions

- назвать конкретный trade-off, а не только API;
- привести короткий пример из FastAPI/PostgreSQL/Redis, когда он действительно уместен;
- обозначить границу Junior: что нужно проверить в документации или измерить.

### Common wrong answers

- Перечислять технологии без связи с решённой проблемой.
- ответ из одного определения без механизма и failure mode.

### Follow-up

- Как изменится решение при повторном запросе, ошибке dependency или двух одновременных операциях?
- Какой unit/integration test подтвердит ключевой контракт?

## Задача

Разбери backend-сценарий: **Сформулируй ответ как определение → механизм → пример → trade-off.**

Запиши решение в формате: assumptions → mechanism → edge cases → test/verification. Для этого урока автоматическая coding-проверка не нужна; ответ сверяется с rubric interview-вопроса.

## Cheat sheet

Перед собеседованием запомни:

- дай точное определение **Как защищать проект**;
- объясни механизм, а не только синтаксис;
- назови один realistic backend example;
- проговори failure mode и trade-off;
- заверши ответ способом проверки: test, constraint, log или metric.
