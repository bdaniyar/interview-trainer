# AI, ML, Deep Learning и работа AI Engineer

Сервис бронирований получает пять разных запросов. Одному клиенту нужна сумма к оплате, другому — действующая инструкция, третьему — черновик письма. В каждом случае успех определяется по-разному. Прежде чем выбирать модель, определи, какой результат можно проверить.

## Учебные цели

- Различить AI, машинное обучение, глубокое обучение и генерацию по механизму.
- Найти в запросе границу между backend-правилом, поиском и моделью.
- Объяснить, какие части системы обычно поддерживают AI Application Engineer, ML Engineer и Data Scientist.

## Теория

**Artificial Intelligence (AI)** — широкая область систем, выполняющих задачи, которые связывают с распознаванием, планированием, рассуждением и другими способностями. В AI есть системы на правилах и поиске, а также обучаемые системы. У этого термина нет единственной границы, по которой можно надёжно классифицировать любой продукт.

**Machine Learning (ML)** — подход, при котором поведение части системы получают из данных. Например, антиспаму показывают исторические сообщения с отметками «спам» и «обычное». Значение этих отметок задают люди или уже известные исходы. Во время **training** алгоритм подбирает параметры модели так, чтобы уменьшить ошибку на примерах. Во время **inference** сервер применяет сохранённые параметры к новому сообщению. Обычный запрос inference сам по себе параметры не обновляет.

**Deep Learning** — область ML, где модели строятся из многих последовательных слоёв нейросети. Слой преобразует входные числа в новое представление. Одни модели классифицируют вход, другие создают выход. **Generative AI** описывает назначение модели — создавать текст, изображения или другие данные. Многие современные генеративные системы используют глубокие нейросети, но «глубокая» описывает устройство, а «генеративная» — назначение.

| Пример в сервисе | Что даёт результат | Как проверить |
| --- | --- | --- |
| Цена по тарифу и числу ночей | Заданная формула и правила округления | Сравнить с расчётом для известных тарифов |
| Сумма оплат за месяц | SQL над авторитетными записями | Сверить отбор, суммы и границы периода |
| Риск отмены брони | Обученная модель возвращает оценку | Сравнить прогноз с позднее известными исходами |
| Ссылка на действующую политику | Поиск, или retrieval, среди доступных документов | Проверить релевантность, версию и права |
| Вежливый черновик письма | Языковая модель, или LLM, создаёт последовательность текста | Проверить формат и утверждения по записи брони |

Детерминированное правило при одинаковых входах и конфигурации даёт одинаковый ответ. Модель тоже может вычисляться детерминированно. Смысл различия в том, **откуда берётся поведение** и **какими доказательствами мы его проверяем**. Например, порог 0,8 для карантина — кодовая политика. Оценка 0,83 получена моделью. Оба значения нужны, но точность порога в тесте не доказывает качество модели.

## Модель понимания

В письме об отмене раздели три операции. SQL читает подтверждённую дату и сумму. Обычный Python проверяет роль и решает, можно ли показывать сумму. Модель формирует черновик обращения на основе разрешённых данных. Ошибка в черновике не должна отменить бронь. Сохранение и отправка требуют собственных условий.

## Что нужно знать на Junior

- **AI Application Engineer** проектирует путь пользовательского запроса, включая проверку прав, адаптер модели, оценку качества, ограничения задержки и стоимости.
- **ML Engineer** часто отвечает за получение, обучение, выпуск и наблюдение модели и её данных.
- **Data Scientist** исследует данные, строит гипотезы, выбирает измерения и оценивает эксперименты.

В небольшой команде один человек может выполнять часть всех трёх ролей. По названию вакансии нельзя вывести точные обязанности. Смотри, за какой результат отвечает команда и как его проверяют.

## Примеры кода

У антиспама есть оценка от модели и правило приложения. Здесь оценки заданы вручную, так что код можно запустить без модели.

```python
def delivery_policy(spam_score: float, threshold: float) -> str:
    if not 0 <= spam_score <= 1 or not 0 <= threshold <= 1:
        raise ValueError("score and threshold must be in [0, 1]")
    return "quarantine" if spam_score >= threshold else "deliver"

assert delivery_policy(0.83, 0.80) == "quarantine"
assert delivery_policy(0.80, 0.80) == "quarantine"
assert delivery_policy(0.79, 0.80) == "deliver"
try:
    delivery_policy(1.4, 0.8)
except ValueError:
    pass
else:
    raise AssertionError("invalid score accepted")
print(delivery_policy(0.83, 0.80))
```

Вывод `quarantine` получается при превышении порога. Ровно на пороге правило также помещает сообщение в карантин. Чтобы обосновать порог, измерь долю пропущенного спама и обычных писем в карантине на новых размеченных примерах. Само число 0,83 ещё не подтверждает, что 83 из 100 похожих сообщений действительно спам.

## Типичные ошибки

- Просить LLM вычислить деньги из нескольких текстовых полей. Числа и правила расчёта известны заранее, поэтому их работу можно проверять точно.
- Отправлять все документы модели ради ссылки на один. Сначала выбери документы, которые пользователь вправе читать, и проверь, решает ли задачу выдача ссылки.
- Считать каждый новый запрос обучением. Сбор данных, изменение параметров и развёртывание новой версии требуют отдельных действий.
- Подменять проверку результата выбором должности. Даже если за сервис отвечает одна команда, этапы и владельцы данных должны быть явными.

## Хорошие ответы

Первый вопрос проверяет объяснение двух жизненных циклов. Порог доставки можно менять без обновления весов. Второй проверяет форму результата. Если нужен существующий документ, верни найденную ссылку после проверки прав. В третьем зафиксируй измерения на каждой границе. Сеть и приложение влияют на задержку, а качество предсказания проверяют на примерах с известным исходом. На практике обе команды участвуют в разборе сбоев.

## Критерии хорошего ответа

Назови источник данных, механизм результата, альтернативу и конкретное ограничение. Например, для черновика письма сравни проверяемый шаблон с моделью, которой нужны проверка фактов и предел стоимости. Автоматические проверки кода ниже сравнивают только выбор подхода. Качество аргумента оценивается по этой рубрике при самостоятельном разборе.

## Задача

Реализуй `choose_approach(requirements: set[str]) -> str` в `main.py`. Вход уже нормализован другим компонентом. Обрабатывай требования как флаги, а не как слова из пользовательского вопроса. Допустимы `fixed_rules`, `database`, `learned_prediction`, `existing_document`, `new_text`. Пустой ввод, неизвестный флаг и сочетание без единственного подходящего шага вызывают `ValueError`. Смешанные задачи с точным источником данных начинаются с поиска по этому источнику. Для конфликта обучения и генерации составь отдельный пайплайн вне этого router.

| Публичный сценарий | Флаги | Подход и объяснение |
| --- | --- | --- |
| Расчёт цены брони | `fixed_rules` | `python`, формула фиксирована |
| Классификация спама | `learned_prediction` | `ml`, прогноз опирается на размеченные примеры |
| Найти инструкцию даже для будущего пересказа | `existing_document`, `new_text` | `retrieval`, первым нужен авторизованный документ |
| Начать чат для свободного черновика | `new_text` | `llm`, требуется новый текст |
| Выбрать форму для модели риска отмены | `learned_prediction`, `fixed_rules` | `ml`, прогноз обучаемый, backend сохраняет свою политику |
| Сумма оплат по дате | `database`, `fixed_rules` | `sql`, сначала нужен расчёт по базе |

Приоритет первых шагов — `existing_document` или `database` перед остальными. Если нужны оба источника, сообщи о неоднозначности. Без источников `learned_prediction` и `new_text` тоже несовместимы. Иначе `fixed_rules` может сопровождать выбранный маршрут. `Run` запускает шесть открытых сценариев. Дополнительные авторские случаи проверяют новые сочетания, пустой ввод, конфликт и неизвестные значения. После выполнения открой эталон только для сравнения. Отметка завершения урока означает самопроверку, а оценка письменного рассуждения остаётся за тобой.

## Шпаргалка

### Краткий конспект

AI — область. ML получает поведение из данных. Deep Learning использует многослойные сети. Generative AI создаёт новые данные. Training подбирает параметры, inference применяет сохранённые параметры к входу.

Для запроса «есть ли действующая политика возврата» первым шагом обычно нужен поиск действующего документа. Для точной цены используй данные и правило. Для прогноза оцени модель на новых размеченных примерах. При генерации сохрани проверки прав и фактов в приложении.

1. Почему обычный запрос к модели не меняет её параметры?
2. Как изменится система при обновлении правила карантина?
3. Когда достаточно поисковой выдачи?

<details>
<summary>Сверить конспект</summary>

При inference используются уже сохранённые параметры. Новое правило меняет обработку оценки, не параметры модели. Поиск достаточен, когда цель — получить существующий разрешённый документ.
</details>
