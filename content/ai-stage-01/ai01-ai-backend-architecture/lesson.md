# Архитектура AI-приложения на знакомом backend

Клиент просит объяснить правило хранения учебных материалов. FastAPI принимает запрос и возвращает ответ. Между ними есть несколько решений: авторизация, подготовка данных, обращение к модели, интерпретация результата и, возможно, запись истории. Если разместить всё в одном обработчике, замена провайдера затронет каждое из этих решений.

## Учебные цели

- Проследить Client → FastAPI → Application Service → Provider Adapter → External Model.
- Назвать границу данных и ошибок на каждом шаге.
- Заменить fake-провайдера, сохранив прикладной контракт и обработку неуспеха.

## Теория

**Transport** получает HTTP-вход, проверяет DTO (форму передаваемых данных) и возвращает HTTP-ответ. DTO может гарантировать длину строки, но не разрешённость доступа к истории. **Application service**, прикладной сервис, реализует один сценарий пользователя. Он выбирает нужную историю, проверяет правила, вызывает провайдер и решает, записывать ли результат.

**Provider interface** — контракт, от которого зависит сценарий. В примере это асинхронный `generate(question)`. **Adapter** — реализация этой границы. Адаптер переводит документированные поля внешней модели в формат приложения и преобразует ожидаемые транспортные ошибки в типизированные ошибки. Если у нового провайдера другой JSON или другой тип исключения, меняется адаптер. Прикладной сервис по-прежнему работает с теми же `status`, `text` и `usage`.

**Usage** — сколько ресурсов сообщил провайдер, например токены входа и выхода. Токен — часть текста, которую модель обрабатывает как единицу. Отсутствующий usage значит «неизвестно». Он не должен превращаться в ноль. **Latency** — время ожидания результата, а полезность текста оценивается отдельно от неё. Успешный HTTP-ответ SDK может содержать статус `incomplete`, например при исчерпании бюджета вывода. Проект может показывать частичный ответ отдельно. Контракт упражнения возвращает текст только при завершении.

| Слой | Вход | Выход |
| --- | --- | --- |
| FastAPI | HTTP + идентичность пользователя | Проверенный DTO, затем HTTP-ошибка или ответ |
| Service | Сценарий, DTO и доверенный actor | Результат приложения |
| Adapter | Вопрос и конфигурация приложения | Типизированный outcome и usage |
| External model | Поля конкретного API | Ответ, события или ошибки этого API |
| Storage | Идентификатор беседы и версия | История, разрешения, запись результата |

Перед внешним ожиданием закрой транзакцию чтения. После ответа проверь, что допустима запись в нужную версию истории, и сохрани её короткой транзакцией. Так одно медленное ожидание не удерживает соединение. Оно всё равно занимает часть бюджета запроса. Локальный timeout ограничивает ожидание и позволяет transport выбрать 504. Отмена запроса должна пройти через service и adapter, чтобы последние могли выполнить cleanup.

## Модель понимания

Бизнес-код определяет смысл результата, SDK определяет форму передачи. HTTP 503 провайдера может стать `unavailable` домена и затем 503 ответа приложения. Пустой завершённый текст означает сломанный контракт, и приложение может вернуть иной статус. Внутреннее исключение и raw-ответ нельзя напрямую отдавать пользователю.

## Что нужно знать на Junior

Напиши контракт словами перед классами. Как читать `incomplete`? Кто сообщает timeout? Действительна ли запись при смене владельца? На эти вопросы нужны явные ответы. Общий клиент хранит соединения, терминируемые в lifecycle приложения. Данные пользователя передаются как аргументы одного вызова. Redis для кэша и Celery для фоновой обработки могут быть полезны позже. Они не меняют семантику внешнего результата и не гарантируют один вызов при повторном запуске.

## Примеры кода

Ниже адаптер читает искусственные записи двух транспортов. Он выбирает форму результата по типу реализации. Сценарий подсчёта длины никогда не видит provider JSON.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Summary:
    text: str

def from_a(wire: dict) -> Summary:
    return Summary(wire["message"]["text"])

def from_b(wire: dict) -> Summary:
    return Summary(wire["answer"])

def visible_length(summary: Summary) -> int:
    if not summary.text.strip():
        raise ValueError("empty answer")
    return len(summary.text)

assert visible_length(from_a({"message": {"text": "ночь"}})) == 4
assert visible_length(from_b({"answer": "ночь"})) == 4
for packet in ({"answer": "  "}, {"wrong_key": "данные"}):
    try:
        visible_length(from_b(packet))
    except (ValueError, KeyError):
        continue
    raise AssertionError("invalid packet accepted")
print("два адаптера, один прикладной контракт")
```

Общий результат виден по одной длине 4. Пустое содержимое и отсутствие ожидаемого поля дают разные причины отказа. В полноценном adapter исключения разбора преобразуются в один договорённый тип ошибки. Пример показывает границу, поэтому кода сети и повторов в нём нет.

## Типичные ошибки

- Разнести типы SDK по роутам и схеме SQLite. Замена транспорта повлечёт смену данных и бизнес-логики.
- Сдать на хранение partial output как окончательный ответ. Поток или завершённое HTTP-тело ещё нужно интерпретировать.
- Подставлять `0` вместо unknown usage. Так отчёт будет увереннее, чем исходные данные.
- Удерживать открытый запрос в БД во время inference. Проверь границу короткой транзакции наблюдаемым тестом.

## Хорошие ответы

Стабильный тип результата определяется приложением. Адаптер отвечает за перевод полей провайдера и его ошибок. Транзакция не должна занимать соединение на сетевом ожидании. Прикладной сервис принимает решение о сохранении partial output, а transport только передаёт формат и статус.

## Критерии хорошего ответа

Укажи владельца DTO, решения о правах, provider lifecycle и политики записи. Объясни, какое значение вернётся при incomplete и чем unknown usage отличается от нуля. Успешная подмена fake показывает совместимость контракта, а качество модели потребует отдельной оценки.

## Задача

Реализуй `async dispatch(provider, question, timeout=0.5) -> Generation`. `provider.generate(question)` возвращает общий `Generation` из `contracts.py` или бросает `ProviderUnavailable`. Возврати непустой завершённый текст и сохрани usage. Например, `Generation("completed", "Расписание готово", 11)` проходит неизменным. Для `incomplete` очисти текст и сохрани usage. Для пустого completed используй `incomplete`, для ProviderUnavailable — `unavailable`, по timeout — `timeout`. У timeout и unavailable usage неизвестен. Пропускай неожиданное исключение и внешнюю отмену.

Открой три публичных сценария через Run. После реализации подмени провайдер функцией с другой внутренней формой, но тем же `generate`. Авторские тесты проверяют замену, перенос поля usage, неуспех, timeout и разные одновременные входы. Сервису запрещено разбирать JSON конкретного провайдера.
