## Теория

### Что это

Это security boundary: сервер проверяет утверждение и безопасно отказывает, не доверяя клиентскому UI.

### Как работает

Назови asset, threat, trust boundary, на стороне сервера verification и безопасный failure result.

**verifier.** `verifier` закрывает конкретную threat на trust boundary; проверка выполняется на стороне сервера, а отказ не раскрывает лишних данных.

**challenge.** `challenge` закрывает конкретную threat на trust boundary; проверка выполняется на стороне сервера, а отказ не раскрывает лишних данных.

**code interception.** `code interception` закрывает конкретную threat на trust boundary; проверка выполняется на стороне сервера, а отказ не раскрывает лишних данных.

**`state`.** ``state`` закрывает конкретную threat на trust boundary; проверка выполняется на стороне сервера, а отказ не раскрывает лишних данных.

**redirect URI.** `redirect URI` закрывает конкретную threat на trust boundary; проверка выполняется на стороне сервера, а отказ не раскрывает лишних данных.

**PKCE не заменяет все меры защиты от CSRF.** PKCE отправляет challenge в authorize request и verifier при token exchange, поэтому перехваченного code недостаточно без verifier.


### Важный нюанс / ограничение

Граница Junior: уверенно объясняй `verifier` и `challenge` на одном проверяемом примере; редкие внутренние детали сначала ищи в официальной документации.

### Где используется в backend

В backend эта тема важна в том месте, где применяется `verifier`; проверяй именно наблюдаемый contract, а не название инструмента.
