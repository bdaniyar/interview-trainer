# FastAPI BackgroundTasks

## Суть

BackgroundTasks прикрепляет небольшую работу к ответу FastAPI. Клиент получает response body, затем приложение запускает callbacks в том же процессе. Это удобно для некритичного аудита; задача не превращается в запись надёжной очереди.

## Учебные цели

Добавить callback к FastAPI response, проверить вход до постановки callback и наблюдать порядок ASGI response body → sink. Отличать этот локальный механизм от отдельного процесса и сохраняемой очереди.

## Теория

### Что это

BackgroundTasks прикрепляет небольшую работу к ответу FastAPI. Клиент получает response body, затем приложение запускает callbacks в том же процессе. Это удобно для некритичного аудита; задача не превращается в запись надёжной очереди.

### Как работает

Объект BackgroundTasks передаётся dependency injection FastAPI. add_task сохраняет функцию и аргументы, а не вызывает её в endpoint. Starlette выполняет задачи после отправки ответа; sync callback использует thread pool, async callback должен сам избегать блокирующего кода. Исключение после response не может заменить уже отправленный status.

Callback должен сам создать необходимые ресурсы. Нельзя предполагать, что request-scoped DB session переживёт response и будет пригодна для фоновой работы; передавайте устойчивый ID и открывайте новую транзакцию. Несколько callbacks не являются параллельным durable workflow.

TestClient обычно ждёт окончания background task, поэтому время возврата client.post само по себе не доказывает порядок response/effect. Наш тест вызывает реальный ASGI app и записывает сообщения http.response.body перед вызовом sink.

### Важный нюанс / ограничение

При SIGKILL процесса callback может не выполниться. Здесь нет persistent retry, lease или восстановления. Для обязательной обработки используйте job/outbox; не переносите критичный business effect в память лишь ради быстрого HTTP.

## Что нужно знать на Junior

### Обязательно

add_task принимает функцию и аргументы. Sync и async callbacks исполняются по-разному, но принадлежат тому же приложению. Ресурсы запроса имеют ограниченный lifetime: для обращения к БД callback открывает собственную сессию по сохранённому ID.

## Примеры кода

```python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()
audit_events = []

@app.get("/ping")
def ping(tasks: BackgroundTasks):
    tasks.add_task(audit_events.append, "ping-seen")
    return {"status": "ok"}
```

GET /ping отдаёт JSON {"status":"ok"}; после response callback добавит строку в audit_events. Это только process-local список для примера, не хранилище аудита. В задаче другой endpoint и строгая валидация входа.

## Типичные ошибки

Вызвать функцию при add_task вместо передачи callback — выполнить работу прямо в endpoint. Использовать request-scoped session позже — зависеть от уже закрытого ресурса. Проверять момент отправки response только временем возврата TestClient.post — не учитывать, что TestClient дожидается background work.

## Задача

Реализуйте `make_app(sink) -> FastAPI` в main.py через обычные Python Run/Check. Создайте FastAPI-приложение функцией make_app(sink). POST /events принимает JSON с непустым строковым value длиной до 20, возвращает 202 и {"accepted": true}. После отправки тела ответа вызовите sink(value) ровно один раз. Неверный value даёт 422 и не вызывает sink. Это in-process работа, без гарантии пережить падение API.

Например, используйте входы из практики выше; граничные и неверные входы также проверяются. Starter намеренно не содержит готового алгоритма.

## Шпаргалка

Callback запускается после response и не меняет уже отправленный status. Передавайте устойчивые данные, открывайте свои ресурсы. Для обязательного выполнения после перезапуска нужна сохраняемая job или outbox. ASGI-тест порядка проверяет более точное свойство, чем длительность client.post.
