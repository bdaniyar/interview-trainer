# Retry and backoff

## Суть

Повтор помогает при временной ошибке: кратком разрыве соединения или перегрузке. Неверный payload или нарушенное бизнес-правило обычно требуют исправления, а не ещё тысячи одинаковых попыток.

## Теория

### Что это

Повтор помогает при временной ошибке: кратком разрыве соединения или перегрузке. Неверный payload или нарушенное бизнес-правило обычно требуют исправления, а не ещё тысячи одинаковых попыток.

### Как работает

Exponential backoff увеличивает паузу после каждой неудачи: base·2^(attempt−1), затем ограничивает cap. Бюджет попыток ограничивает суммарную работу. Jitter добавляет случайный разброс, чтобы много клиентов не повторяли запрос синхронно; в маленькой задаче jitter намеренно отсутствует для детерминированного контракта.

В durable проекте attempts увеличивается атомарно при claim, available_at определяет следующую допустимую попытку. Recoverable failure отпускает ownership и переводит job в queued с будущим временем. Падение процесса не вызывает fail: job остаётся running до истечения lease, а следующий claim использует новую generation. Исчерпанная expired job переходит в failed.

После timeout нельзя считать, что операция не выполнилась. Повтор с новым ключом может сделать второй платёж. Retry должен сохранять business idempotency key и учитывать общий deadline; много уровней retry могут перемножить нагрузку.

### Важный нюанс / ограничение

Backoff рассчитывает задержку, но не определяет, безопасно ли повторять действие. Эта функция не спит и не обращается к сети. В проекте retry schedule хранится в PostgreSQL, поэтому рестарт процесса не сбрасывает бюджет.

## Что нужно знать на Junior

### Обязательно

Номер попытки должен иметь однозначное начало; cap ограничивает задержку, max_attempts — работу. При timeout исход может быть неизвестен. Для повторного внешнего запроса сохраняются прежние operation key и общий deadline.

## Примеры кода

```python
delays = [min(12, 3 * 2 ** (attempt - 1)) for attempt in range(1, 5)]
assert delays == [3, 6, 12, 12]
```

Тип результата — list[int]. Это расчёт другого примера base=3, cap=12; он не реализует целиком контракт функции задачи с валидацией аргументов.

## Типичные ошибки

Повторять неверный payload — расходовать бюджет без шанса на исправление. Спать внутри открытой транзакции — удерживать ресурсы во время backoff. Ограничить только delay, но не attempts — получить бесконечный цикл. Независимые retry в клиенте, API и worker могут перемножить нагрузку.

## Задача

Реализуйте `backoff(attempt, base=1.0, cap=8.0) -> int | float` в main.py через обычные Python Run/Check. Верните min(cap, base * 2 ** (attempt - 1)). attempt — целое от 1 до 8, bool запрещён. base и cap — конечные положительные int/float, bool запрещён, base <= cap. При неверных аргументах ValueError. Функция только рассчитывает задержку, не вызывает sleep и не выполняет retry сама.

Например, используйте входы из практики выше; граничные и неверные входы также проверяются. Starter намеренно не содержит готового алгоритма.
