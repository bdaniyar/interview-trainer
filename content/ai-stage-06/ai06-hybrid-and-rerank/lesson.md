# Лексический поиск, RRF и reranking

У запроса «регламент X17» важен точный код. У парафраза важна тема. Hybrid поиск использует оба сигнала, а кандидатов объединяет по рангам.

## Учебные цели

- Сравнить лексический и dense поиск.
- Реализовать BM25, RRF и ограниченный rerank с проверкой IDs.

## Теория

Инвертированный индекс связывает слово со списком документов. PostgreSQL FTS превращает документ в `tsvector`, запрос в `tsquery`, а `@@` проверяет совпадение. `ts_rank_cd` использует покрытие и близость лексем. В P5 это лексический baseline. BM25 реализуем отдельно на маленьком корпусе.

TF — сколько раз термин встречается в документе. IDF больше для редкого слова: `ln(1+(N-df+0.5)/(df+0.5))`, где N — число документов, df — число документов с термином. Вклад термина BM25 равен `IDF*TF*(k1+1)/(TF+k1*(1-b+b*D/avgD))`. D — длина документа в токенах. k1 управляет насыщением: десятое повторение помогает меньше первого. b управляет поправкой на длину.

Dense bi-encoder независимо кодирует запрос и текст. Cross-encoder оценивает пару совместно, поэтому обычно применяется к малому shortlist. RRF суммирует `1/(K+rank)` по веткам. Ранг начинается с 1 после dedup. K сглаживает преимущество первого места. Дополнительный scripted reranker оценивает только первые N доступных результатов и оставляет хвост в прежнем порядке.

## Модель понимания

При K=4 списки [a,b] и [b,c] дают b 1/6+1/5, a 1/5 и c 1/6. Вес сырого score здесь не нужен. Похожая лексема может дать несопоставимые численные значения в FTS и cosine.

## Что нужно знать на Junior

Оставь tenant и ACL внутри запросов к обоим источникам. Выход reranker не может создать нового кандидата, получить частный текст или вынести документ из чужого tenant в context.

## Примеры кода

```python
from math import log1p
idf = log1p((2 - 1 + .5) / (1 + .5))
print(round(idf * 2.2 / (1 + 1.2), 3))
for key, ranks in {"a": [1], "b": [2, 1], "c": [2]}.items():
    print(key, round(sum(1 / (4 + rank) for rank in ranks), 3))
```

Для TF=1 и D=avgD вклад BM25 равен `0.693`. RRF печатает a 0.2, b 0.367, c 0.167. Итоговый порядок b,a,c.

## Типичные ошибки

- Складывать сырые score из разных шкал.
- Считать повторы в одной ветке независимыми голосами.
- Давать reranker весь корпус или доверять новому ID из ответа.

## Вопросы с собеседований

1. Почему ts_rank_cd и BM25 сравниваются отдельно?
2. Зачем сначала dedup?
3. Почему rerank запускают после retrieval?

## Хорошие ответы

**Почему ts_rank_cd и BM25 сравниваются отдельно?**

PostgreSQL реализует собственную функцию ранжирования. Сравнивай их на одинаковых размеченных запросах.

**Зачем сначала dedup?**

Одна ветка даёт один вклад на ID. Повторы не влияют на ранги остальных кандидатов.

**Почему rerank запускают после retrieval?**

Парная оценка дороже поиска по индексу. Ограничь количество сравнений и передавай только разрешённые источники.

## Критерии хорошего ответа

Назови инвариант, покажи конкретный вход, объясни наблюдаемый результат и случай, когда операция должна завершиться отказом.

## Задача

Реализуй `bm25(query,corpus,k1=1.2,b=.75)`, `rrf(branches,rank_constant=60,limit=10)` и `rerank(ordered,allowed,n,scorer)`. Query и документы — списки подготовленных токенов. Считай один вклад на уникальный query term, нулевые score исключи. BM25 и RRF возвращают пары (ID, score), убывание, затем ID. RRF удаляет повторы внутри ветки до рангов, positive K и limit>=0. Rerank удаляет повторы и чужие ID, вызывает scorer ровно для первых n при непустом окне. Строго один конечный score на каждый ID, неизвестный или отсутствующий даёт ValueError. Хвост сохраняет порядок. Пример Run печатает b,a,c. Браузер проверяет формулы и границы, P5 запускает настоящий PostgreSQL FTS.

## Шпаргалка
