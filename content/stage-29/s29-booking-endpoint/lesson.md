## Теория

### Что это

Booking endpoint — не только INSERT брони. Он должен атомарно проверить доступность, зарезервировать единицу, сохранить идентичность запроса и не потерять notification intent.

### Как работает

Public contract принимает room_id и key. При новом key транзакция создаёт booking, conditional UPDATE уменьшает available только при available>0, затем сохраняет intent. SoldOut откатывает INSERT. Unique key разрешает concurrent retries, hash запрещает переиспользовать key для другого room.

Два разных запроса последнего места блокируются на одной строке inventory; после COMMIT первого PostgreSQL проверяет условие второго на актуальной версии. Он не возвращает строку, и второй получает 409. CHECK available>=0 дополнительно защищает состояние.

В monolith notification пишется в эту же transaction. В services booking COMMIT не ждёт consumer: клиент читает booking отдельно от notification status. Реальные интервальные бронирования могут требовать exclusion constraints; один integer inventory этого контракта их не моделирует.

### Важный нюанс / ограничение

Проверка доступности отдельным SELECT до INSERT недостаточна. Нужна атомарная граница, которая сохраняет invariant при независимых соединениях.

## Модель понимания

Проследите один booking от HTTP до durable state. Подпишите владельца данных и каждый COMMIT. На сетевой границе отдельно отметьте timeout, возможный повтор и наблюдаемое состояние receiver.

## Что нужно знать на Junior

### Обязательно

Доступность и создание брони меняются в одной транзакции. Request hash связывает key с телом. Успешный новый запрос и его replay имеют согласованный UUID; проигрыш за последний ресурс является ожидаемым бизнес-конфликтом.

## Типичные ошибки

Списать остаток до отдельного COMMIT брони — оставить частичное состояние. Использовать один ключ для разных room_id без проверки hash — скрыть ошибку клиента. Ждать notification внутри долгой transaction — связать row locks с сетью. Повторить неизвестный запрос с новым ключом — превратить retry в новую покупку.

## Шпаргалка

Вход валидируется, request key дедуплицируется, остаток и booking меняются атомарно, intent не теряется. После COMMIT response может пропасть: replay прежнего ключа восстанавливает известный результат без новой брони.
